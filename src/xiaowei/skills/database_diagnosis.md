# 数据库诊断工作方法

适用于 SQL 或查询慢、失败、结果异常。查询与诊断由你一个人完成，没有另外的诊断流程。

## 做法

1. 先判断回答这个问题需要哪些证据、已有哪些；缺什么补什么，不默认全面巡检，不为走流程调用工具。
2. 用取得的证据验证或推翻假设，修正判断；证据足以支持结论，或碰到能力、预算边界时停止。
3. 纯静态分析（看 SQL 写法、解释用户贴出的执行计划）不访问数据库；需要取证时按「数据库查询工作方法」的环境规则，只在用户选定的环境取证。
4. 先查后诊的任务（如“列出最近慢查询并分析最慢的一条”）直接复用已取得的证据，不重复取证。

## 取证

- 诊断 SQL 性能时按缺失证据选择 describe_table、describe_table_layout、explain_query，已有足够依据不必重复取证，缺什么就补什么；不要为诊断执行原查询；需要找实际运行慢的查询时用 list_slow_queries。
- 对 list_slow_queries 的某条原文取执行计划时，未写库名的物理表须按该行 database 补全；database 为空且无法确定原执行库时，不猜库，不获取计划。
- 执行计划是优化器按统计信息给出的估算，取得计划时没有执行原查询，不含实际耗时；审计记录的指标是实际运行值。表布局中的分区键只显示列名、不显示分区粒度，分区裁剪效果要结合计划中的 partitionRatio 判断。
- 通过 /诊断 进入时实际查询工具不可用，用可用的取证工具完成。

## 结论

- 文字中说明每个判断依据哪项结果（可把对应事实块放在旁边），并说明它是观察到的现象、可能原因还是优化建议；事实、原因判断、待验证假设、建议与限制分开写。
- 只有审计指标、没有取得执行计划时，只基于指标说明，不推断执行计划、不确认根因，并写明缺少什么、用户可以如何提供。
- 优化后的 SQL 只作为建议给出，不得声称已执行或已验证效果。收集统计信息、修改表属性或资源配置等管理变更只作为建议，不自行执行。
