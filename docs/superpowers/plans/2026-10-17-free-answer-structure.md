## 1. 背景

最终回答 `AgentAnswer`（`models.py:260`）是固定格子：`evidence_ids`、`inferences`、`clarification`、`advice` 三者互斥，每条分析必须关联本回答引用的证据，交付时套固定标题（`evidence.py:130-135`）。它用“限制回答形状”间接保护事实，带来两类问题：

- **表达不自然。** 问候只能走“澄清”，显示为“需要澄清（本轮未执行业务查询）”；有证据时的追问只能写进“分析”并挂“依据”；配置事实、能力说明没有位置；结论、数据、原因、建议不能按自然顺序组织。
- **失败来自形状而非事实。** 2026-10-16/17 生产日志中的 `answer_rejected`：`mixed_kinds` ×2、`inference_unlinked` ×1、`uncited_query` ×1，工具与数据源均正常。PR #110/#111 已让这类错误在 Runner 内改写一次，规则本身仍在。

形状限制也没有保证模型文字中的事实：`extra="forbid"` 只禁止多余字段，挡不住文字里写错数字。旧规则同样不证明推理正确。

## 2. 产品原则

> **模型自主决定回答结构、语气和内容组织；程序负责生成和验证系统可信事实。模型自由文字属于解释或推断，不得获得系统已核实事实的身份。**

**系统可信事实**：查询结果的数值、行与行数，实际执行的 SQL，告警/静默等监控事实及采集时间，动作的提出、批准、执行状态，以及截断、分页、未核实来源、容量与交付状态等完整性说明。只由代码从获准 Evidence、Action 记录或执行/交付账本生成。

**可执行的呈现承诺**（替代“事实只出现在事实块”）：只有代码生成的区域能获得“系统已核实”的呈现身份；来源标识由代码添加，不依赖模型自称“分析”。模型可以在文字中复述数字、结果编号，甚至写“系统根据证据生成”或 Markdown 表格，这些仍是模型解释，不能取得系统区域的身份（各渠道做法见 6.8）。不靠禁止模型使用某些词语来区分来源。

程序**不**保证模型推理正确，也不逐句核实模型文字；这部分靠完整展示证据、明确标识和真实模型评测衡量。

## 3. 本次范围与后续自由报告方向

**后续方向（已明确）：** 模型自主组织报告内容、设计版式并编写 HTML/CSS，小维负责事实绑定、安全检查和可靠交付；不预先规定章节、KPI 卡片、配色或布局。自由指表达和设计不受固定模板约束，权限、事实来源、安全和交付边界继续有效。

本次与后续的关系：

- **本次**解决自然回答、事实边界和完整交付，并把现有 HTML/MD 报告（`feishu_report.py`）适配到新回答；**不实现**模型自由编写完整 HTML/CSS。
- text/fact 顺序块是当前消息及现有报告适配的表达方式，**不是**未来所有报告的唯一布局。
- 后续 HTML 报告可以有模型设计的文档结构，共用现有 Evidence 验证、事实绑定、报告持久化（`xiaowei_delivery_part` 原字节）和附件交付链。
- 后续 MD 报告允许模型自主组织标题、段落、列表和表格；复杂布局与配色主要由 HTML 承担，MD 外观取决于阅读器。
- 普通消息文字块禁止原始 HTML（6.8），这条**不扩大**为禁止未来专门的 HTML 报告；后者需要独立的 HTML/CSS 安全检查（脚本、外链资源、表单、样式遮盖等）。
- 系统事实保护不等于固定视觉模板：模型可以设计事实所在区域，但不能隐藏或遮盖必需事实、来源标识、分页/截断说明和系统状态。
- 模型决定事实放在哪里，代码决定可信事实填什么；自由文字不会因报告通过安全检查就变成已核实事实。
- 未来自由 HTML 的事实引用方式和容量处理单独设计；不能假定现有 fact 块或任意文本切分已经解决，任意 HTML 也不能按字节截断。

本次不提前增加 report DSL、模板平台、通用文档框架或没有当前消费者的接口。

## 6. 设计

### 6.1 回答结构

模型通过 SDK `output_type` 提交按顺序排列的块，只有两种：

- `text`：模型自由文字（结论、解释、建议、追问、闲聊），按 6.8 的 Markdown 安全子集渲染。
- `fact`：模型只选择证据与展示方式（`full` / `brief`），内容由代码生成。

外加 `report_format`（沿用，语义见 6.7）。

**schema 形式在 S2 决定，不预设。** [事实] 用 SDK 0.22.3 的 `AgentOutputSchema` 实测：平铺可空字段同样生成 `anyOf`（`str | null`），嵌套 `TextBlock | FactBlock` 生成 `anyOf` + `$ref` + `const`，两者都能生成严格 schema。平铺写法还需额外校验字段组合，`type` 枚举挡不住 `fact + evidence_id=null`、`text + evidence_id` 等非法组合。S2 对比两种最小 schema 后取其一（6.10）。

**资源限制。** 模型文字合计字节上限与块数上限只约束模型输出规模（S2 定初始值，8.1），不照搬旧的逐项写作长度限制；能否内联发送由完整渲染后的实际请求字节与组件数决定（6.9），Session 容量按实际序列化历史与配置上限计算。

**版本判别放在可信外层。** 模型不输出 `format`。保存的 `TurnAnswer` 由代码写入答案版本；缺失视为旧版本，未知或损坏的版本按不可用处理，不静默回退（6.11）。

**空白归一化。** 空白 `text` 块与重复 `fact` 引用由代码丢弃或去重；最终没有任何可交付内容（无文字、无事实、无其余结果、无系统说明）时才拒绝。

### 6.2 职责分工

| 内容 | 谁决定 | 谁生成 |
| --- | --- | --- |
| 回答顺序、详略、语气，结论、解释、建议、追问 | 模型 | 模型（`text` 块） |
| 正文展示哪些事实、放在哪里、完整还是简要 | 模型 | 代码（`fact` 内容） |
| 查询数据、行数、实际 SQL、告警/静默事实、采集时间 | — | 代码，从当前渠道获准投影 |
| 动作状态与完整审批材料 | — | 代码，从 Action 记录（6.6） |
| 未核实来源、截断/分页/容量/附件状态、会话提示 | — | 代码，固定位置 |
| 本轮未放入正文的获准查询结果 | — | 代码，“其余结果”（6.4） |
| 执行失败或结果未知的说明 | — | 代码，只来自执行账本（6.5） |

### 6.4 “其余结果”

**来源。** 只来自可信执行记录，不用整个 `context_evidence`（含历史证据），也不用 `Delivery.basis`（`evidence.py:874`，只是本轮工具/对象提示，不是结果清单）。

**方案：交付时计算，不新增持久化清单。** 每次交付（首次、历史读取、重发）都对 `context_evidence` 做现有的 `_context_readable` 一批复核，在复核通过的 `EvidenceRecord` 中取：原执行轮次等于 `ctx.identity.turn_id`、工具属于“需交付结果”类别的证据，作为“本轮需交付结果全集”；减去模型显式 `fact` 引用，得到“其余结果”，按产生顺序展示。

理由：
- [事实] 交付上下文已有原执行轮次：`channel._validated` 重建 `TurnAnswer` 时不传 `run_turn_id`，但随后的 `channel._context` 设置 `turn_id = record.run_turn_id or record.turn_id`（`channel.py:558`），审批恢复轮也能确定原轮。现有 `_basis` 已按同一条件筛选本轮证据。
- [事实] 提交时 `context_evidence` 已包含本轮在工具范围内的全部 `produced` 证据（`app.py:766-769`），全集不会因“未列入清单”而缺项；不需要再证明一份清单的完整性，也没有“新版本缺清单字段”的解析分支。
- 代价 **[边界]**：工具类别按交付时的可信配置判断，不冻结提交时的范围。配置使工具不可用时证据复核失败、整条不交付（现有行为）；仅类别调整而工具仍可用时，历史读取按新类别展示，内容仍是同一批获准证据。

一致性：正常结束、暂停材料（`PausedTurn` 用暂停前原轮 `ctx.identity.turn_id`）、审批恢复（恢复原轮 `TurnLedger` 与原 `ctx.identity.turn_id`，不用审批请求的新 turn ID）、Session 最终校验（复用同一验证器）用同一计算函数。暂停前成功的查询仍属于原轮；一个请求已发送的分项不视为另一个请求已交付。

**需交付结果的工具类别。** [事实] `app._queries`（`app.py:405-418`）= query 用途 − diagnose 用途 − 发现读取（`PROMETHEUS_DISCOVERY_POLICIES | GRAFANA_READ_POLICIES`），再加 propose/approval；`_read_queries` 是其中 effect 为 read 的部分。按实际集合：

| 工具 | 归属 |
| --- | --- |
| StarRocks 实际只读查询 | 查询结果，进入“其余结果” |
| 与 diagnose 共有的元数据、EXPLAIN、审计慢查询等 | 不补全 **[已确认]** |
| Prometheus query / range | 查询结果 |
| Prometheus discovery、`GRAFANA_READ_POLICIES` | 不补全 **[已确认]** |
| Alertmanager 读取 | 查询结果 |
| `get_action_status`（`actions.action_status_catalog`，effect=read，经 `runtime._app_config` 进入 query 用途，因此在 `_read_queries` 中） | **动作区域**，不进“其余结果”或普通附件 |
| propose / approval | 动作区域（6.6）；不属于 `_read_queries` |
| write | 不进入 Runner 工具集合，其事实经 Action 投影 |

动作状态按可信 policy/tool 类别路由，不只凭 effect=read：结果不因重新分类被丢弃，仍完整展示在动作区域；历史只读状态查询不升级为新的待审批材料。不按工具名（如 list/get_status）泛化归类。

**授权。** 显式引用与其余结果一起进入同一批 `_context_readable` 复核；群聊/私聊、跨会话、撤权后任一不可读则整条回答不交付，不只验证最终选中的事实。

### 6.5 未完成执行（`unfinished`）

[事实] 现在的判定（`app.py:756-763`）在 Runner 返回后执行，不在 `_answer_check` 的模型改写路径内：`len(produced ∩ _queries) + 分类的监控失败 + 准备拒绝 != started ∩ _queries` 时，与 `uncited` 共用 `UNCITED_QUERY` 拒绝。账本含义见 `governance.py:391-420`。

新设计只做拆分：判定式不变；应用错误类型、日志原因与渠道映射同步区分 unfinished；用户回执仍为 `evidence_failed`，DB 回执码不变 **[已确认]**。已分类监控失败、取消、超时不改名为 unfinished。

测试预期（S1/S3）：

| 场景 | 预期 |
| --- | --- |
| 同工具两次调用，一次成功一次分类失败 | started=2，1 个结果 + 1 个失败，计数平衡，交付 |
| 分类失败后修正成功 | 失败记录保留，后续追加成功 Evidence，计数平衡 |
| 执行前拒绝 | 不计入 started |
| busy 退款 | 只针对确认零 SQL 的槽位超时（`_refund_before_io`，`governance.py:880`），不是任意超时 |
| 工具成功但 Evidence 保存失败 | produced 尚未追加，整轮失败 |
| 未分类监控异常 | 记录 unclassified 失败，可继续其他源 |
| 非监控执行异常 | 通常中止整轮 |
| 取消、整轮超时 | 走取消/超时路径，通常到不了最终计数检查 |
| 审批恢复 | 恢复原 `TurnLedger`；实际 write 不计入 `_queries`，approval 结果计入 |
| 用户拒绝审批 | 恢复路径产生 approval 状态证据，计数平衡 |
| proposal 明确拒绝 | 计入 `proposal_rejections`，计数平衡 |
| 审批后再次暂停 | 账本随新暂停保存，恢复后同式判定 |
| 同工具并发一成一败 | 与串行同样平衡 |

### 6.6 动作材料与状态

- 动作组件由代码从 Action 记录与动作状态证据生成，**置于回答最前**，模型块不能移除或改位；置顶的是完整组件，**不用摘要替换完整审批材料**。“进入动作区域并置顶”与 `requires_complete` 是两个独立判断：动作状态查询进入动作区域，但不因此获得 `requires_complete`。
- 保留 `requires_complete` 的专有语义，条件不变（[事实] `evidence.py:465-468`：effect 为 propose，或 effect 为 approval 且证据属于当前原执行轮次；propose 没有“必须本轮”的条件，历史提案的完整材料保护不能取消）：完整审批材料单独成 `approval` 分项（`feishu_delivery.py:170-200`），放不下时首次发送标记失败、重发直接拒绝，不预览、不转附件。
- 历史读取时继续按当前 Action 状态刷新并移除已失效的审批命令（`channel.py:470` 起）。
- 覆盖状态：待审批、已批准执行中、成功、失败、结果未知、拒绝、过期、升级作废、无法恢复、发起人失效、会话失效、反馈失败（`channel.py:89-130` 的 `_ACTION_FAILURE_CODES` 与 `_RECEIPTS`）。

### 6.7 澄清与报告

[事实] 旧契约中澄清忽略 `report_format`（`evidence.py:241`、`:431`），长澄清超容量直接失败、不转附件（`feishu_delivery.py:87-100`）。两种块加 `report_format` 无法直接表达“这是在等用户补充信息”。

**最小方案 [已确认]：** 回答增加一个布尔字段 `awaiting_user`，由模型声明“本条在等待用户补充信息”。为真时代码忽略 `report_format`、不生成文件，超容量按旧规则失败。这是一个显式字段，不按关键词猜，不恢复三套互斥结构。反例：用户要求 HTML 报告但没给集群，模型 `awaiting_user=true` 发普通消息澄清；残留的 `report_format` 被忽略。

未采用的备选：只靠提示词要求澄清时 `report_format` 为 null，模型出错时澄清问题会被做成报告文件。

**组合语义。** `awaiting_user` 只决定交付载体与超容量行为，不决定哪些内容要验证、补全或展示；不新增“有事实就不得 awaiting_user”的互斥规则。处理顺序：先形成并验证完整可信交付内容（6.9），再按 `awaiting_user` 选择载体。

| 组合 | 行为 |
| --- | --- |
| 纯文字 | 忽略 `report_format`，普通消息；超容量失败 |
| 带显式 fact | 事实照常完整验证与展示，可用事实卡片 |
| 本轮有未引用的查询结果 | 照常补全其余结果，不因 `awaiting_user` 提前返回 |
| 带动作材料 | 动作组件置顶，完整材料与独立 `approval` 分项回执不变 |
| 上述内容放不进普通消息 | 不生成文件、不删事实、不声称完整交付，明确失败；已确认发送的审批分项保持原状态 |

“普通消息”指不生成文件，可以是卡片，不等于纯文本。

### 6.8 呈现与来源区分

| 输出 | 现状 [事实] | 新设计 |
| --- | --- | --- |
| Web（`static/app.js`） | 只用 `textContent` 与 DOM API，不解析 HTML；事实与“分析与建议（模型推断）”分节 | 按块顺序渲染；事实块为代码生成的结构化区域，带“系统根据证据生成 · 结果 N · 来源 · 采集时间”；文字块为普通段落，不解析 Markdown。模型文字里的同样字样只是普通文字，不进入事实区域样式 |
| 飞书卡片（`feishu_render.py`） | 事实为卡片组件；模型文字经 `feishu_markdown.py` 白名单转为受限组件 | 事实块沿用代码组件与系统标题；文字块只经白名单转换，生成不了事实组件 |
| 飞书 post | 有模型文字且无 `basis` 时使用 `prose_post`，并把 `monitoring_notice`、`session_notice` 等代码说明插在前面（`feishu_render.py:521-537`）；锁定的 lark-channel-sdk 1.4.0 在平台返回 `format_error` 时把 post 的 text runs 拼成纯文本重发（`lark_channel/channel/outbound/sender.py:526-539`），不经 Transport 的 `mention_safe`，所以 `feishu_render.py:528-536` 预先检查降级文字 | post **只用于纯模型说明**（不含任何代码生成的说明）；只要同时含代码说明（查询事实、动作状态、监控失败、会话提示、分页/截断、交付说明）与模型文字，就走有来源边界的卡片。降级文字检查不变 |
| 纯文本 | 固定回执、容量说明用纯文本（如 `feishu_delivery.py:68-81`）；`_data_parts` → `_preview` 生成的附件正文可能同时含代码交付说明（“本次完整结果见附件”）与模型文字 | **承诺**：代码说明与模型文字不在同一纯文本或 post 中混排；需要同时出现时用卡片分区（附件正文、独立审批材料之后的剩余正文同样适用）。代码独立回执仍可用纯文本。纯模型说明可以是 post 或其纯文本降级 |
| MD/HTML 报告（`feishu_report.py`） | 代码模板，模型文字转义（如 `feishu_report.py:264`） | 本次按块顺序填入现有模板：事实章节由代码生成并带来源；文字段落转义，不能产生事实章节样式 |

**纯模型文字的剩余风险 [边界]：** 即使没有任何代码说明，模型仍可能在文字里写“系统已核实”。来源区分保证的是这类文字拿不到代码区域的呈现身份，不保证用户不被措辞误导；不靠禁用词语解决，由提示词与评测（E）衡量。

**普通消息 Markdown 安全子集**（以 `feishu_markdown.py` 现有行为为唯一实现；Web 不渲染 Markdown）。区分“可作为字面文字输入”和“支持格式化渲染”：
- 支持格式化渲染 [事实]：标题（转为加粗）、有序/无序列表、`**…**` 加粗、换行。斜体不生成斜体组件。
- 整段降级为 `plain_text` [事实]：传入文字含代码块或行内代码、含反斜杠、超过 `MAX_FORMAT_CHARS=3500` 或 `MAX_FORMAT_TOKENS` 时，**整个传入文字**按原文输出，不是只处理其中一段；不含任何受支持格式时同样为纯文字。
- 其余语法（原始 HTML、链接与自动链接、图片、表格、飞书 `<at>`/标签、样式）可作为字面文字出现，不渲染、不报错（Lark 特殊字符编码为实体）。本次不开放链接 **[已确认]**，也不为兑现格式能力新增斜体、代码格式或链接。
- 工具返回的字符串（事实单元格、SQL、告警标签）不进入 Markdown 解析，按纯文本组件或转义输出（`feishu_markdown.py` 文件头约束）。

### 6.9 容量与诚实交付

原则：**先形成完整可信交付内容（动作材料 → 模型块与显式事实 → 其余结果 → 系统说明），再做容量规划**。规划只决定放在正文还是附件，不删内容。“完整交付”指完整交付已返回的获准结果，不等于取得后端全部数据；分页、截断、未核实说明始终保留。

[事实] 现有机制（PR #107）：
- 卡片/post 按请求字节（`MAX_REQUEST_BYTES = 30_000`，`feishu_render.py:17`）和组件数（≤200，`feishu_delivery.py:137`）约束；纯文本回复受 `max_reply_chars`（配置 200–3500，`config.py:199`，`feishu.py:1108`、`:1275`）约束；`max_message_chars`（≤10000，`config.py:198`）是输入上限，不用于判断回复。
- 正文放不下时生成报告附件：每文件 `MAX_REPORT_BYTES = 400_000`（`feishu_report.py:16`），`build_reports` 按整章节或整行分文件（`feishu_report.py:426`）。400_000 是每文件上限，不是整轮预算。`expand_brief = delivery.report_format is not None`（`feishu_delivery.py:101-103`）：显式报告请求展开历史 `brief`；容量不足自动转 MD 时保留所选摘要。
- 每个分项（`approval`/`md`/`html`/`body`）保存原字节与发送状态；任一 `unknown` 则整体 `unknown`，有未发送分项则 `failed`；v1 飞书完成/暂停记录无分项按失败；v0 旧记录 `unknown` 不改为确定失败（`channel_store.py:955-980`）。
- 重发只发未发送分项，按原字节与原容量规则检查，不按新模板重建（`feishu_delivery.py:113-140`）。

新设计在此之上：
- “其余结果”与显式事实一起进入现有规划，正文放不下时转附件，正文保留代码生成的“完整结果见附件”说明。
- 单行超过文件上限、说明本身放不下时：交付失败并给代码回执，不截断事实、不声称已交付。
- 模型文字写“已全部发送”不改变可信交付状态；交付状态只由分项回执决定，用户可见的完成/未知说明由代码生成。
- 区分“程序生成了正确的失败说明”和“接收方实际收到”：渠道不可用时只保证状态如实记录，不承诺通知送达。
- Web 当前单次响应全部渲染、无附件；其实际容量上限与降级方式在 S3 核实 **[待验证]**。
- 现有报告拆分只适用于代码模板，**不是**未来自由 HTML 的通用拆分方案。

反例（S3 测试）：一个附件成功、另一个 unknown；单行超限；说明本身放不下；模型文字声称“已全部发送”。

来源边界组合（S3 测试，检查最终卡片与降级结果）：全源查询失败的未核实说明、会话容量提示、附件正文的交付说明、独立审批材料之后的剩余正文，分别与仿写“系统已核实”的模型文字组合；断言代码说明与模型文字不在同一 post/纯文本中混排。

`awaiting_user` 组合（S3 测试）：6.7 表中每行一例。

### 6.11 新旧兼容

**两个独立维度：** 答案版本（旧 `AgentAnswer` / 新块结构）与交付版本（PR #107 的 `delivery_version` v0/v1）。[事实] 旧 `AgentAnswer` 已可使用交付 v1。

| 情形 | 做法 |
| --- | --- |
| 未绑定交付内容 | 按答案版本解析并投影，复核当前权限 |
| v1 已绑定分项 | 复核当前权限后用 `xiaowei_delivery_part` 原字节、分项身份、UUID 与回执；已确认 `sent` 的分项不重发 |
| v0 已绑定报告 | 经 `get_bound_report`（`channel_store.py:1219`）读取 `xiaowei_report` 原字节；没有 v1 分项不等于没绑定过旧报告 |
| 上传 `unknown` | 禁止重新上传（`feishu_delivery.py:356`） |
| 消息发送 `unknown` | 不自动重试；用户明确手动补发时沿用原 UUID 补发路径并保留可能重复的说明 |
| 后续明确失败 | 不能把此前的 `unknown` 覆盖为确定未送达（`channel_store.py:955-980`） |
| v0 `sent` | 不追认为“完整结果已交付”；现有审批前提中 v0 `sent` 视为材料已送达（`channel_store.py:1916`）的规则不变 |
| 最早期只存 `AgentAnswer`、无 `context_evidence` | 继续拒绝交付（`channel.py:454`） |
| 缺版本字段 | 只进入严格旧格式解析，不接受任意缺版本数据 |
| 未知版本、损坏 JSON、已知新版本缺必需字段 | 拒绝；新版本解析失败不回退旧版本 |

需要兼容的读取路径（“不迁移历史数据”不等于不需要兼容解析）：
- `channel_store._saved_answer`（`:2151`）与 `channel_store._record`（`:2001`，另行解析 `TurnAnswer.run_turn_id`）；
- Session 最终项校验（`session.py:480-495`）：新轮次只接受新格式；回放历史中的旧助手消息与工具证据照常作为模型历史；
- `channel._validated`（`channel.py:449`）重建 `TurnAnswer`、刷新动作状态、移除失效审批命令；
- 历史读取、重发、报告原文件（原字节，`channel_store.py:1220`）；
- 审批暂停/恢复（下）。

**审批暂停的 RunState。** [事实] `app._native_binding`（`app.py:894`）由应用绑定、openai-agents 与 mcp 版本、本轮工具的证据指纹组成，不含答案契约版本；恢复时不一致抛 `action_not_approvable`（`app.py:1114`），但不作废候选，候选保持 `pending` 直到过期，回执也不具体。`migrations/010_sdk_approval.sql` 只是对当时存量数据的一次性作废，不会因答案格式变化重新执行。`reject_native`（`channel_store.py:1822`）当前只接受三种原因，不含 `action_upgrade_invalidated`（DB 约束已允许该码）。

策略（S2 后条件性选择方案 1，正式入口在 S3 验证，不成立改方案 2；见 8.1）：
1. **兼容**：SDK 恢复时由新代码重建 Agent，最终输出按新 schema 生成；若实验证明旧暂停 RunState（历史项为旧格式）能用新 Agent 恢复并产出合法新回答，则不改绑定，直接恢复。
2. **不兼容**：在 `_native_binding` 加入答案契约版本（只影响待审批候选，不动 Session 绑定 `self._binding`，不废弃旧会话）；不一致时在业务写 I/O 之前调用 `reject_native(action, "action_upgrade_invalidated")`（作废本身要写数据库；放宽其原因白名单，无需迁移），用户收到“已因升级作废、未执行，请重新提出”。[事实] `_reject_native`（`channel_store.py:1832-1860`）作废同一原轮内全部 `pending` 候选并消费该恢复记录，SQL 不覆盖 executing/succeeded/unknown，不修改 Session。

两种做法下，已执行、执行中或结果未知的动作都在绑定检查之前被 `state != "pending"` 拦下（`app.py:1080`），保留原状态，不重放。

已有证据与缺口：S2 的 SDK + 隔离 PostgreSQL 实验结果与条件性选择见 8.1。它不代表完整小维恢复链通过；Action claim、Evidence、PolicySession、权限复核、并发防重与真实 provider 的兼容仍待 S3/S4 **[待验证]**。

- 离线用例与预期（对最终选定 schema）：非法字段组合拒绝；未知引用最多改写一次；改写不增加业务工具调用；改写失败受控；超长、Unicode 多字节按累计字节判定；块数上限；旧历史回放、旧 RunState 暂停恢复（批准、拒绝）、预算结束收尾各一例。任一非法输入不得静默通过。
- 移到 S3（属于新契约的归一化与交付校验，不在 spike 中提前实现）：重复引用去重、空白块丢弃；系统权限失败不改写。
- 真实样例（需批准凭据，S4 执行，不是 S2 离线实验的前提）判据：格式成功率、改写率、任务正确率、完整交付率、耗时与用量，与真实评测基线 `9231f45` 同批对比。阈值现在不定 **[已确认]**：真实评测开始前先在基线版本上取基准（基线需先按 S0 部署，待安排），再与用户确定，原则是新版不低于旧版，按指标方向理解：成功率、正确率、交付率越高越好；耗时、用量、改写率越低越好。
- 结论：选定 schema 形式与资源上限，RunState 选 6.11 的方案 1 或 2。

### 8.1 S2 离线结论（2026-10-17，实验基线 `9231f45`，等待定向复审）

实验文件 `tests/spike/test_answer_s2_protocol.py`（锁定 openai-agents 0.22.3；真 SDK Runner、`ScriptedModel`、本地 `VertexModel` + `MockTransport`、现有飞书渲染器、隔离 PostgreSQL 测试实例），59 passed。

**验证层次。** 只验证 6.10 四层中的前两层：SDK 生成与本地校验、本地 `VertexModel` 转发。真实 provider 接受与真实模型遵守、任务质量待获准后安排，不能由“关键字集合与生产相同”推导为线上兼容。

**现有生产 schema 已用到的关键字**（[事实] `AgentOutputSchema(AgentAnswer)`）：`$defs`、`$ref`、`anyOf`（仅“类型或 null”）、`enum`、`maxLength`、`minLength`、`default`、`additionalProperties`、`required` 等。未用到：`const`、`maxItems`、`discriminator`、对象之间的 `anyOf`。

| 对比项 | 平铺（`type` + 可空字段） | 嵌套联合（`TextBlock \| FactBlock`） |
| --- | --- | --- |
| SDK 严格 schema | 可生成 | 可生成 |
| 相对生产的新关键字 | 无 | `const`；对象之间的 `anyOf` |
| 非法字段组合 | schema 全部放行，须手写逐字段组合校验；首版校验漏掉“text 带 evidence_id、view 为空”，被改写用例发现 | 类型本身拒绝，无需手写 |
| 模型读 schema | 看不出哪些字段属于哪种块 | 每种块的必填字段自描述 |
| `Field(discriminator=…)` | — | 会把 OpenAPI 的 `discriminator` 写进 schema，**不用** |

**选定：嵌套联合，发送前把单值 `const` 改写为单值 `enum`。** `_AnswerSchema`（已是 `AgentOutputSchema` 子类）覆盖 `json_schema()`，只改发给 provider 的 schema，本地解析仍按 `Literal` 类型；改写后关键字集合不超出生产已用集合，唯一的新形态是对象之间的 `anyOf`。真实 Vertex 是否接受该形态 **[待验证]**；若实际拒绝，再改用本实验同样覆盖过的平铺 + 逐字段组合校验，不得降级为无约束输出。本地 `VertexModel` 对平铺、嵌套（`const`）、选定方案都原样转发 `responseJsonSchema`；provider 返回 400 时如实失败。

**选定方案（嵌套 + 单值 enum + 合成引用预检）的离线覆盖**，平铺作为退路以同一参数化覆盖：

| 路径 | 断言 |
| --- | --- |
| 未知引用、非法字段组合、文字累计字节超限 | 各被拒绝后由 `invalid_final_output` 无工具改写一次合格；业务工具执行 1 次；处理器调用 1 次、模型调用 3 次、预留的第 4 步未被消费；改写调用不带业务工具；最终类型就是选定类型 |
| 改写仍失败 | 抛出原 `ModelBehaviorError`；业务工具 1 次、改写 1 次、预留步未消费 |
| `max_turns` 收尾 | 无工具收尾调用产出选定类型 |
| 旧助手回答历史回放 | 同一 `SQLAlchemySession` 中旧 `AgentAnswer` JSON 原样作为助手历史送入模型，新回答按选定类型解析 |
| 旧审批 RunState（批准、拒绝各一独立用例） | 见下 |
| 每次模型调用（含改写、收尾、恢复） | 拿到的 schema 等于选定 schema，且无生产以外的关键字：schema 转换与引用预检同时生效 |

引用预检使用实验中的合成可见集合，不代表正式 Evidence 授权链已验证。三组变异（去掉引用预检、去掉预算校验、去掉 `const`→`enum` 转换）分别使 3、6、9 个选定方案用例失败。

**资源上限（初始值，只约束模型输出规模，均在代码校验）：**
- 模型文字合计 **16_000 UTF-8 字节**（约 5300 个汉字，高于旧 `advice` 4000 字），块数 **64**。
- 边界用例：16_000 与 16_001 字节；多个文字块累计（8_000 + 8_000 通过，再加 1 字节拒绝）；“中”×5333（15_999 字节）通过、×5334（16_002 字节，字符数远低于上限）拒绝；4 字节 emoji ×4000 通过、再加 1 字节拒绝；64 块通过、65 块拒绝。[事实] schema 的 `maxLength` 只数字符，所以字节预算在代码校验，不新增 `maxItems`。
- **这两个数不保证内联交付。** 用现有渲染器的反例（测试断言超过真实阈值，不固定快照）：16_000 字节双引号文字加一条事实，JSON 两次转义和请求包装使请求超过 30_000 字节的两倍；64 条小事实的组件数远超 200，现有渲染器只能发容量说明；回答 JSON 本身也大于文字原始字节。独立审核实测同类输入为请求 66,956 字节、64 条事实 1,148 个组件、请求 69,344 字节（来源：独立审核；本次自行复现了 66,956 字节一例；组件数按每条事实增量 17 个推算 64 条约 1,088 个，未绕过上限实测）。这些是现有渲染器的反例，不是 S3 新渲染器的测量。
- 因此：能否内联发送由完整渲染后的实际请求字节与组件数决定；Session 容量按实际序列化历史计算，上限来自配置；超限后转附件、明确失败与诚实说明由 S3 交付链验证；`awaiting_user=true` 时仍不生成文件，放不下即明确失败。
- 本次消息上限不经单独设计不成为未来自由 HTML/MD 报告的通用上限（第 3 节）。

**旧格式恢复（6.11）：**
- 流程（批准、拒绝各一独立用例，选定方案与平铺都跑）：同一 `SQLAlchemySession` 先保存一条旧 `AgentAnswer` 助手回答 → 下一轮旧 Agent 调用需审批的合成工具并暂停 → `RunState` 序列化后写入 PostgreSQL 并提交 → 新连接读回、与原快照一致 → 同名、选定 schema 的新 Agent `RunState.from_string` 恢复。
- [事实] 暂停快照的 `original_input` 含旧格式 JSON（独立审核先复现，本次用例断言）；恢复时它作为助手历史送入新 Agent 的模型调用。
- 批准：合成写工具执行 1 次，新回答按选定类型解析；拒绝：工具 0 次，新回答同样合法。
- **条件性选择方案 1（兼容恢复，不改 `_native_binding`）。** 理由：恢复时使用新代码重建的 Agent 与 output schema；旧格式助手回答可能存在于输入历史中，实验验证它可以保留并回放。不以“暂停状态不含旧回答”为前提。
- 边界：以上证明 SDK 机制与实验中的存取流程；不证明正式 Action claim、Evidence、PolicySession、权限复核与并发防重完整链；单次实验执行一次不等于重复恢复的全局幂等。正式入口的批准、拒绝恢复用例留 S3；不成立则改用方案 2（本轮未实现）。

**S2 离线完成项：** 两种 schema 对比与选定；选定方案的非法组合、未知引用改写、字节与块数边界、改写失败、收尾、旧历史回放、旧 RunState 批准/拒绝恢复；本地 `VertexModel` 转发与 400 如实失败；容量反例与论据修正。

**留 S3：** 重复引用去重与空白块丢弃（新契约归一化）；系统权限失败不改写（`evidence_unavailable` 在 Runner 返回后的交付校验，不进 schema 预检）；正式 Evidence 授权链下的引用预检；新渲染器下的转附件、明确失败与诚实说明；正式入口的审批恢复。

**真实 provider / 模型待验证（S4，需批准凭据）：** 真实 Vertex 是否接受对象之间的 `anyOf`；真实模型遵守率、改写率与任务质量。先在真实评测基线 `9231f45` 上跑第 9 节 E 项样例取基准（基线部署待安排），再与用户定阈值，新版同批对比；复用 `scripts/dialogue_real_model.py` 与 `scripts/gate0_real_model.py` 的执行方式，评分口径按第 7 节改为“结论与全部结果一致”。
