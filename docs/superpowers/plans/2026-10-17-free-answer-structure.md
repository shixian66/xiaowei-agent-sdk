# 自由表达的回答结构：模型组织表达，代码保证可信事实

> 状态：**设计提案（修订版），待复审与用户确认**。基线 `c00ede6`（PR #111 合入后的 main），文中代码位置均按该版本核对。本文不改代码；确认后再写入 ARCHITECTURE 并按第 8 节切片实施。
>
> 标记：**[事实]** 已按 `c00ede6` 源码核对；**[待验证]** 需在指定切片实验或评测；**[边界]** 明确接受的限制；**[待确认]** 未定的产品取舍。

## 1. 背景

最终回答 `AgentAnswer`（`models.py:260`）是固定格子：`evidence_ids`、`inferences`、`clarification`、`advice` 三者互斥，每条分析必须关联本回答引用的证据，交付时套固定标题（`evidence.py:130-135`）。它用“限制回答形状”间接保护事实，带来两类问题：

- **表达不自然。** 问候只能走“澄清”，显示为“需要澄清（本轮未执行业务查询）”；有证据时的追问只能写进“分析”并挂“依据”；配置事实、能力说明没有位置；结论、数据、原因、建议不能按自然顺序组织。
- **失败来自形状而非事实。** 2026-10-16/17 生产日志中的 `answer_rejected`：`mixed_kinds` ×2、`inference_unlinked` ×1、`uncited_query` ×1，工具与数据源均正常。PR #110/#111 已让这类错误在 Runner 内改写一次，规则本身仍在。

形状限制也没有保证模型文字中的事实：`extra="forbid"` 只禁止多余字段，挡不住文字里写错数字。旧规则同样不证明推理正确。

## 2. 产品原则

> **模型自主决定回答结构、语气和内容组织；程序负责生成和验证系统可信事实。模型自由文字属于解释或推断，不得获得系统已核实事实的身份。**

**系统可信事实**：查询结果的数值、行与行数，实际执行的 SQL，告警/静默等监控事实及采集时间，动作的提出、批准、执行状态，以及截断、分页、未核实来源、容量与交付状态等完整性说明。只由代码从获准 Evidence、Action 记录或执行/交付账本生成。

**可执行的呈现承诺**（替代“事实只出现在事实块”）：只有代码生成的区域能获得“系统已核实”的呈现身份；来源标识由代码添加，不依赖模型自称“分析”。模型可以在文字中复述数字、结果编号，甚至写“系统根据证据生成”或 Markdown 表格，这些仍是模型解释，不能取得系统区域的身份（各渠道做法见 6.8）。不靠禁止模型使用某些词语来区分来源。

程序**不**保证模型推理正确，也不逐句核实模型文字；这部分靠完整展示证据、明确标识和真实模型评测衡量。

## 3. 本次范围与后续自由报告方向

**后续方向（已明确）：** 模型自主组织报告内容、设计版式并编写 HTML/CSS，小维负责事实绑定、安全检查和可靠交付；不预先规定章节、KPI 卡片、配色或布局。自由指表达和设计不受固定模板约束，权限、事实来源、安全和交付边界继续有效。

本次与后续的关系：

- **本次**解决自然回答、事实边界和完整交付，并把现有 HTML/MD 报告（`feishu_report.py`）适配到新回答；**不实现**模型自由编写完整 HTML/CSS。
- text/fact 顺序块是当前消息及现有报告适配的表达方式，**不是**未来所有报告的唯一布局。
- 后续 HTML 报告可以有模型设计的文档结构，共用现有 Evidence 验证、事实绑定、报告持久化（`xiaowei_delivery_part` 原字节）和附件交付链。
- 后续 MD 报告允许模型自主组织标题、段落、列表和表格；复杂布局与配色主要由 HTML 承担，MD 外观取决于阅读器。
- 普通消息文字块禁止原始 HTML（6.8），这条**不扩大**为禁止未来专门的 HTML 报告；后者需要独立的 HTML/CSS 安全检查（脚本、外链资源、表单、样式遮盖等）。
- 系统事实保护不等于固定视觉模板：模型可以设计事实所在区域，但不能隐藏或遮盖必需事实、来源标识、分页/截断说明和系统状态。
- 模型决定事实放在哪里，代码决定可信事实填什么；自由文字不会因报告通过安全检查就变成已核实事实。
- 未来自由 HTML 的事实引用方式和容量处理单独设计；不能假定现有 fact 块或任意文本切分已经解决，任意 HTML 也不能按字节截断。

本次不提前增加 report DSL、模板平台、通用文档框架或没有当前消费者的接口。

## 5. 非目标与暂缓

| 暂缓项 | 理由 | 复查触发条件 |
| --- | --- | --- |
| 模型自由编写完整 HTML/CSS 报告 | 已明确的后续方向，需独立的 HTML 安全检查、事实引用与容量设计 | 本次 S3 上线后单独立项 |
| 文字中的数值占位符 | 行选择、字段重名、格式化、权限与派生计算会演变成新 DSL | 评测显示“文字中直接写查询数值且出错”比例显著 |
| 模型标记某次结果“已被取代” | 筛选不同不等于取代，易成为隐藏数据的口子 | 用户反馈“其余结果”重复展示造成明显干扰 |
| 提交回答工具模式 | SDK 0.22.3 已有 `tool_use_behavior` / `ToolsToFinalOutputResult`，不需要另建 Loop；但迁移要改 Vertex 适配器（`vertex_model.py:60` 未映射 `tool_choice`，取值即拒绝）、历史结构、审批恢复与收尾，收益尚未成立 | 上线后 `answer_repair` 仍频繁失败，或常需补查证据才能改对 |
| 自然语言事实核查 | 无可靠确定性方法 | 由评测指标驱动 |

## 6. 设计

### 6.1 回答结构

模型通过 SDK `output_type` 提交按顺序排列的块，只有两种：

- `text`：模型自由文字（结论、解释、建议、追问、闲聊），按 6.8 的 Markdown 安全子集渲染。
- `fact`：模型只选择证据与展示方式（`full` / `brief`），内容由代码生成。

外加 `report_format`（沿用，语义见 6.7）。

**schema 形式在 S2 决定，不预设。** [事实] 用 SDK 0.22.3 的 `AgentOutputSchema` 实测：平铺可空字段同样生成 `anyOf`（`str | null`），嵌套 `TextBlock | FactBlock` 生成 `anyOf` + `$ref` + `const`，两者都能生成严格 schema。平铺写法还需额外校验字段组合，`type` 枚举挡不住 `fact + evidence_id=null`、`text + evidence_id` 等非法组合。S2 对比两种最小 schema 后取其一（6.10）。

**资源限制。** 统一总字节预算（按现有 Session 与渠道容量推导，S2 定值）；块数只设宽裕的防滥用上限；不照搬旧的逐项写作长度限制。

**版本判别放在可信外层。** 模型不输出 `format`。保存的 `TurnAnswer` 由代码写入答案版本；缺失视为旧版本，未知或损坏的版本按不可用处理，不静默回退（6.11）。

**空白归一化。** 空白 `text` 块与重复 `fact` 引用由代码丢弃或去重；最终没有任何可交付内容（无文字、无事实、无其余结果、无系统说明）时才拒绝。

### 6.2 职责分工

| 内容 | 谁决定 | 谁生成 |
| --- | --- | --- |
| 回答顺序、详略、语气，结论、解释、建议、追问 | 模型 | 模型（`text` 块） |
| 正文展示哪些事实、放在哪里、完整还是简要 | 模型 | 代码（`fact` 内容） |
| 查询数据、行数、实际 SQL、告警/静默事实、采集时间 | — | 代码，从当前渠道获准投影 |
| 动作状态与完整审批材料 | — | 代码，从 Action 记录（6.6） |
| 未核实来源、截断/分页/容量/附件状态、会话提示 | — | 代码，固定位置 |
| 本轮未放入正文的获准查询结果 | — | 代码，“其余结果”（6.4） |
| 执行失败或结果未知的说明 | — | 代码，只来自执行账本（6.5） |

### 6.3 校验规则

| 规则 | 现状 | 新设计 | 处理方 |
| --- | --- | --- | --- |
| 引用当前上下文外的证据（`unknown_evidence`） | 拒绝 | **保留** | 输出 schema 预检，可改写一次 |
| 块字段组合非法、超出资源上限 | — | 新增 | 输出 schema 预检，可改写一次 |
| 上下文任一证据当前不可读（`evidence_unavailable`） | 整条拒绝 | **保留**：即使回答只有文字也复核（模型可能复述可见证据） | 交付校验，不改写 |
| 模型、Session、当前渠道投影交集；Evidence owner/session/channel 归属；权限、策略、有效期、依赖 | 交付与历史复核 | **保留**，显式引用与其余结果走同一授权链 | 交付校验，不改写 |
| 夹带字段（`extra="forbid"`） | 拒绝 | **保留** | schema |
| 三选一互斥（`mixed_kinds`） | 拒绝 | 删除 | — |
| 每条分析须关联证据（`inference_unlinked`） | 拒绝 | 删除 | — |
| 缺证据（`missing_evidence`） | 拒绝 | 删除；**不**据此推断“本轮未查询” | — |
| 查询结果须全部引用（`uncited_query`） | 拒绝 | 改为程序补全（6.4）；不再要求模型引用全部结果 | 代码 |
| 已开始的查询既无结果也无分类失败（现与 `uncited_query` 混用） | 拒绝 | 独立系统失败（6.5），不进入模型改写 | 代码 |
| 重复引用（`duplicate_evidence`） | 拒绝 | 自动去重 | 代码 |
| 本轮新事实选 `brief` | 拒绝 | 自动改为完整 | 代码 |
| 非飞书渠道设置 `report_format` | 拒绝（误记 `mixed_kinds`，`evidence.py:241-243`） | 正文照常交付，附代码说明“当前渠道不支持文件” | 代码 |

规则仍集中在 `evidence.citation_error`（PR #111），由本轮输出 schema 预检与交付校验共用；自动去重、brief 升 full 在两处用同一归一化函数，Session 提交（`session.py:480-495` 复用同一验证器）与交付看到的结果一致。

### 6.4 “其余结果”

**来源。** 只来自可信执行记录，不用整个 `context_evidence`（含历史证据），也不用 `Delivery.basis`（`evidence.py:874`，只是本轮工具/对象提示，不是结果清单）。

**清单在提交时由代码确定并随 `TurnAnswer` 保存**（新增字段，可信外层）：本轮 `TurnRuns.produced` 中、原执行轮次为本轮、工具属于“需交付结果”类别、且未被模型 `fact` 引用的证据，按产生顺序。每次交付、历史读取、重发都校验它是 `context_evidence` 的子集并按当前权限复核。保存而不在读取时重算，原因是：[事实] `channel._validated`（`channel.py:457`）重建 `TurnAnswer` 时不带 `run_turn_id`，审批恢复轮的执行轮次与请求轮次不同，读取时无法可靠重算“本轮”。

**需交付结果的工具类别。** [事实] `app._queries`（`app.py:410-418`）= query 用途 − diagnose 用途 − 发现读取，再加 propose/approval 工具，不等于“所有只读工具”。新设计拆开两类：
- **查询结果**：`_read_queries`（`_queries` 中 effect 为 read 的部分）的成功证据，进入“其余结果”。
- **动作材料**：propose/approval 证据只进入动作组件（6.6），不进“其余结果”，也不转普通数据附件（沿用 `evidence.py:465` 的约束）。
- diagnose/发现读取保持现状：不强制交付。是否纳入作为 **[待确认]** 列入第 10 节。

**授权。** 显式引用与其余结果一起进入现有 `_context_readable` 一批复核；群聊/私聊、跨会话、撤权后任一不可读则整条回答不交付，不只验证最终选中的事实。

### 6.5 未完成执行（`unfinished`）

[事实] 现在的判定（`app.py:756-763`）：`len(produced ∩ _queries) + 分类的监控失败 + 准备拒绝 != started ∩ _queries`，不等则按 `uncited_query` 拒绝。账本含义（`governance.py:391-420`）：`started` 是通过前置检查、占用预算后开始执行的调用；I/O 前拒绝不进入 `started`；确认零 SQL 的槽位超时经 `_refund_before_io`（`governance.py:880`）从 `started` 移除并退还预算；多数执行后失败直接中止整轮。

新设计：
- 判定式不变，但改用独立系统失败原因，日志可区分；它表示“开始执行但结果去向不明”，**不交模型改写**（改写不会让结果出现，只会诱导重查）。
- 用户回执沿用 `evidence_failed`，不新增 DB 失败码（避免迁移）；是否需要独立用户可见码 **[待确认]**。
- 审批恢复：`TurnLedger` 随暂停保存，恢复后账本含暂停前计数，判定沿用同一式子。

需要的反例（S3 测试）：同一工具两次调用一成一败（分类失败）；失败后重试成功；执行前拒绝与 busy 退款不计入；工具成功但 Evidence 保存失败（应整轮失败，不能静默通过）；未分类失败、取消、超时；审批恢复前后计数一致。

### 6.6 动作材料与状态

- 动作组件由代码从 Action 记录生成，**置于回答最前**，模型块不能移除或改位；置顶的是完整组件，**不用摘要替换完整审批材料**。
- 保留 `requires_complete`（`evidence.py:465-471`：本轮 propose 及本轮 approval 证据）的专有语义：完整审批材料单独成 `approval` 分项（`feishu_delivery.py:170-200`），放不下时首次发送标记失败、重发直接拒绝，不预览、不转附件。
- 历史读取时继续按当前 Action 状态刷新并移除已失效的审批命令（`channel.py:470` 起）。
- 覆盖状态：待审批、已批准执行中、成功、失败、结果未知、拒绝、过期、升级作废、无法恢复、发起人失效、会话失效、反馈失败（`channel.py:89-130` 的 `_ACTION_FAILURE_CODES` 与 `_RECEIPTS`）。

### 6.7 澄清与报告

[事实] 旧契约中澄清忽略 `report_format`（`evidence.py:241`、`:431`），长澄清超容量直接失败、不转附件（`feishu_delivery.py:87-100`）。两种块加 `report_format` 无法直接表达“这是在等用户补充信息”。

**最小方案 [待确认]：** 回答增加一个布尔字段 `awaiting_user`，由模型声明“本条在等待用户补充信息”。为真时代码忽略 `report_format`、不生成文件，超容量按旧规则失败。这是一个显式字段，不按关键词猜，不恢复三套互斥结构。反例：用户要求 HTML 报告但没给集群，模型 `awaiting_user=true` 发普通消息澄清；残留的 `report_format` 被忽略。

不采用时的取舍：去掉该语义，只靠提示词要求澄清时 `report_format` 为 null；模型出错时澄清问题会被做成报告文件。这改变旧行为，需明确接受。

### 6.8 呈现与来源区分

| 输出 | 现状 [事实] | 新设计 |
| --- | --- | --- |
| Web（`static/app.js`） | 只用 `textContent` 与 DOM API，不解析 HTML；事实与“分析与建议（模型推断）”分节 | 按块顺序渲染；事实块为代码生成的结构化区域，带“系统根据证据生成 · 结果 N · 来源 · 采集时间”；文字块为普通段落，不解析 Markdown。模型文字里的同样字样只是普通文字，不进入事实区域样式 |
| 飞书卡片（`feishu_render.py`） | 事实为卡片组件；模型文字经 `feishu_markdown.py` 白名单转为受限组件 | 事实块沿用代码组件与系统标题；文字块只经白名单转换，生成不了事实组件 |
| 飞书 post | 仅有模型文字且无 `basis` 时使用 `prose_post`（`feishu_render.py:521-537`）；锁定的 lark-channel-sdk 1.4.0 在平台返回 `format_error` 时把 post 的 text runs 拼成纯文本重发（`lark_channel/channel/outbound/sender.py:526-531`），不经 Transport 的 `mention_safe`，所以 `feishu_render.py:528-536` 预先检查降级文字 | 保留：post 只用于不含系统事实的回答；降级文字检查不变 |
| 纯文本 | 代码自己的纯文本只用于固定回执、纯说明和容量说明（如 `feishu_delivery.py:68-81`）；事实只经卡片或报告文件交付 | **承诺**：含系统事实的回答不以纯文本混排模型文字交付，放不下时转附件并附代码说明（S3 加断言）。纯文本没有样式，模型仿写的标识无法区分 — **[边界]** 只发生在不含系统事实的纯说明中，由评测抽查 |
| MD/HTML 报告（`feishu_report.py`） | 代码模板，模型文字转义（如 `feishu_report.py:264`） | 本次按块顺序填入现有模板：事实章节由代码生成并带来源；文字段落转义，不能产生事实章节样式 |

**普通消息 Markdown 安全子集**（以 `feishu_markdown.py` 现有白名单为唯一实现；Web 不渲染 Markdown）：
- 允许：段落、标题、列表、代码块/行内代码、加粗/斜体、换行（[事实] `MarkdownIt("zero", {"maxNesting": 16})` 只启用这些规则）。
- 不允许：原始 HTML、链接与自动链接、图片、表格、飞书 `<at>`/标签、颜色等样式。不支持的语法按原文显示（Lark 特殊字符编码为实体），不报错。是否开放 `https` 链接 **[待确认]**，默认不开放。
- 预算：`MAX_FORMAT_CHARS=3500`、`MAX_FORMAT_TOKENS`、嵌套深度 16；超出或含反斜杠的段落整段按 `plain_text` 保留（现有行为）。
- 工具返回的字符串（事实单元格、SQL、告警标签）不进入 Markdown 解析，按纯文本组件或转义输出（`feishu_markdown.py` 文件头约束）。

### 6.9 容量与诚实交付

原则：**先形成完整可信交付内容（动作材料 → 模型块与显式事实 → 其余结果 → 系统说明），再做容量规划**。规划只决定放在正文还是附件，不删内容。“完整交付”指完整交付已返回的获准结果，不等于取得后端全部数据；分页、截断、未核实说明始终保留。

[事实] 现有机制（PR #107）：
- 卡片/post 按请求字节（`MAX_REQUEST_BYTES = 30_000`，`feishu_render.py:17`）和组件数（≤200，`feishu_delivery.py:137`）约束；纯文本受 `max_message_chars`（配置 ≤10000）约束。
- 正文放不下时生成报告附件：每文件 `MAX_REPORT_BYTES = 400_000`（`feishu_report.py:16`），`build_reports` 按整章节或整行分文件（`feishu_report.py:426`）；附件中历史 `brief` 展开为完整（`expand_brief`）。
- 每个分项（`approval`/`md`/`html`/`body`）保存原字节与发送状态；任一 `unknown` 则整体 `unknown`，有未发送分项则 `failed`；v1 飞书完成/暂停记录无分项按失败；v0 旧记录 `unknown` 不改为确定失败（`channel_store.py:955-980`）。
- 重发只发未发送分项，按原字节与原容量规则检查，不按新模板重建（`feishu_delivery.py:113-140`）。

新设计在此之上：
- “其余结果”与显式事实一起进入现有规划，正文放不下时转附件，正文保留代码生成的“完整结果见附件”说明。
- 单行超过文件上限、说明本身放不下时：交付失败并给代码回执，不截断事实、不声称已交付。
- 模型文字写“已全部发送”不改变可信交付状态；交付状态只由分项回执决定，用户可见的完成/未知说明由代码生成。
- 区分“程序生成了正确的失败说明”和“接收方实际收到”：渠道不可用时只保证状态如实记录，不承诺通知送达。
- Web 当前单次响应全部渲染、无附件；其实际容量上限与降级方式在 S3 核实 **[待验证]**。
- 现有报告拆分只适用于代码模板，**不是**未来自由 HTML 的通用拆分方案。

反例（S3 测试）：一个附件成功、另一个 unknown；单行超限；说明本身放不下；模型文字声称“已全部发送”。

### 6.10 SDK 落点

- 继续每轮一个 `AgentOutputSchema` 子类作为 `output_type`（PR #111），`invalid_final_output` 一次无工具改写保留。删掉旧规则后它仍负责：当前上下文中的合法引用、块字段组合、必要资源上限、可修正格式错误的一次改写。
- 权限不可用、`unfinished` 等系统错误不进入改写；程序补全不能重新变成“模型必须引用全部结果”。
- 不新增 Agent Loop；`max_turns` 收尾与审批恢复沿用同一 schema。
- 提示词（S3 最低限度）：重写 `DEFAULT_INSTRUCTIONS` 的回答部分（两种块的用途、文字不获得系统身份、动作状态以系统组件为准、澄清时 `awaiting_user`）；`_citation_rule` 改为“查询结果系统会完整交付，正文选重点”；`runtime.py:577` 的模型检查提示词与 `_check_result`（`runtime.py:643`）同步。

**S2 需分清四层，前一层成立不证明后一层：** SDK 能生成 schema → 本地 `VertexModel` 原样转发 `responseJsonSchema`（[事实] `vertex_model.py:127-128`）→ 真实 provider 接受 schema → 真实模型遵守约束。重点核对 `const`、可空、`$ref`/`$defs`、`maxLength`/`maxItems`。本地模拟成功不证明真实 provider 可用。

### 6.11 新旧兼容

**两个独立维度：** 答案版本（旧 `AgentAnswer` / 新块结构）与交付版本（PR #107 的 `delivery_version` v0/v1）。[事实] 旧 `AgentAnswer` 已可使用交付 v1。

| 情形 | 做法 |
| --- | --- |
| 未绑定交付内容 | 按答案版本解析并投影，复核当前权限 |
| 已绑定分项 | 复核当前权限后保留原字节、分项身份、UUID 与回执；已发送分项不重发；`unknown` 不当作普通失败自动重试 |
| v0 `sent` | 不追认为“完整结果已交付”；现有审批前提中 v0 `sent` 视为材料已送达（`channel_store.py:1916`）的规则不变 |
| 最早期只存 `AgentAnswer`、无 `context_evidence` | 继续拒绝交付（`channel.py:454`） |
| 未知或损坏的答案版本 | 按不可用处理，不回退旧版本 |

需要兼容的读取路径（“不迁移历史数据”不等于不需要兼容解析）：
- `channel_store._saved_answer`（`:2151`）与 `channel_store._record`（`:2001`，另行解析 `TurnAnswer.run_turn_id`）；
- Session 最终项校验（`session.py:480-495`）：新轮次只接受新格式；回放历史中的旧助手消息与工具证据照常作为模型历史；
- `channel._validated`（`channel.py:449`）重建 `TurnAnswer`、刷新动作状态、移除失效审批命令；
- 历史读取、重发、报告原文件（原字节，`channel_store.py:1220`）；
- 审批暂停/恢复（下）。

**审批暂停的 RunState。** [事实] `app._native_binding`（`app.py:894`）由应用绑定、openai-agents 与 mcp 版本、本轮工具的证据指纹组成，不含答案契约版本；恢复时不一致抛 `action_not_approvable`（`app.py:1114`），但不作废候选，候选保持 `pending` 直到过期，回执也不具体。`migrations/010_sdk_approval.sql` 只是对当时存量数据的一次性作废，不会因答案格式变化重新执行。`reject_native`（`channel_store.py:1822`）当前只接受三种原因，不含 `action_upgrade_invalidated`（DB 约束已允许该码）。

策略（S2 验证后二选一）：
1. **兼容**：SDK 恢复时由新代码重建 Agent，最终输出按新 schema 生成；若实验证明旧暂停 RunState（历史项为旧格式）能用新 Agent 恢复并产出合法新回答，则不改绑定，直接恢复。
2. **不兼容**：在 `_native_binding` 加入答案契约版本（只影响待审批候选，不动 Session 绑定 `self._binding`，不废弃旧会话）；不一致时在任何写 I/O 之前调用 `reject_native(action, "action_upgrade_invalidated")`（放宽其原因白名单，无需迁移），用户收到“已因升级作废、未执行，请重新提出”。

两种做法下，已执行、执行中或结果未知的动作都在绑定检查之前被 `state != "pending"` 拦下（`app.py:1080`），保留原状态，不重放。[待验证] 真实兼容性在 S2 实验前不当作已有能力。
