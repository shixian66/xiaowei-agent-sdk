# 自由表达的回答结构：模型组织表达，代码保证可信事实

> 状态：**设计提案，待用户确认**。基线 `c00ede6`（PR #111 合入后的 main）。本文不改代码；确认后再写入 ARCHITECTURE §8 并按第 7 节切片实施。

## 1. 背景

小维现在的最终回答 `AgentAnswer`（`src/xiaowei/models.py:260`）是固定格子：`evidence_ids`、`inferences`、`clarification`、`advice`，三者互斥（`answer_kinds_mixed`），每条分析必须关联本回答引用的证据，交付时套固定标题（`evidence.py:130-135`）。它用“限制回答形状”间接保护事实，带来两类问题：

- **表达不自然。** 问候只能走“澄清”，显示为“需要澄清（本轮未执行业务查询）”；有证据时的追问只能写进“分析”并挂“依据”；配置事实、能力说明、通用知识没有位置；结论、数据、原因、建议不能按自然顺序组织。
- **失败来自形状而非事实。** 2026-10-16/17 生产日志中的 `answer_rejected`：`mixed_kinds` ×2、`inference_unlinked` ×1、`uncited_query` ×1，工具与数据源均正常。PR #110/#111 已让这类错误在 Runner 内改写一次，但规则本身仍在。

同时，形状限制并没有保证模型文字中的事实：`extra="forbid"` 只禁止多余字段，挡不住模型在文字里写错数字。

## 2. 产品原则

> **模型自主决定回答结构、语气和内容组织；程序负责生成和验证系统可信事实。模型自由文本属于解释或推断，不得冒充系统核实的事实。**

“系统可信事实”指：查询结果的数值、行与行数，实际执行的 SQL，告警/静默等监控事实及其采集时间，动作的提出、批准、执行状态，以及截断、分页、未核实来源等完整性说明。它们只由代码从获准 Evidence 或 Action 记录生成。

程序**不**保证模型推理正确，也不逐句核实模型文字；这部分以证据展示、明确标识和真实模型评测衡量。

## 3. 目标与验收

| 结果 | 验收项 | 证明方式 |
| --- | --- | --- |
| **一、说话更自然** | 问候、能力、配置问题正常回答，不出现错位标题 | 离线断言渲染结果；真实模型样例人工评审 |
| | 同一回答可含结论、事实、分析、建议、追问，顺序由模型决定 | 离线：多种顺序均可交付；评测：统计自然结构比例 |
| | `mixed_kinds`、`inference_unlinked` 规则移除 | 离线：拒绝码不再产生；生产日志为 0 |
| | 新旧版本同批样例自然度对比 | 真实模型评测人工打分 |
| **二、查询成功后可靠交付完整结果** | 本轮有效查询结果均可完整查看：正文未放入的由程序补为“其余结果”，容量不足转附件 | 离线：模型只放部分事实，其余仍完整交付 |
| | 不能全部展示时由代码如实说明（截断、分页未完、平台容量） | 离线三类各一 |
| | 查询成功不再因“引用不全”失败（`uncited_query` 不再作为回答拒绝） | 离线：生产两种形态直接交付；生产日志为 0 |
| | 查询成功轮次的最终交付率 | 生产日志，对比部署 #111 后的基线 |
| **三、关键事实仍由代码生成与验证** | 事实只出现在代码渲染的事实块，带系统标识；模型文字不得获得该标识 | 离线：文字中仿写标签、表格不被渲染为系统事实 |
| | 动作状态由 Action 记录生成并由程序置顶；模型文字不改变状态 | 离线：已提出/已批准/已执行/结果未知四态 |
| | 原有安全测试原样保留并通过（不可见证据、撤权、跨会话/跨群、夹带字段） | 现有用例不删不放宽 |
| | 旧回答的历史读取、重发、续聊、审批恢复语义不变 | 离线：旧格式存量数据四条路径 |
| | 模型文字与证据不一致的比例 | 真实模型评测抽查（代码不能保证，明确记录） |

## 4. 非目标与暂缓

| 暂缓项 | 理由 | 复查条件 |
| --- | --- | --- |
| 数值占位符（文字中引用证据数值） | 行选择、字段重名、格式化、权限与派生计算会演变成新 DSL | 新结构上线后，评测显示“文字中直接写查询数值且出错”比例显著 |
| 模型标记某次结果“已被取代” | 筛选不同不等于取代，易成为隐藏数据的口子 | 用户反馈“其余结果”重复展示造成明显干扰 |
| “提交回答工具”模式（`tool_use_behavior` + `tool_choice=required`） | 需改 Vertex 适配器（`vertex_model.py:60` 不映射 `tool_choice`）、历史结构、审批恢复与收尾；不是自然表达的前提 | 上线后 `answer_repair` 后仍频繁失败，或常需补查证据才能改对 |
| 自然语言事实核查 | 无可靠确定性方法 | 由评测指标驱动 |

## 5. 设计

### 5.1 回答结构（`AgentAnswer` v2）

模型交一组按顺序排列的块，仍通过 SDK `output_type` 提交：

```json
{
  "format": 2,
  "blocks": [
    {"type": "text", "text": "结论：当前 8 条告警，其中 2 条需要优先关注。", "evidence_id": null, "view": null},
    {"type": "fact", "text": null, "evidence_id": "ev_…", "view": "full"},
    {"type": "text", "text": "建议先看磁盘增长趋势……需要我再查这两项吗？", "evidence_id": null, "view": null}
  ],
  "report_format": null
}
```

- **只有两种块。** `text`：模型自由文字（结论、解释、建议、追问、闲聊），Markdown 子集。`fact`：模型只选择证据与展示方式（`full` / `brief`），内容由代码生成。
- **平铺结构，不用联合类型。** 每块同一对象、字段可空，由校验器检查组合；避免 `anyOf` 在 OpenAI 严格模式与 Vertex `responseJsonSchema` 下的兼容风险（切片 S2 实测确认）。
- **有界。** 块数、单块与总文字长度设上限（数值在 S2 按现有 Session/渠道容量确定），超限可改写一次。
- **`extra="forbid"` 保留**，`format` 用于新旧版本区分。

### 5.2 职责分工

| 内容 | 谁决定 | 谁生成 |
| --- | --- | --- |
| 回答顺序、详略、语气，结论、解释、建议、追问 | 模型 | 模型（`text` 块） |
| 正文中展示哪些事实、放在哪里、完整还是简要 | 模型 | 代码（`fact` 块内容） |
| 查询数据、行数、实际 SQL、告警/静默事实、采集时间 | — | 代码，从当前渠道获准投影 |
| **动作状态** | — | 代码，从 Action 记录；**固定置顶**，模型不能移除或改位 |
| 监控未核实来源、截断/分页/容量说明、会话提示 | — | 代码，固定位置 |
| 本轮未放入正文的有效查询结果 | — | 代码，补为“其余结果”（见 5.4） |
| 本轮未查询数据时的说明 | — | 代码生成一条系统说明，替代模型侧的“澄清/建议”标题 |

### 5.3 校验规则

| 规则 | 现状 | v2 |
| --- | --- | --- |
| 引用不可见证据（`unknown_evidence`） | 拒绝 | **保留**，可改写一次 |
| 当前权限不可读（`evidence_unavailable`） | 拒绝 | **保留**，不改写 |
| 夹带字段（`extra="forbid"`） | 拒绝 | **保留** |
| 动作状态 | 独立组件 | **保留并置顶** |
| 三选一互斥（`mixed_kinds`） | 拒绝 | **删除** |
| 每条分析须关联证据（`inference_unlinked`） | 拒绝 | **删除**（文字块不要求关联） |
| 查询结果须全部引用（`uncited_query`） | 拒绝 | **改为程序兜底**：未放入正文的补为“其余结果”；`unfinished` 另立系统失败码，不再混用 |
| 缺证据（`missing_evidence`） | 拒绝 | 删除：无事实块的回答是合法的纯文字回答，由系统说明“本轮未查询数据” |
| 重复引用（`duplicate_evidence`） | 拒绝 | **自动去重** |
| 本轮新事实选 `brief` | 拒绝 | **自动改为完整展示** |
| 显示方式无效 | 拒绝 | 由块结构消除 |
| 非飞书渠道要求文件 | 拒绝（误记 `mixed_kinds`） | 不静默丢弃：正文照常交付并附系统说明“当前渠道不支持文件” |
| 文字块为空白 | 无 | 拒绝，可改写一次 |

规则仍集中在 `evidence.citation_error`（改名为 v2 校验函数），由本轮输出 schema 预检与交付校验共用（PR #111 的结构保留）。

### 5.4 交付与渲染

- `Delivery` 增加有序 `blocks`（文字或事实引用），各渠道按序渲染：Web（`static/app.js`）、飞书卡片（`feishu_render.py`）、纯文本降级（`feishu_delivery.py`）、MD/HTML 报告（`feishu_report.py`）。事实块复用现有 `DeliveryFact` 与渲染组件。
- **系统标识只属于代码内容。** 事实块带“系统根据证据生成 · 结果 N · 来源 · 采集时间”；文字块作为普通正文，不带系统标识，含分析时可有轻量“模型说明”提示。模型在文字中写出同样字样或表格，也只按普通文字渲染。
- **其余结果。** 本轮成功查询中未放入正文的，追加在正文之后的“其余结果”区域，完整展示；容量不足按现有内联阈值（PR #107）转附件，放不下如实说明。现有 `basis`（`evidence.py:874`，只列工具/对象）由此升级为完整结果。
- **用户可见的证据编号**统一映射为“结果 N”，不再露出 `ev_…`（含提案/执行与纯文本降级）。

### 5.5 SDK 落点

- 继续使用每轮一个 `AgentOutputSchema` 子类作为 `output_type`（PR #111），JSON schema 换为 v2；`invalid_final_output` 一次无工具改写保留作兜底。
- 不新增 Agent Loop、不引入工具提交模式；`max_turns` 收尾与审批恢复沿用同一 schema。
- 提示词：重写 `DEFAULT_INSTRUCTIONS` 的回答部分（删除三选一与分析关联要求，写明两种块的用途、文字不得冒充系统事实、动作状态以系统组件为准）；`_citation_rule` 改为说明“查询结果系统会完整交付，正文选重点”。

## 8. 测试与评测

**离线**（真 SDK Runner、脚本模型、真 PostgreSQL）：第 3 节每个验收项至少一例；生产两种失败形态改为直接交付；文字仿写系统标识；四种动作状态；三种不完整说明；旧格式四条路径；现有安全测试全量保留。

**真实模型评测样例**（需批准的 Vertex Profile）：问候与能力介绍；“我只有这 3 套集群吗”；“这 3 套集群的详情”；“Alertmanager 正在告警有哪些”及按 severity 再筛；“对比 fat 和 pre 的库”；Prometheus 即时值加 5 分钟趋势；创建静默提案并审批。指标：自然度评分、结构多样性、事实块覆盖、文字与证据不一致率、动作状态表述、交付率、步数、耗时与用量；与 `c00ede6` 对比。

**生产**：`answer_reject` 分布、查询成功交付率、“其余结果”出现频率与附件比例。

## 9. 风险与待定

| 项 | 说明 | 建议 |
| --- | --- | --- |
| 模型在结论中只挑有利结果 | 数据完整交付，但结论可能偏 | 纳入评测“结论与全部结果一致” |
| 文字块 Markdown 渲染 | Web/飞书需安全子集（不允许 HTML、链接需限制） | S3 定义白名单子集 |
| 其余结果过长 | 多次监控读取时正文后附大量明细 | 先完整交付并依赖附件阈值；看生产数据再定折叠方式 |
| 纯文字回答中的上下文证据复核 | 现规则：上下文任一证据不可读则整条回答拒绝 | 保持（模型可能复述可见证据） |
| 历史中的 v1 输出影响模型 | 回放旧格式可能诱导模型 | 严格 schema 约束 + 离线回放测试 |

**需要用户确认：** ① 第 2 节原则与第 3 节验收；② 第 4 节暂缓项及复查条件；③ “其余结果”默认完整展示（容量不足转附件）；④ 删除 `missing_evidence`，无事实块时由系统说明“本轮未查询数据”；⑤ 切片顺序。
