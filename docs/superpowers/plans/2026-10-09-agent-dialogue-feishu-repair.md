# Agent 对话与飞书结果展示修复实施计划

> **执行方式：** 获准实施后使用 `superpowers:executing-plans`，按切片串行执行；每片先本地验证、交独立复审，复审通过后再按用户授权开 PR、合入。当前授权仅为编写计划。

**Goal：** 让小维按用户问题自主补充证据、尽量返回完整原始结果，并在飞书中清楚展示结果、限制和模型分析。

**Architecture：** 保留唯一 SDK Agent/Runner 和现有治理、Evidence、Session、投递状态机。先修提示词、工具说明与固定回执；随后从获准的飞书投影生成消息卡片，通过锁定 SDK 的公开发送接口交付。

**Tech Stack：** Python 3.11、OpenAI Agents SDK 0.22.3、lark-channel-sdk 1.4.0、Pydantic、SQLAlchemySession/PostgreSQL、现有 StarRocks Adapter 与 pytest。执行时以锁文件为准，不新增框架。

**Spec：** 本轮用户要求与本文 §2；架构边界见 [ARCHITECTURE](../../../ARCHITECTURE.md)，监控依赖见 [监控实施计划](2026-10-09-monitoring-mcp.md)。需求与实施步骤集中在本文，不再另建重复需求表或设计文档。

### 本轮提出的契约变化

1. 提示词中的工具顺序改为按需取证；时间只在业务需要时澄清；完整原文请求不主动截短。这不授予新工具或执行权限。
2. 有成功证据但需要补充条件时，在现有证据回答的分析里提问；三种最终类型仍互斥。
3. 飞书结果从纯文本改为卡片；事实、采集时间、固定说明及不完整提示默认可见，分析在事实之后单列为模型推断。技术详情可折叠。
4. 飞书超容量时，优先保留证据归属、时间、必要说明和结果，再安排分析；不能让分析挤掉全部事实。这会改变现有“先保分析”的截断优先级，须在 U2 交付中明确说明并据批准契约更新相应测试。

本文审阅通过前，不实施上述行为或展示契约变化。

## 3. Global Constraints

- SDK 是唯一 Agent Loop，不新增 Planner、前置用途分类 Agent、固定业务流程、调度器或模型文字解析执行器。
- 每次 I/O 前的权限、目标、参数、SQLGuard、预算复核全部保留；显式诊断轮继续隐藏并拒绝真实查询工具。
- 本轮全部成功业务查询证据仍须引用；Evidence 拒收仍失败，**本轮不做拒收后自动改写**。
- 历史读取、首次发送与显式重发均重新验证当前权限、来源、归属和接收渠道；权限撤销仍阻断。
- 四种投影独立；飞书只读 `feishu` 投影，不能借 Web 投影获取更多结果。仅折叠不会减少 payload 大小。
- 原始结果与展示截断分别如实标记；不会因好看而丢列、丢行、改数值、拼 DDL 或声称取全。
- 保留 `max_reply_chars` 的 200–3500 校验及可见/折叠内容总限额，不自动提高配置；单卡放不下时明确展示不完整。
- 一轮结果只发一条消息、一次发送；发送异常、超时、取消结果未知，不自动重发，也不在失败后改发另一消息类型。
- 不增加数据库表或迁移，不改已有投递状态机、不增加已读推测、不自动重跑历史查询。
- 不新增附件导出、公开结果链接、卡片回调/分页按钮、动态更新或流式消息；这些需要另行定义数据与投递边界。
- 本次计划工作不调用真实 Vertex、飞书/Lark、公司 StarRocks 或监控源，不实施、不发布、不部署。实施后的真实评估在获准环境单列。
- 浏览器验证只用 18501 或其他空闲端口，不占用或停止 8501。

## 4. Review Focus

- 元数据多页、空页仍有游标、游标失效、预算不足：不能把部分页当全部，也不能无限翻页。
- 历史回答已提交但发送超时：继续追问不能被解释为用户已经收到了；再展示仍验证当前权限。
- 长文本包含真实换行、字面 `\n`、双向控制符、`<at>`、管道符与反引号：显示编码可转义，不能把数据变成卡片结构或消息指令。
- 宽表、大整数、真正 NULL、字符串 `"NULL"`、空字符串与缺字段：保留值的区别，不能靠 Markdown 反解析结果。
- 卡片超容量、发送被取消、SDK 明确失败、重复飞书事件：只允许一次发送，保持 `sent/failed/unknown` 的真实状态。

### U1 的工作方法提示词要点

保留可组合的工具用途、补证据方法与停止条件，而非只删掉规则：

- 准确对象、列和业务口径已有可信信息时直接完成任务；缺哪项就补哪项，遇到多个合理候选才澄清。
- 查结构/DDL、列库表、查无时间条件的业务值不必先询问时间；涉及“最近、昨天、趋势”等才确认必要口径与时区。
- 原文请求保持完整含义；汇总需求在数据库聚合；用户要摘要时才选择性截取长文本，且说明。
- `next_cursor` 是续页请求；同一查询因结果截断重新执行最多一次的现有策略仅用于该种重查，不覆盖正常分页。所有调用仍计预算，不自动提高预算。
- 取得证据后又需要用户选择候选或补条件，用 evidence + inferences 展示已核实部分并提问；完全没有可引用证据才只发 clarification。
- 工具调用前的可修正拒绝可在剩余预算内调整；执行后失败、结果不明、Evidence 拒收仍按现行边界停止。

- [ ] **Step 2：先写失败回归与预览数据。** 样本覆盖 14 个库、5 条业务记录、4 列表结构、多行 DDL、证据分析、多行未执行 SQL 草稿、无结果、多个不同来源。断言来源/时间/note/截断默认可见，技术详情默认收起，分析单列且默认可见，依据编号可见，事实表只出现一次。
- [ ] **Step 3：补编码与容量边界。** 真正 NULL、字符串 `"NULL"`、空串、缺字段、64 位大整数、嵌套 JSON、管道/反引号、真实换行与字面 `\n` 分开验证；`<at>`/群 mention、伪造标题、控制符不能生成新卡片元素或通知。超容量仍保留来源与不完整标记，数值不能裁半，保留的表格行须完整；原始 DDL 放不全不声称完整。
- [ ] **Step 4：运行目标用例并确认旧代码失败。** 失败来自纯文本/缺结构字段/换行被转义的目标问题；不删除或跳过原用例。原“优先保分析”的预期明确按 §2 展示契约更新，同时新增事实优先与分析截断标记的断言。
- [ ] **Step 5：实现接收渠道结构化投影。** 从 Evidence 校验后、当前 `feishu` 投影构建 facts、analysis、feishu_text；保留 `Delivery.layout` 与 content 一致校验。新增测试使 Web/飞书投影故意不同，确认飞书只含自己获准字段；旧历史重读/重发仍重新校验。
- [ ] **Step 6：实现纯渲染并给用户看预览。** 卡片标题简短，正文顺序按下表。静态结构由代码生成；表格来自结构化行，不从模型文本解析。SQL/DDL 使用平台支持的代码显示或保留换行的纯文本组件；危险字符仅作无损显示转义，不能修改 Evidence 原值。
- [ ] **Step 7：容量与发送接入。** 保留 `max_reply_chars` 总限制；卡片 JSON UTF-8 编码另用固定 `CARD_CONTENT_MAX_BYTES = 24_000` 内部上限，为 SDK 包装留余量。按官方 30 KB 建议，将完整请求的内部预算定为 30_000 字节，用 SDK 协议测试测实际编码，并在 Step 1 核实所用消息 API 的约束。超限在 I/O 前选择一张明确标记不完整、按完整行保留前缀的卡片；若连必要来源/限制都放不下，预先选一条固定“结果未展示：单消息容量不足”说明，不能伪装结果。`sent` 此时仅表示这条说明发送成功，不能证明完整结果已交付。发送开始后无论 failed/unknown 都不改发文本。
- [ ] **Step 8：验证成功、失败、取消与恢复。** 通过真 SDK/本机合成端点验证单聊、指定群回复原消息、明确失败、超时/取消 unknown、重复事件一次发送；撤权在发送前零 I/O；旧投递尝试不能落定新尝试。`feishu/lark` 两域名装配仍遵守原配置，真实域名收发另列未验收。
- [ ] **Step 9：隔离变异与上下游回归。** 把时间或 note 移入折叠区、去掉飞书投影选择、恢复字面换行，各自用例必须失败。核对 Web、Session 回放、CLI 显式重发、MCP/StarRocks 事实和固定回执兼容；只改确实受契约影响的断言，不放宽安全断言。
- [ ] **Step 10：记录版本、独立复审与交付。** 列明展示契约与 `Delivery` 渠道结构的变化，提供 SHA、离线证据、预览、容量限制与真实 Lark 未验收项；复审通过后再按用户授权开 PR/合入。

### 卡片内容安排

| 区域 | 默认显示 | 内容 |
| --- | --- | --- |
| 结果标题 | 是 | 结果/集群；建议或澄清用对应标签，避免问候也展示长免责声明 |
| 事实 | 是 | 获准结果表、标量或 SQL/DDL；来源、目标、采集时间、证据编号 |
| 必要说明 | 是 | 历史快照、列库范围、桶数不能确定、工具/展示截断、还有后续页；相同说明同条回答可去重，但关联范围明确 |
| 分析与建议（模型推断） | 是，在事实之后 | 结论、口径、限制、建议与依据编号，不再画同一张事实表 |
| 技术详情 | 收起 | 执行 SQL/元数据采集模板、游标、行数、耗时；原文 JSON 只有容量允许时提供，不用重复 JSON 挤掉事实 |

用户直接请求的 SQL、DDL、JSON 原文属于结果，不能因它“像技术字段”而默认隐藏。折叠只改变默认视图；所有内容仍计入投影、字符与消息字节上限。

参考：[Lark 应用机器人发送卡片](https://open.larksuite.com/document/ukTMukTMukTM/uAzMxEjLwMTMx4CMzETM)、[官方消息 FAQ 与大小说明](https://open.larksuite.com/document/server-docs/im-v1/faq)。执行 U2 时仍须核对所用组件与当前客户端能力，文档/离线 JSON 不证明真实 Lark 渲染。

## 7. O1：性能测量，另行决定是否实施

O1 不阻塞 U1/U2 或监控 P2。确有延迟症状时，以同一 SHA、同一配置、合成目录规模 17/200/309/1000 个对象，记录新查询、Session 回放、交付验证与飞书发送的耗时、探测 SQL/连接数、复核批次与重复对象数。

测量只记固定阶段名、次数、耗时与有限错误码，不记 SQL/参数/模型文本/结果/主机或凭据。先核对现有 `app._stage` 与 SDK usage，能复用的就复用。只有数据证明需要，才另开权限探测批处理或同边界去重优化计划；不增加跨阶段 TTL 授权缓存，不撤掉交付/历史/重发的权限复核。O1 需要单独获准，不在 U1/U2 顺手实现。

监控 PromQL 有限纠错、分类后的部分失败继续调查与源恢复继续按监控 R1b/P2/G3/A4 计划推进；本计划不重复实现或提前放宽它们。

### 真实模型与入口样例（获得环境授权后执行）

| 用户问题/条件 | 应观察的结果 | 主要切片 |
| --- | --- | --- |
| “desc quota_virtual_account_quasi_rt”，单集群/多集群/同名表分别测试 | 已有可信上下文就定位；歧义才问，不猜库，不要求每次固定搜表 | U1 |
