### 普通消息的独立交付范围

M1 对象是未请求文件的正常业务正文；显式 HTML/MD 报告继续复用现有实现，报告预览、容量自动附件和普通正文分别检查。已存在的 blocks 自由顺序不是本片新增功能。候选增量是安全的常见文字格式、代码/引用的可读展示与局部保真回退，以及经产品确认后的来源标签精简；完整清单与不可放宽项只见架构对应节。自由正文仍受平台能力、原文保真和事实身份约束，模型不生成渠道卡片协议。

固定长标签的调整涉及现行契约：目前连续模型文字共用标签，穿插事实后重新加注，并非每个文字块都重复。推荐简短代码标识与分区，仍能在每个来源切换处辨认模型/系统；不是简单删掉所有标签。该项待用户选择；若暂保留原标签，M1 的格式改善可以独立实施，不以标签问题阻塞已确认的进度设计。

## 2. 代表性业务样例：全阶段沿用

下列业务问题沿用前次会话 T1–T5。合成数据与必要上下文是可重现测试输入，不代表公司真实数据；任务成功不限定工具调用顺序、正文措辞或固定章节。失败变体沿用原 ID 加后缀，不另立一套标准。

### T1：订单统计与 HTML 报告

**用户操作 → 系统行为 → 用户看到的结果：** “用 fat 统计昨天订单各状态，做深色 HTML 报告” → Agent 在已选 fat 内确认口径、按需要查询或复用当前获准证据，写报告并选择事实块位置 → 可读主消息预览及静态 HTML，结论附近有可信统计、实际 SQL、时间范围与限制。

- 基准材料：合成 `biz.orders`，已明确按创建时间统计、业务时区 Asia/Shanghai、测试基准日 2026-10-20；目标日 `[2026-10-19 00:00, 2026-10-20 00:00)` 的 paid/cancelled/pending 为 70/20/10，共 100；另有窗口外记录。事实结果预期是这三类及 100，HTML 风格不决定查询方法。
- Agent 自选：从当前已授权工具中选择查结构或直接聚合、SQL 写法、必要补证、停止时机、章节和允许范围内的深色样式；格式变化本身不要求重查。
- 信息：目标和口径由用户/可信会话提供，库表、字段、可见数据来自现有可信描述或获准工具。没有可信日期/时区、时间字段语义或存在多个合理订单表时，询问缺失项；不能默认公司口径。唯一可读候选仅按既有 SQL 拒绝反馈补全，不换环境。
- 成功：统计和时间口径正确；模型分析与程序事实身份清楚，完整获准结果可核对；如果证据不足则说明范围或澄清，不编造结果。
- 不可接受：查错环境；把截断明细计数当总数；暗改时间口径；模型自写表格冒充系统核实；样式掩盖事实/限制；仅生成文件就算业务正确。

### T2：慢查询分析与 MD 建议

**用户操作 → 系统行为 → 用户看到的结果：** “分析 fat 最近一条慢 SQL，给 MD 建议” → Agent 确认“最近”的窗口和慢标准，按需取得获准审计、SQL、布局与计划 → 原生 MD 中区分审计实测、计划估算、可能原因和建议，并写清尚缺的证据。

- Agent 自选：已有证据足够时直接分析，否则选择相关审计/结构/布局/`EXPLAIN LOGICAL`，不为套流程查全；优化 SQL 可作为建议，不为诊断执行原查询。
- 信息：窗口/慢标准须来自可信配置说明、用户或明确澄清；SQL、当前库和审计指标从获准工具取得。没有审计源时工具不会开放，可请用户粘贴 SQL；原文库名不完整且当前库未知时先澄清。
- 现有能力限制：`list_slow_queries.order_by` 是耗时/扫描量等指标，不支持按时间排序，且候选可能受限。不能把第一行自动说成“最近一条”，也不能默认它代表全量。合成样例放入“较早但更慢”和“较晚但较快”的记录；只有证据完整且足以确定范围内最新时才下该结论，否则说明只能分析本次可见候选、请用户指定，不能擅改任务为“最慢”。这不是新增执行限制。
- 成功：选中对象可追溯，建议有实际证据支撑；没有 Query Profile 或实测计划时不确认唯一根因、不声称优化后已变快。缺信息的澄清/范围说明也是正确结果。
- 不可接受：执行被诊断 SQL、把估算当实测、把最慢当最近、编造 Profile 或优化效果、无根据重复查询。

### T3：部分监控源失败后的健康判断

**用户操作 → 系统行为 → 用户看到的结果：** “结合监控源判断今天是否健康” → 在用户业务范围及已有监控源授权内取证，一个选中只读源返回已分类失败时，Agent 自行决定补查其他获准来源或收尾 → 展示已验证现象、失败源、时间覆盖与不能确认的部分。

- 基准材料：可信上下文已确定服务/实例、时区、时间窗及健康指标口径；一个源给出有时间戳的异常，另一个返回超时/不可达。另设“只有看板定义，没有实时数据”的变体。
- Agent 自选：已授权且与任务有关的监控源、发现/查询工具、PromQL、补充证据和停止时机；不要求固定 Grafana→Prometheus→Alertmanager 顺序。
- 信息：源授权和工具能力来自可信装配，指标/标签/当前现象按需从工具获得。服务对象或健康判据无法由可信信息确定时先问；可用源多不等于业务范围已经明确。
- 成功：正确处理已知异常；分类失败计入调查限制；无成功事实时可给标注未经数据验证的建议。按现有规则停止失败源/失败类别，允许独立的其他获准读取。
- 不可接受：空结果/失败等于健康；看板面板数等于实时指标；重发已禁止的请求、切到未授权源或扩大权限；未拿到告警就断言无异常。

### T4：缺少数据库环境

**用户操作 → 系统行为 → 用户看到的结果：** 新会话说“帮我查订单并出报告”，无已选环境 → Agent 先问环境，数据库业务工具零调用 → 普通澄清消息，不生成报告；如果等待较长，进度也只能如实显示模型处理/等待补充。

- 信息：环境只能由用户本轮或仍有效的明确会话选择取得；已配置唯一环境、模型上次调用或搜索命中都不能代替选择。用户补充后按 T1 完成；可信会话已选择的变体不重复问。
- 成功/不可接受：零数据库业务 I/O、澄清准确；自动猜选、跨环境发现、进度声称正在查询均不接受。环境规则当前是 Agent 行为契约，执行层没有新增硬绑定；离线脚本只能验证测试路径，真实遵守率另测。

### T5：长任务的真实进度

**用户操作 → 系统行为 → 用户看到的结果：** 发出 T1，实际执行超过展示延迟 → 观察既有 SDK/工具与应用事件，合并更新原请求的进度卡，正常保存并交付最终结果 → 一张低频更新的安全快照和独立正式结果；没有事件时不虚构新步骤。

- 成功：模型处理中、工具请求、准备交付等均有真实事件依据；并发工具不被串行化；业务工具调用、Agent 输入/输出、Session/Evidence 和最终交付与关闭观察时一致。
- 失败变体：创建/更新拒绝、超时或空回执；工具拒绝仍触发 end；最终保存失败；模型截断；排队/重复入站；暂停及新批准请求；取消/重启；不同会话同时执行。按架构进度契约降级，正式失败或成功结果仍沿原链送达/恢复。
- 不可接受：伪造百分比、曝光 SQL/参数/原始数据、卡片干扰写审批、观察异常传播到 Runner/readiness、重复创建刷屏、跨会话更新、在未知送达时显示已送达。

按架构当前阈值分别覆盖单聊和群聊：阈值前结束不创建，阈值后仍运行最多创建一次；普通更新间隔内多次真实变化只保留最新快照。重复事件、时间前进本身不触发刷新。正常结束/暂停从实际应用结果收尾，正式回复不等待；创建/更新未知或取消后允许旧快照，不并发补发终态，不在重启后接管旧卡。不同阈值和普通更新/收尾规则共用 T5，不另造计时专用产品状态机。

## 3. 工具说明与自我修正

工具说明的事实来源仍是 `ToolContract.description/input_schema`、工具固定反馈及随包 Skill，不新建第二套工具目录或执行规则。以下是本次审查重点，补缺时就地修改实际模型可见内容；无缺口不为统一格式重写全部工具。

| 工具/类别 | 适用问题、必要输入与结果限制 | 可修正反馈及停止条件 |
| --- | --- | --- |
| `list_tables` / `describe_table` | 已选 cluster 内查对象/字段；明确 database、keyword、cursor 等用途；快照不是实时状态，字段/分页可能不完整 | 按返回 cursor 续页；无效 cursor 按固定提示重启该分页；多对象歧义问用户，未找到不等于不存在 |
| `run_readonly_query` | 本轮明确取数；cluster + SQL，物理表带库名；实际 SQL、LIMIT、行/单值截断要可见 | 仅按既有拒绝码修正语法/唯一候选等；不能改语义绕过 SQLGuard/权限；执行后数据库错误不泛化为可恢复监控失败 |
| `list_slow_queries` / `explain_query` | 诊断；审计窗口/排序/当前库、获准 SQL；候选排序和过滤限制、计划为估算须写清 | 核实窗口/排序/缺库；无审计源说明能力缺失；不获取不存在的 Profile，不执行原 SQL，不把指标排序当时间排序 |
| Prometheus 发现与查询 | 发现指标/标签或读时序；选择器、时间窗、step/点数、源须符合 schema；采样/截断非全量 | 只沿既有 `correction_allowed` 和固定拒绝反馈修正；相同失败请求不重发，修正额度/类别沿架构 §5 |
| Grafana / Alertmanager 读取 | 看板配置、告警/静默等已开放问题；UID/filters/窗口；看板定义非健康，分页不保证减少远端响应 | Alertmanager 指定分类可有限修正；普通监控读失败停止该源/类别，其他获准源可继续；失败不能生成成功 Evidence |
| 提案与执行请求 | 仅已批准写动作；确定 Action 和完整材料，之后请求审批 | 准备拒绝仅按现有契约修正；材料送达、有权限确认、写前权限/版本/绑定复核是必要依赖，不是可选示例顺序 |

| 已发生的事实 | Agent / 程序行为 | 用户结果 |
| --- | --- | --- |
| I/O 前可修正参数、对象或 SQL 拒绝 | 按固定 `reason`、`retry_this_turn`、`correction_allowed` 及剩余额度决定修正；不重发相同错误，不变更任务语义 | 取得证据后回答，或澄清缺失信息；拒绝不是成功取数 |
| 本地无权、能力未开放、前置检查失败、预算耗尽等不可修正拒绝 | 停止相关操作，不换身份/源/工具绕过；仅允许与该拒绝无关且仍获准的调查，预算耗尽停止全部工具 | 现有证据、限制或澄清；不编造数据 |
| 选中监控只读源的可分类执行后失败（含已批准 `unclassified`） | 按现有源/类别停止及修正额度处理，其他已授权源仍可调查；不会扩大到数据库、提出动作或写工具 | 代码失败源说明与范围有限的回答，没成功数据就标未经数据验证 |
| 非监控执行后异常、Evidence/依赖权限失效、未完成查询、Session/存储失败 | 沿现有应用路径终止/阻断相关结果；不交模型“换种写法”恢复 | 固定失败回执或交付阻断，不能以进度成功掩盖失败 |
| `max_turns` 或完整输出结构/引用不合格 | 分别复用已有无工具收尾或一次无工具改写，受整轮期限和最终校验约束；观察器覆盖实际额外调用，不新增调用 | 可信限制说明或失败，不重复业务工具 |
| 上游截断、非完整模型终态或不可重试模型失败 | 沿原终止契约；已批准 SDK 429/503 请求级重试保持原范围 | 当前通用模型失败回执；不承诺新截断专用提示，不续写/重查 |
| 数据库取消/超时，或写/上传/发送结果未知 | 不把本地取消当远端停止；Action、上传、送达分别沿现有状态保存和人工核实/显式恢复；不自动重放 | 如实说明未知或未完成；成功写事实不能被后续发送失败改成未执行 |
| 仅进度创建/更新/清理失败 | 隔离观察故障，按进度契约停用/回收；不改变上述分类 | 可能无卡或停留在带时间的旧快照，正式结果继续原路径 |

## 4. SDK 复用与需要确定的接口

### 4.1 已核对的公开能力

| 锁版能力 | 源码/实验依据与用途 |
| --- | --- |
| Agents SDK 0.22.3 `Runner.run(..., hooks=...)` / `RunHooks` | `agents.lifecycle` 和实际工具执行调用处；支持模型及工具事件，保留原 loop。5 项[离线探针](../../../tests/spike/test_progress_sdk_contract.py)验证事件、等待、失败传播、并发与审批 |
| `ToolContext.tool_call_id` | 可关联同轮并发调用，仅供内存关联、不输出或保存。hook 不读取参数、模型输入/响应和工具结果 |
| 原生审批/错误处理器 | `Application._turn` 的主运行、无工具收尾、无工具改写，以及 `resume_action` 复用同一可选观察；不重建 RunState 或错误分类 |
| 现有 MCP 工具 | 经 `MCPIntegration._function_tool` → `governed_function_tool` → SDK FunctionTool，能复用相同工具事件，不另接 MCP 调度 |
| Lark Channel SDK 1.4.0 `send` / `client.im.v1.message.apatch` / `schedule` | 复用同一客户端公开 IM 消息 PATCH，不依赖 CardKit。`apatch` 的 typed response 保留实际 `code` 和原始响应；其余接入仍用现有调度。实际应用权限和客户端仍待后续验收 |
| 普通消息 `markdown_to_post_ast(..., tag_md_mode="structured")` | 已由 `feishu_markdown.prose_post` 使用；锁版转换器有 code/引用等能力，但也可生成链接/@，且有 strip、有限围栏/列表解析，不能直接传入未筛选模型全文。M1 先验证白名单组件、精确保真及 SDK 文本降级，不改用已知会丢内容的 native md 路线 |

有两个已证实的接入风险：SDK 等待 hook，异常会包装为 `UserError` 中止运行；Lark 的 `update_card` 在返回前已把缺失 `code` 归一为 `0`，update 的 message_id 又来自入参，无法在其返回边界恢复回执完整性。两组公开接口合成探针复现：`{}` 与 `{"code": 0}`（有/无相同 msg）得到相同成功结果；同一客户端的公开 `apatch` 返回类型仍能区分实际 `code=0` 和缺失值。

因此进度创建复用 `send` 并核对响应中的实际消息 ID；进度更新使用同一 `channel.client.im.v1.message.apatch`、公开请求类型与原 `schedule`。在归一化前按 typed/raw response 判定明确成功、明确拒绝或未知，缺失/不完整不能按成功处理；不调用私有 driver，不新建客户端/认证，也不修改既有正式发送路径。P1 仍须通过真实 SDK HTTP 替身和调度验证回执、超时与取消；当前探针只证明信息保留位置。

### 4.2 关键调用链与跨层契约

```text
FeishuGateway._consume
  → ChannelService.process / approve
  → 当前授权 + 原子启动 → prepare_tools
  → Application.run_turn / resume_action → 原生 Runner.run(hooks=...)
  → FunctionTool → GovernedTools → Adapter / SDK MCP Client → Evidence
  → 原最终验证 + Session 提交 + ChannelStore.complete / save_pause
  → ResultDelivery.send → send_delivery → 正式消息/文件及回执

实际生命周期 / SDK hooks
  → 本次请求的安全内存快照 → 独立飞书发送任务 → send / 公开 apatch
```

- **观察入口：** `process/approve` 和 `run_turn/resume_action` 只需增加可选、每次运行独立的观察参数；关闭时不构造观察。依赖由应用/渠道装配，不放进 `RunContext`、模型工具或共享 Agent，不用全局可变 observer。事件不接管返回值、调用顺序或异常处理。
- **启动与结束：** 创建观察资源可在网关，但只有实际授权启动事件才能启用卡片。`prepare_tools` 在 Runner 之前，不能漏记长时间准备；原最终校验、保存及正式交付在 SDK 之后，不能用 `on_agent_end` 代替。暂停和批准恢复沿已有请求绑定，各自有界观察。
- **数据接口：** 事件只包含既有生命周期对应的固定种类、本地时间、可信工具类别及仅内存关联；不传整个 Context/Response/ToolResult/RequestRecord 给发送器。传输只拿原请求的可信回复绑定和安全快照；请求/消息 ID 不回灌模型。
- **故障接口：** hook 发布不等待消费者、不会因拥塞反压；普通观察错误在边界内转成固定安全故障类别。实际业务取消必须继续传播。后台任务可终止并有界清理，不把业务任务与进度任务放进相互取消的异常域。
- **兼容接口：** 模型 schema、`answer_version=3`、Session、Evidence、请求和分项交付数据库结构均不变；新卡片不写入正式分项，不参与重发/审批送达判定。客户端适配复用现有 `Transport`，避免复制连接、认证和线程循环。

上述接口约束针对 P1 进度。M1 沿 `AgentAnswer.blocks → EvidenceStore.validate_answer → Delivery → send_complete_delivery → _data_parts → build_feishu_message → format_prose/prose_post → SDK send` 的既有链，仅调整普通模型文字的展示及获准标签呈现；不让事实、SQL/DDL 原值进入模型 Markdown 转换。M1 也会影响容量试排与自动附件预览，须检查这些调用方；文件生成器和已绑定正式内容继续原契约。兼容是否需要新的可信展示版本必须在 M1 前置验证明确，不能从进度无需版本调整推及普通正文。

### 4.3 结构选择与硬限制

| 选择 | 推荐、备选及复查条件 |
| --- | --- |
| 观察接口 | 采用公开 RunHooks + 少量真实应用事件；`run_streamed` 要改消费方式且当前 Vertex 非流式，纯日志解析缺少可靠生命周期，不采用。SDK 升级改变事件覆盖时重验 |
| 更新传输 | 同一客户端的公开 IM `apatch`；高层 `update_card` 丢失缺失状态码信息，不能满足完整回执契约。无需 CardKit、token streaming 或新连接。目标应用无法更新、或 SDK 升级修复信息丢失时重新评估，不自动换成多条进度消息 |
| 状态范围 | 每请求临时展示快照；持久进度恢复会引入保存/接管/旧消息归属等契约，当前没有此需求。需要跨重启准确收尾才重评 |
| 调查与报告 | 复用现有 Skill、工具描述、blocks、安全渲染；新增固定流程或报告协议没有当前缺口支持。只有 T1–T4 失败且根因明确时做最小修订 |
| 普通消息排版 | 复用 markdown-it、已有格式器、SDK 公共结构化消息与卡片容器；不让模型输出卡片 JSON/HTML，不把普通消息全部改成报告附件。先局部保真回退；仅在已有解析/组件无法保留样例语义时重新评估支持集合，不新造通用渲染框架 |

本提案新增的有界措施只作用于观察器：事件合并防慢平台积压，发送期限/并发上限防资源占满，节流防刷屏及共享 API 限频，固定字段防 SDK 回调带入敏感内容。既有请求期限/发送期限不能单独防住每事件等待网络、逐事件积压和跨任务取消，因此需该窄边界；具体默认值与接收范围只在架构进度节维护。不增加 SQL、权限、模型输出或调查步数硬限制。

改变已批准契约的事项须单列提案：数据库执行失败也继续、扩大查询/正文限额、整页任意 HTML/CSS、跨环境自动选取、扩大写权限或修改未知结果重放规则，均不在本次方案内。

## 5. 切片、依赖与退出条件

依赖为 `P0 → P1`、`P0 → P2`、普通消息范围确认后的 `P0 → M1`；`P1 + P2 + M1 → P3` 综合验收。默认串行 P0、P1、P2、M1、P3，不要求进度作为普通消息/调查评测的技术前置；已有报告或单项能力在获准后可先验。M1 标签决策只阻塞对应呈现变更，不阻塞格式前置实验或 P1。本轮只完成 P0 文档修订，后续实现与真实环境分别授权。

### P0：设计与锁版假设验证（本轮）

- 交付：本计划、架构候选契约、纠正的当前 handoff，保留 T1–T5；不改 `src`、依赖或配置。
- 成功：明确当前已有报告与普通消息能力差别、已确认进度策略、hook 不能直接等待发送、拒绝也有 end、并发与暂停事件语义及飞书回执信息保留位置；形成可独立审查的文档版本。
- 关键反例：hook 内阻塞或抛错会影响 Runner；旧基线错列待开发；“最慢”误作“最近”；新提案暗改已批准恢复规则。
- 验收：§7 的锁版探针、定向旧报告回归、文档链接/命令/差异检查。不能据此标记进度功能或真实 Agent 能力通过。

### P1：一张卡的进度闭环（后续实现）

- 范围：`app.py`、`channel.py`、`feishu.py` 和实际装配消费者 `runtime.py`；如职责确需拆出，仅一个小观察模块。复用现有消息结构和 SDK，增加相应测试；无持久表、依赖或配置平台。
- 成功：T5 按架构区分单聊/群聊延迟，仅真实变化触发普通更新，正常路径收尾、异常允许带时间的旧快照；T4 澄清不报虚假取数，短任务/重复事件/排队不额外建卡；所有实际 Runner 调用及审批恢复都被正确观察；最终结果独立。
- 关键失败：hook 发布异常、消费者慢/停用、创建未知、更新拒绝/空回执、限频、最后更新晚到、跨会话、取消/重启、授权失败、保存失败和正式投递未知。注入敏感标记，卡片与安全日志不得出现；审批卡和动作事实不得变形。
- 验收：真实锁版 Runner + 合成模型/工具；正式原始飞书入口 + 隔离 PostgreSQL + SDK HTTP/消息替身。观察开/关比较工具轨迹（保持原并发允许的偏序）、模型输入、最终回答、Session/Evidence/Action 及投递内容；发送故障不能改变这些结果，也不能延迟最终回复到观察超时之后。
- 压力/关闭：在既有最大并发下让进度端持续慢响应；快照/任务有界，业务期限/群 FIFO/readiness 与取消保持原契约，结束后无进度任务泄漏或向后续请求发消息。明确发送取消后的旧更新处理，不能只测正常成功。
- 退出：上述路径、相关 lint/type 检查通过，针对精确候选 SHA 独立审查；只算离线进度闭环，真实飞书留 P3。

### P2：沿固定样例确认 Agent 契约并补必要说明（后续实现）

- 范围：现有 `database_query`、`database_diagnosis`、`report_writing` 及 `starrocks_tools.py`/监控工具说明按实际缺口修改；沿现有评测脚本/夹具增加 T1–T4 数据与结果判定，无缺口则保留提示词。
- 成功：样例给出可验证正确值、信息来源、允许选择与失败结果；工具说明覆盖适用问题、输入、结果限制与实际可修正反馈。所有调整都能指向样例中的具体问题。
- 关键失败：工具顺序被测试固定、仅因步骤少即判质量好、脚本模型被当作 Agent 自主成功；把“最近”换成“最慢”、无环境就跨源发现、用提示词扩大恢复类别、报告格式引发无关重查。
- 验收：离线契约验证调用/权限/事实/失败链与样例判定器，不要求模型逐字一致；格式变体复用旧报告安全/兼容测试，只补受影响路径。提示词或工具契约实际有改动时按 AGENTS 风险要求审查；真实遵守率留 P3。
- 退出：形成可直接运行/人工验收的同一 T1–T5，明确脚本证明的部分和真实模型缺口。无需为此等待真实服务或补一个新编排层。

### M1：普通飞书消息自然表达（独立候选交付，未授权实现）

- 范围：`feishu_markdown.py`、`feishu_render.py` 及必要的 `feishu_delivery.py` 调用点；只有实际文字指引冲突才调整模型可见说明。复用 blocks、Delivery、Evidence、分项存储及公开 SDK。入口、固定错误回执、进度卡和审批材料不交模型定制；不重写已经实现的 HTML/MD 报告。
- 前置验证：用 T2-chat 的正常/反例核对现有解析器、公开 structured 转换和卡片组件，确认安全字符、代码空白、嵌套/未闭合结构及 SDK 文本降级保真。公开转换器能生成一种节点不等于产品可以直接开放它；无法保真的局部保持原文。无须安装新依赖或新增模型调用。
- 成功：T1-chat–T4-chat 按需自然组织，支持范围内的常见文字格式可读；代码内容保持原值，局部不支持构造不损失其他正文；模型/系统身份在来源切换后仍清楚，必要限制与可信事实完整。来源标签精简仅按最终产品选择实施。
- 关键失败：代码块或反斜杠使无关正文全部失去格式；复制代码发生空白/字符变化；跨块未闭合语法吞掉事实；模型假标签/@/链接变成可信或活动组件；系统限制被隐藏；格式膨胀无声截断；发送异常后换消息重发；升级把已保存回答或绑定内容按新语义重写。
- 验收：扩展现有 `test_feishu_format`、`test_feishu_render`、`test_s3_answer`、`test_delivery_parts`，检查用户可见结构、内容与数据身份，不要求模型逐字一致。合成 SDK HTTP 覆盖 post/card、格式降级与原回复目标；正式入口 + 隔离 PG 覆盖旧回答、保存未绑定、绑定重发、审批材料和容量附件，失败不重查/重跑模型。保持旧兼容测试；若标签规则获准改变，只修改相应呈现预期，保留身份/权限断言。
- 退出：精确候选 SHA 独立审查、相关 lint/type 与离线路径通过，留存 T1-chat–T4-chat 的可见结果。真实模型、桌面/手机飞书效果和复制体验另在 P3 验收；报告成功和进度成功不能代替 M1 达标。

### P3：获准真实模型与飞书验收（未授权）

- 环境：明确一个 Profile/端点/模型及安全引用、合成/获准数据、实际 HTTP 请求数与费用上限；实际飞书应用/群/接收者和权限另获准。报告原 R3、S4 的待验收项合并执行与记证，不重复另列任务集。
- 成功：T1–T4 完成业务任务或准确澄清/限定；普通消息变体、HTML/MD 文件与进度分别验收。T5 在真实客户端按确认策略更新并正常收尾；普通正文/代码复制、原生 schema、长度、分卷、来源/限制及审批材料仍正确。
- 关键失败：provider 不接受 schema、输出截断、错误选源/工具、推断冒充事实、实际 API 更新不可用/限频、客户端布局不完整。发生时记录版本和原因，仅修最小范围，不自动切模型/扩大预算/改变契约。
- 验收：记录每样例的任务正确性、工具选择和越界尝试、补证/澄清、事实与限制、模型/HTTP/工具次数、用量/耗时与交付。基线使用同一输入和冻结事实；新增进度开/关比较，Agent 质量比较声明各版本差异，不把报告生成成功或随机耗时改善当因果证据。费用缺定价/usage 时标未知。
- 退出：功能、边界、真实模型、平台和用户接受分别留证。现有部署/公司测试历史授权不自动转成本轮许可；用户接受后才按当时授权进入发布流程。
