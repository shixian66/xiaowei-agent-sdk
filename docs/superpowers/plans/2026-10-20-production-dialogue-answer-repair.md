## 2. 根因、方案判断与范围

**主要根因是两个契约缺口叠加。**

1. **取数未围绕结果形状。** 用户需要一个有明确日期、排序、数量的审计查询；工作方法却笼统要求找慢查询用 `list_slow_queries`。工具没有每次调用的行数与绝对日期参数，不能自然表达这个任务。现有 `run_readonly_query` 已允许在授权范围内直接查询审计表，无须新造 SQL 执行入口。
2. **完整交付与默认展开仍有耦合。** 新事实的 brief 目前无效，正文提示又过度禁止必要的数据提炼。历史 brief 允许只交付摘要是现有取舍，不是应一并删除的缺陷；扩展本轮 brief 时须防止误用该省略路径。无需增加第二个模型展示字段，单调折叠阈值也不能减少查询、模型输入和附件大小。

**另有独立的已复现代码缺陷，不能冒充本次 100 行的直接原因。** `audit_references()` 生成一份不会执行、也不会展示的规范化 SQL，并用其长度再次拒绝原本合规的审计原文；同一已接受原文随后再次解析。生产粘贴中的 `omitted_sqlguard=0`，不支持认定这一误滤发生在本次请求。

根治所需的职责是：**Agent 围绕问题取数并组织答案；代码核验数据与来源、完整提供必交内容；渠道按意图展示正文和详情。** 正文中的模型推断不因有引用就自动为真；可信表格仍由代码生成。当前 `AgentAnswer` 的有序 blocks 可以承载这个方案，无须撤掉结构化输出、Evidence 或 SDK Loop。

“让所有事实默认折叠”会把用户真正要看的三行结果也藏起来；“新增任意行列选择器”又会引入新的投影语义。优先精确查询、简洁正文和现有 view，不建设第二套查询或展示策略系统。Prometheus 目前的 `result: str` 不能直接当成结构化标签表；正文可以有依据地提炼，完整原文在详情或文件，结构化监控协议另有实际任务需要时再研究。

### 精确查询失败与候选结果规则

- 精确日期、排序、数量或字段要求不因工具失败而改变。禁止直查失败后悄悄换 `list_slow_queries`，仍称得到“今天全量 Top 3”或同等精确结果；不新增自动工具 fallback。
- 当前 SQLGuard 的前置拒绝以 `ToolRejectedError` 返回模型。明确可纠正的写法问题可在同一权限与预算内作语义等价修正；不能把所有 SQLGuard 拒绝一概设为终止，也不能删掉日期、排序或数量条件来求通过。
- 权限不足、权限无法复核、预算用尽等沿现有停止/说明规则，不换工具绕过。数据库执行中的权限错误、超时、资源错误等通常经 `ToolExecutionError` 终止整轮；保留现有受控失败出口，不把本片扩成失败续轮或重试工程。已确定未发 SQL 的连接槽位繁忙按现有独立契约处理。
- 一开始只有快捷诊断工具可用时，可以在其独立获准范围内给出“受限候选结果”，明确窗口、排序、过滤和截断口径，以及精确请求尚未完成；候选中的前三不能冒充用户要求的全范围前三。这不是失败后绕过权限或资源限制的通道。
- 原文或结果被截断，须显示代码生成的限制，并准确区分“返回了三条记录”和“三条 SQL 原文均完整”；不能因为已拿到三个 Query ID 就声称完整交付。不足三条时如实报告实际条数，不补齐、不暗中扩大窗口。

| 状态追问 | 通过任务视图中的关联审批事实区分废草稿 A 与待批 B。问现状时读取当前记录；只确认前一步时可用“上一步已确认……”。多个有效任务仍无法消歧时才澄清，不默认选择最大 ID 或重建任务 |

默认去掉字段／值表、内部 ID／版本、技术工具名清单、预算／配额／容差秒数／排队细节、重复采集说明和泛化免责声明。能力范围不能删除：从可信 spec.targets/spec.tools 生成覆盖实际授权上界的业务说明，如“目标：fat、fat1、pre；只读：数据库查询与安全巡检”；不能只用任务标题代替能力范围，其他获准能力也须如实呈现。确认命令中的 Action ID 有实际用途，保留。实际到期、失败、unknown、错过不补跑等重要限制必须出现；内部原证据、预算、绑定与权限核验保持完整，不为简洁删除证据或扩展留存。

用户要求长期、实际却受旧数据期限约束时，保留一行原因和办法：“受最早数据期限限制；如需无旧依赖版本，可显式 /新建 后完整重述（会轮换全群共享上下文）。”不自动新建，也不把这项决策信息当作重复免责声明删除。

**状态只说证据支持的程度：** Action 成功激活任务，不等于巡检完成；active 表示已激活，不等于此刻正在运行；通知 accepted／代理 HTTP 2xx 不等于群内实收或已读。历史通知无法绑定到本次执行时，不声称它就是本次结果。当前 get_task 没有逐次 run 状态，缺证据就说明当前执行未核实；本次不新增运行历史查询。

按原对话时点的合格示例：**“经你批准，任务已激活。首次为 10 月 26 日 14:10，之后每小时检查 fat、fat1、pre 上一个完整北京时间小时，按计划分别汇总到指定群。任务有效至 11 月 23 日 22:13；首次巡检尚未开始。”** 若首次说明长期任务的实际期限，同时给出上一段的一行原因。实际回执只保留当次已验证且与问题有关的信息，不固定重复整段。审批主体是有权用户，不能说“我已自动完成审批”；未来计划不表述为确定送达。

### 8.5 真实模型 eval 与完成判据

不预建新的 approval eval 套件、动态命令 DSL 或采集平台。沿已有可用群入口／合成夹具按固定脚本验证，已有日志足够记录工具选择、步数、耗时和用量；不为本轮新增观测字段。

用户已明确：本地继续离线，公司隔离环境承担真实模型验证。公司使用获准模型、操作测试群和只读源，先执行以下两段固定对话，各一次，不要求固定工具顺序：

1. **正常五轮：** 建立周期任务 → 无空格批准实际 Action → 追问是否运行 → 重复批准 → 确认是否好了。批准 ID 来自真实生成的合成记录，不写死原生产 A/B；不为复刻旧故障人为创建 B。应只创建／执行一次，用户看到简洁材料、正确状态与实际期限。
2. **暂停期间追问与旧状态：** 合成准备 A 已因无法恢复而作废，正常创建 B 并停在 SDK 等待审批；在 B 尚未处理、该轮尚未写入 Session 时，新来“创建好，在运行了吗？”。应从任务工具识别 A 已作废、B 待确认，不能批准 A、默认回到 A 或因读取缺口重复澄清。再推进到 B 审批过期后，先批准 B、再追问，正确说明“审批已过期”；不能复活 A/B、不编按钮、不自行重建；补问“为什么有到期时间”，保留原因和无旧依赖办法。此段不能用“成功批准 B 之后再追问”替代。

两段检查实际出现的激活／执行、当前／历史与期限表述；第一段恢复后若携带暂停前事实，应说“此前查询时……”，不能当成最新状态。检查批准人是用户、模型不声称自动审批，未来通知只说“按计划发送”。不要求逐字一致或固定工具顺序；未出现的 accepted／unknown 等状态不计为真实模型已验证，其代码表达沿离线事实回归。异常时只重复失败场景定位；不固定要求基线／候选各三次或将离线故障矩阵再全部跑真实模型。这是固定样例验收，不据两次通过声称长期稳定率或性能提升。
