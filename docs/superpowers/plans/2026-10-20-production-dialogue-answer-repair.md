**目标：** 用户问什么，AI 就围绕什么给出结果；系统保证可信数据可核对、必交内容不丢失，但不强迫用户先阅读全部原始证据。

用户要求 3 条，就让 Agent 生成最多返回 3 条的获准查询；记录充足且限额允许时返回 3 条，不用 100 条候选冒充精确查询。用户只要求两个字段，就优先展示这两个字段。本轮应交付的原始结果完整可核对，不强行铺到默认正文；历史 brief 保持摘要语义，不因追问计数重新导出历史原值。

**用户可见回答的验收约定：** 默认正文直接回答问题，只呈现完成该任务需要的关键事实、结论，以及影响判断的必要限制。用户只要 IP/主机名，就呈现这两项；用户要三条记录，就呈现所需三条；用户要详细分析或原文，再按要求展开。简洁不等于省略用户明确要求的内容。

- 飞书/Web 消息及 MD/HTML 报告正文均不得自动附上一份像日志的“系统事实”清单。工具参数、整段指标、原始 JSON、调查过程计数和重复的来源/采集说明默认放在可选择查看的证据详情或独立明细附件；正文保留轻量依据入口，不能只是把消息中的日志搬进报告正文或末尾。
- “结果很小”“view=full”“属于必交内容”均不能单独成为把原始证据铺到正文的理由。直接回答任务的精简结果表可以在正文展示，支持它的完整证据保持可核对。
- 来源身份用轻量标识与详情保留，不要求用户反复阅读“AI 分析与建议／系统事实”标题。查询未完成、结果截断、范围不全等影响结论的限制仍须在正文简短说明；审批必交材料沿既有约束。
- 若模型已经给出所需关键事实，系统随后又默认展开用户未要求的原始字段，即判本次验收失败，即使引用、附件和全部技术检查均通过。
- 用户截图中的“其余结果／系统事实／结果 N”、原始 `start_time/end_time`、`step`、`warnings: NULL`、“共 6 个字段”等重复块，作为明确的失败样例。真实查询范围、采样或告警若影响结论，应使用简短、可读的业务说明；空警告与内部字段计数默认不展示。原始值继续保留在证据中，不通过删数据实现简洁。

**架构：** 保留单 Agent、SDK Runner、现有受治理查询与 Evidence 交付链。先落实查询的日期、排序、数量和字段，再分开正文、详情与交付状态。复用必填的 `FactBlock.view`：full 呈现可信结果；本轮 brief 收起但完整交付；历史 brief 沿现有摘要契约，原文放不下时明确提示，不自动生成历史明细附件。其余结果收起，普通非表格 metadata 不生成正文清单。不新增 presentation、模型 schema、持久化字段或第二套展示服务。

**已确认的业务时区：** 用户本轮决定默认统一采用 `Asia/Shanghai`，不采用集群 `time_zone` 作为业务默认值；本会话用户明确指定的时区优先。集群会话时区与 `audit.time_zone` 仍分别保持数据库会话及审计写入语义，不为迁就默认业务日期修改配置。

**技术栈：** Python 3.11，锁定的 openai-agents 0.22.3、Pydantic 2.13.5、sqlglot 30.17.0，SQLAlchemySession/PostgreSQL，既有 StarRocks Adapter、飞书/Web 组件与 Markdown/HTML 依赖；优先复用，不预设新增依赖。

## 2. 根因、方案判断与范围

**主要根因是两个契约缺口叠加。**

1. **取数未围绕结果形状。** 用户需要一个有明确日期、排序、数量的审计查询；工作方法却笼统要求找慢查询用 `list_slow_queries`。工具没有每次调用的行数与绝对日期参数，不能自然表达这个任务。现有 `run_readonly_query` 已允许在授权范围内直接查询审计表，无须新造 SQL 执行入口。
2. **完整交付与默认展开仍有耦合。** 新事实的 brief 目前无效，正文提示又过度禁止必要的数据提炼。历史 brief 允许只交付摘要是现有取舍，不是应一并删除的缺陷；扩展本轮 brief 时须防止误用该省略路径。无需增加第二个模型展示字段，单调折叠阈值也不能减少查询、模型输入和附件大小。

**另有独立的已复现代码缺陷，不能冒充本次 100 行的直接原因。** `audit_references()` 生成一份不会执行、也不会展示的规范化 SQL，并用其长度再次拒绝原本合规的审计原文；同一已接受原文随后再次解析。生产粘贴中的 `omitted_sqlguard=0`，不支持认定这一误滤发生在本次请求。

| **终止错误与可自我修正错误的范围不同。** 有些失败后不能像正常调查那样继续解释或补证 | `tools.py:45–85,275` 已将部分前置拒绝交回模型；监控只读有分类恢复，但 `governance.py:739–773` 的普通数据库执行错误会终止轮次，`app.py:1373` 映射固定失败 | 作为能力边界记录，不是本次原始对话根因。后续若有具体无副作用、结果状态已知的数据库错误样本，再最小化扩展分类反馈；权限/证据不可核验、取消和结果未知继续停止，不新增通用重试 |
| **现有通过证据没有覆盖真实任务质量。** 能引用、能发送，不等于答对或只答所问 | `test_autonomy_tasks.py` 明示脚本模型不证明自主质量；handoff 的真实模型和客户端验收仍开放。生产中“默认 100 才能确保前三”的解释没有被类型/Evidence 检查证明 | P4 同时测真实取数、回答含义、默认可见内容、证据可达及多轮复用；不能只看 JSON 合法、引用存在或文件 sent |

根治所需的职责是：**Agent 围绕问题取数并组织答案；代码核验数据与来源、完整提供必交内容；渠道按意图展示正文和详情。** 正文中的模型推断不因有引用就自动为真；可信表格仍由代码生成。当前 `AgentAnswer` 的有序 blocks 可以承载这个方案，无须撤掉结构化输出、Evidence 或 SDK Loop。

“让所有事实默认折叠”会把用户真正要看的三行结果也藏起来；“新增任意行列选择器”又会引入新的投影语义。优先精确查询、简洁正文和现有 view，不建设第二套查询或展示策略系统。Prometheus 目前的 `result: str` 不能直接当成结构化标签表；正文可以有依据地提炼，完整原文在详情或文件，结构化监控协议另有实际任务需要时再研究。

### 简化方案比较与推荐

| 方案 | 能解决的部分 | 仍存在的具体问题与取舍 |
| --- | --- | --- |

### 精确查询失败与候选结果规则

- 精确日期、排序、数量或字段要求不因工具失败而改变。禁止直查失败后悄悄换 `list_slow_queries`，仍称得到“今天全量 Top 3”或同等精确结果；不新增自动工具 fallback。
- 当前 SQLGuard 的前置拒绝以 `ToolRejectedError` 返回模型。明确可纠正的写法问题可在同一权限与预算内作语义等价修正；不能把所有 SQLGuard 拒绝一概设为终止，也不能删掉日期、排序或数量条件来求通过。
- 权限不足、权限无法复核、预算用尽等沿现有停止/说明规则，不换工具绕过。数据库执行中的权限错误、超时、资源错误等通常经 `ToolExecutionError` 终止整轮；保留现有受控失败出口，不把本片扩成失败续轮或重试工程。已确定未发 SQL 的连接槽位繁忙按现有独立契约处理。

- 原文或结果被截断，须显示代码生成的限制，并准确区分“返回了三条记录”和“三条 SQL 原文均完整”；不能因为已拿到三个 Query ID 就声称完整交付。不足三条时如实报告实际条数，不补齐、不暗中扩大窗口。
