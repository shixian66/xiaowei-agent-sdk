## 1. 根因

这次事故中，小维未经选择就查询了 fat、fat1、pre 三个环境。主要原因是现行规则本身允许这样做：

| 位置 | 现状 |
| --- | --- |
| `app.py:122` `DEFAULT_INSTRUCTIONS` 末段 | "没有明确目标时可以先问，也可按任务做获准发现"，以及"恰好一个精确库表的唯一可读匹配时可继续读取" |
| `app.py:122` 同段 | "本轮只有一个合理的获准目标时无需反问或穷举发现" |
| `starrocks_tools.py:337-344` 工具说明后缀 | 结构/查询类工具："或完整发现的唯一可读精确匹配"。**`list_databases`/`list_tables` 另有一支："可按任务发现获准候选"**（v4.1 核对补充；列库正是本次事故的第一步） |
| `tools.py:62` `unknown_target` 拒绝回执 | "核实本轮用户明确目标或完整发现的唯一可读匹配"（Codex 复审发现，模型传入未知环境后实际收到这段文字） |
| `app.py:1316` `_TARGETS_HEADER` | 列出全部获准集群本身没有错，模型需要知道合法的参数值；问题在于其中的规则与上述各处重复、互相冲突 |

用户问"有哪些数据库可以查"，按这些规则就是对全部获准环境做发现，属于合法行为。所以第一步的核心是把规则改对，并把工作方法写清楚。

## 2. 规则变化（ARCHITECTURE §6 R7 同步改写）

- **B1(a) 改为：**
  - 用户没有明确数据库环境时，先澄清选哪个环境，不做跨环境发现，也不按"唯一匹配"继续。
  - 用户选定后，同一会话的后续数据库任务沿用该环境。
  - 只有用户明确要求切换（如"切到 pre""改用 pre 查"）才改变。
  - 只是提到别的环境（如"pre 上也有吗？"）时，先问是否切换，不直接去查。
  - 只有一个配置环境时也先确认，与之前的决定一致。
  - 新建会话后重新询问。
- **B1(b) 群聊：**
  - 群内成员明确选定的环境，作为该群会话的环境沿用。
  - 其他成员要换环境时，同样需要明确切换。
  - 每次调用仍按当前发起人复核权限，执行许可不继承。
- **无法从对话确定当前环境时，重新询问，不凭印象。** 例如群内多人选择互相冲突。正式会话按完整历史回放，不会自动裁剪（`session.py:392`、ARCHITECTURE §会话）；历史超过轮数或字节上限时直接拒绝，并提示新建会话。
- **不访问数据库的 SQL 任务不要求选环境。** 例如用户已给出足够信息时的 SQL 生成、解释，或静态分析。只有需要取数或查结构时才问环境。
- **不变的部分：**
  - 模型每次调用仍必须给出 `cluster`。
  - 未知集群在 I/O 前拒绝。
  - 环境失败、不可用、撤权时不换源。
  - 权限、SQLGuard、预算和 Evidence 全部照旧。
  - 环境选择不授予权限，也不代替本轮执行意图。"只解释、不执行"仍然有效。
- **在 ARCHITECTURE 中记录已接受风险与复查触发条件**（§7）。

## 6. 残余风险与未覆盖

- **没有执行层兜底。** 模型不遵守时，跨环境查询会照常执行。权限仍把查询限制在获准环境内，SQLGuard 与资源限额照旧生效，但都还没有约束到"用户选定的那个环境"。
- **选择只在对话历史中。** 正式会话完整回放、不裁剪历史，但模型仍可能忽略或混淆历史中的选择，群内多人交替发言时尤其如此。Skill 要求无法确定时重新问，但不能保证。
- **"切换"与"提及"由模型区分，** 可能误判。
- **未覆盖：** 实现与离线测试（未开始）、真实模型测试（未获准）、真实 StarRocks 与真实飞书、部署和用户验收。

- 用户把某个具体环境确认为需要强制约束的环境（例如生产或其他非测试环境），或确认把小维开放给新的使用范围。由用户逐项确认，不由开发方推断"是否重要"。
- 生产日志或用户反馈中再次出现跨环境新取数。

"多余反问多、但没有越界"不是启动第二步的条件，按任务能力问题修改 Skill 文字。
