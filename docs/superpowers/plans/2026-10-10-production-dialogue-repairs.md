# 生产对话七项修复实施计划

> 文档版本：v2，2026-10-10。状态：待独立审查、未实施。纠正 v1 只覆盖会话问题的遗漏；七项范围统一在本文件维护，原会话细案并入 §6。当前仅授权设计、计划、文档与有边界离线验证；产品功能、真实服务、推送、PR、合并和部署仍须后续授权。
> 后续实施按 `superpowers:executing-plans` 串行完成可验证切片；每片先观察目标测试失败，再最小修复、验证和提交。计划审查不等于产品已实现。

**目标：** 同名表不擅自选集群；回答清楚、保留获准原文与限制、减少重复；长排障能在明确容量内继续；图片文档与报告附件有明确的可用范围及失败反馈。

**架构：** SDK 仍是唯一 Agent Loop。复用当前模型、工具治理、Evidence/PolicySession、请求与投递路径；展示用当前渠道结构化投影。附件只补对应入口/模型适配/交付所必需的边界，不新建 Planner、意图分类器、通用文件平台或记忆服务。

**权威：** 协作与验收引用 [AGENTS](../../../AGENTS.md)，生效架构引用 [ARCHITECTURE](../../../ARCHITECTURE.md)。本文件是这七项的唯一实施计划；新增契约在 §4 列明为提案，批准后才更新 ARCHITECTURE。监控按[监控实施计划](2026-10-09-monitoring-mcp.md)独立推进。

### 1.1 逐轮还原（沿用已确认样例）

| 对话 | 已取得的证据 | 结论与未证实部分 |

## 2. 七项根因、架构落点与同类场景

| 编号 / 用户问题 | 根因与源码证据 | 落点 / 同类场景 | 最小修复及验收位置 |
| --- | --- | --- | --- |
| 1. Markdown、SQL/DDL 代码块没有样式 | ARCHITECTURE §7 要求所有不可信内容 plain_text；feishu_render 不解析 Markdown。当前是有意边界，不是加粗渲染失效 | 渠道展示；分析、SQL 草稿、原始 DDL、反引号和围栏 | 受限格式解析与原文代码展示，保持原值；R12，涉及 C1 |
| 2. 有些回复卡片、有些还是文本 | feishu_render.build 按 facts 分流，无事实的建议/澄清用文本；符合既有契约，不是发送失败后偷偷回退 | 渠道构造；问候、澄清、草稿、有事实分析、固定回执 | 模型业务回复统一静态卡片；固定操作回执明确保留文本；R12，涉及 C2 |
| 3. 分析重复字段/表格/DDL，简短追问也重发整表 | DEFAULT_INSTRUCTIONS 已禁止复述，真实模型仍违背；Evidence.validate_answer 对每个引用总是生成完整事实 | 模型表达与事实展示两种根因；列库、结构、原文、历史条数追问 | 模型只解释；历史简短追问可用摘要视图，原事实不改；R3，涉及 C3 |
| 4. 会话太短、失效原因不清 | 20 次提交、400000 回放字节、7 天固定期限；PolicySession 多种失败合并，渠道记录无细分原因/提醒 | Session → App → 请求存储 → 双入口；长 DDL、多工具排障、最后提交超限 | 容量测算、有限调参、安全原因与同条提醒；R4 / §6，涉及 C4 |
| 5. 不能接收图片和文档 | feishu.py 在 message_type != text 时丢弃；Vertex._message 与 PolicySession 只接受文本；SDK 下载能力不等于产品支持 | 入站身份/下载/提取 → 模型适配 → 历史；截图、日志文件、说明文档 | 先准确提示不支持；另片贯通有限附件输入；E5，涉及 C5 |
| 6. 巡检结果不能交付 MD/HTML 文件 | AgentAnswer/Delivery 与发送链没有报告附件；ARCHITECTURE §2 暂缓导出/上传 | 事实生成 → 报告构造 → 上传/发送/重发；巡检、故障复盘 | MD 先行、固定模板 HTML 后行；E6，涉及 C6 |
| 7. 多集群同名表自行选 pre | cluster 是模型必填参数，路由没有默认 pre；治理证明允许访问，不证明用户本轮选择。已有“不猜集群”提示不足 | Agent 目标选择；表结构、布局、DDL、查数及源故障追问 | 明确目标来源与歧义规则；真实模型评估，R7；硬目标确认如需要另列 C7 |

七层归因：入口（文本/附件、身份、新建）→ 模型选择（目标、重复、意图）→ SDK/工具契约（显式 cluster）→ 治理（权限/参数/预算）→ Adapter（实际目标、SQL、结果）→ Evidence/Session（引用、回放与保存）→ 展示/发送（plain_text、容器、重复完整事实、容量、投递状态）。只在对应层修根因；不通过放宽 Evidence、改路由默认值或添加第二个模型循环弥补体验。

## 3. Agent 的任务、信息与自主范围

### 3.1 交给 Agent 的选择

在本轮权限、工具集合和预算内，Agent 根据缺少的信息选择工具、写查询、补取证、比较或结束调查。不规定“搜表 → 查列 → 查布局 → 查询”的固定顺序；已有准确限定表名和可见证据时可直接用适合的工具。报告请求也不固定巡检顺序，缺必要证据时自行补充，未覆盖项必须如实记录。

| 必要信息 | 可用来源 | 缺失时如何处理 |
| --- | --- | --- |
| 查询意图与目标集群 | 当前用户明确要求；当前会话里用户已明确且仍适用的目标；只有一个符合任务的获准目标 | 多个合理目标时问用户，不把“看过多个库”“搜索命中”“最近工具用了 pre”当成选择；新建后无继承目标 |
| 库表/字段、同名对象 | 用户限定名、可信业务说明、获准结构工具 | 发现候选可以选适合的搜索；候选不唯一或跨源同名则澄清，不用另一源代替用户目标 |
| 时间、指标口径、单位 | 本轮可信时间、已配置业务时区/口径、用户、工具证据 | 只问影响答案的缺项；查结构不追问时间；解释/草稿不继承查询许可 |
| 原文、分页、结果完整性 | 结构化结果、next_cursor、真实截断标记、采集时间 | 原文不能先 SUBSTRING；分页与值丢失分开；预算不足基于已有证据说明只拿到部分 |
| 图片/文件里的说明 | 经准入的用户附件，仍是不可信输入 | 附件内容不能授予工具权限，不能替其他人发布指令；格式、能力或容量不支持则告知，不猜内容 |
| 报告事实、限制与结论 | 当前渠道获准 Evidence + 单列模型推断 | 无证据不写“已巡检/健康”；部分源失败则注明未核实，不能用模型记忆补事实 |

### 3.2 修正、继续和停止

- 治理在 I/O 前返回已批准的参数/SQL/预算拒绝时，给模型固定且可操作的原因；模型可在预算内改写、澄清或结束。保持现有分类，不把全部异常改成可重试文本。
- 监控已批准的 timeout/auth/unavailable/5xx/表达式错误，按监控契约停用本源本轮或修正表达式，其他获准源可继续；不生成成功 Evidence，不跨源偷换问题。
- 目标不清时暂停该目标的具体表读取/查询。可为用户要求的跨源发现使用获准列库/搜表；发现本身不授权后续具体查询。用户明确要比较多个源时可以分别取证，标明每个目标。
- 会话不可安全回放/提交、不可修正协议错误、Evidence/最终回答拒收，沿原链停止相关轮次；不新增“重复就拒收”、自动重写或异常吞掉后继续。
- 本地构造失败且发送未开始为 failed；发送开始后结果未知为 unknown，不自动补发。操作者 requests resend 只复核并交付已保存的结果，不重新调查或查询。
- 权限、调用预算、Evidence、当前接收授权、未来写审批都是必要依赖。任何显示/附件功能不替用户批准监控写动作；Session 新建/关闭不改变 Action 执行事实。

### 3.3 工具说明要求

沿现有工具名称、参数模型与治理接口修改必要说明，不新增测试专用产品覆盖入口：列库/搜表适合发现；describe_table 是字段、layout 是布局、show_create_table 是获准内部表原始 DDL；run_readonly_query 要有本轮执行意图和明确目标；每项写明目标要求、结果上限、分页/截断和可修正拒绝。示例顺序只作示意。报告导出不是数据库 SQL 能力，不能给 SQLGuard 增加 INTO OUTFILE 等语法。

## 4. 契约取舍与批准状态

以下提案纳入完整计划，**不视为已获产品实施批准**。实施前确定对应项，其他独立切片不必等待。

| 决定 | 当前契约 → 最小提案 | 取舍 / 生效文档 |
| --- | --- | --- |
| C1 受限 Markdown 与代码展示 | 飞书全部 plain_text → 只由代码解析/生成白名单格式，其他内容仍是文字 | 需要验证格式不能生成 @、链接、图片或 HTML；SQL/DDL 必须保真且围栏不能逃逸。ARCHITECTURE §7 |
| C2 回复容器 | 无事实的问候/澄清/草稿文本 → 模型业务回复也用一张静态卡片 | 新建/授权/排队/失败/容量说明等固定回执可保留文本；JSON 2.0 客户端下限和单消息预算不变。ARCHITECTURE §7 |
| C3 简短追问视图 | 引用即默认完整显示 → 历史简短追问可摘要，原表放技术展开区 | 建议由 Agent 选择 full/brief 的闭集显示意图，代码生成数值；只影响视图，不裁剪 Evidence。默认 full、原文/本轮新查询 full；模型误选仍须评估，不能靠关键词分类器保证。ARCHITECTURE §7/§9 |
| C4 会话 | 20 轮 → 容量测算后建议 100；安全状态随请求保存、同条提醒 | 400000 字节、1000000 模型请求、7 天暂保留；若不足另提最小调整；新增应用表字段需迁移。细案仅 §6 |
| C5 附件输入 | 文本入口 → 有限图片与选定文档格式 | 增加向获准模型传送附件的数据范围、临时保存/回放边界；先定格式、容量与 Profile，不能全格式默认启用。ARCHITECTURE §2/§7/§9 |
| C6 报告附件 | 不导出/上传 → 用户请求时交付 MD，随后静态 HTML | 以一个文件消息替代该轮最终卡片，避免默认再发多条。文件可下载且平台留存不能由 Evidence 过期撤回，必须明确接受。ARCHITECTURE §2/§7/§9 |
| C7 硬目标确认（条件提案） | 单 Agent 判断自然语言目标 → 如要求代码绝对阻止误选，增加可信结构化目标选择并收窄 Target Scope | 提示词不能提供确定性保证；不让另一个意图识别模型或正则解析器假装可信选择。影响入口交互，需另行设计/批准；R7 不偷偷增加 |

没有为自主性取消任何保护。C1 的格式白名单解决 SDK Markdown 会解释标签的具体风险；C5/C6 的限额解决新增二进制、解码、外发和留存风险，现有纯文本/JSON 限额不足以覆盖。只作用于新增显示或附件路径，不改变 SQL、连接、只读账号及治理权限。

## 5. 切片、依赖与验收

推荐顺序：**R7 → R3 → R12 → R4（S1–S3）→ E5 → E6**。R7/R3 的模型证据门槛与离线工作分开；环境暂不可用不阻断独立的文档/协议工作，但不能因此写成行为已通过。E5 的“不支持类型提示”可提前；真正附件输入与报告输出分别批准，不绑成一次巨大 PR。

### R7：多集群同名表的目标确认（第 7 项，优先）

**最小范围：** DEFAULT_INSTRUCTIONS、可信目标说明和必要工具说明、对话评估样例；显式 cluster 路由与治理不放宽。不新增共享 Agent 工具变更或前置自然语言分类器。

- [ ] 先建合成 fat/fat1/pre，三源同名表用不同结构/哨兵；正式 Application/SDK/治理链还原“新建 → 多源列库 → 无目标表结构”。旧提示的真实模型复现与脚本模型护栏分别记录，不用字符串断言宣称旧模型已复现误选。
- [ ] 区分“可用”“用户已选”“模型上次调用”三种信息，明确后两者不能混淆；歧义时问用户，不以最新成功工具当目标。无需自动保存一个由模型猜出的可信选中源。
- [ ] 早期成功对照：用户明确 pre 时，仅 pre 对象读取；关键反例：未选择且三源合理时，交付选择问题，不执行 describe/layout/show_create/read_query。工具本身仍会按模型显式参数执行，脚本故意猜目标不能被当作代码已拦住。
- [ ] 同类样例覆盖单获准目标不反问、明确延续 fat、要求切到 pre、要求三源比较、历史曾看多源、目标不可用不替换、同名不同库、新建后无目标；结构、DDL、布局和业务查数一并验。
- [ ] 对未知集群、撤权、诊断隐藏工具断言无未授权 I/O；保留预算、证据及全部本轮查询引用要求。隔离变异去掉 cluster 复核须被现有/新增护栏用例发现。
- [ ] 获准模型在新旧精确代码树各至少 3 次固定样例，逐轮记录实际目标/工具 I/O、澄清、错选、步数/耗时/用量。关键歧义不得擅自读取候选表；未取得真实证据不合入该行为切片，除非用户单独接受例外。
- [ ] 若模型仍误选，先报告具体任务与失败率，再决定是否需要 C7 的确定性入口；不悄悄扩成固定工具工作流。

### R3：减少重复，简短追问保留可核查事实（第 3 项）

**两个可分验的结果：** 模型不再重画结果；已批准 C3 后，历史简短追问默认摘要而不重复展开全表。复用 Evidence.validate_answer 和原引用规则。

- [ ] 分别复现字段/DDL 在 inferences 重复，以及“刚才多少条”因代码引用重展整表；不把后者全部归罪模型。
- [ ] 提示词保持结论、口径、限制、建议职责；原始表和 DDL 由事实区展示，不添加文字过滤或重复拒收。真实模型验列库、结构、DDL、五条查询及简短追问；相关旧提示词契约测试保留。
- [ ] C3 通过后，给最终回答增加最少的闭集显示意图，校验层只允许已有可见历史事实进入 brief；本轮新查询与明确索要原文的任务使用 full。模型 schema、旧保存回答的缺省 full、Session/重发解析兼容同时验证。
- [ ] 摘要数值来自当前渠道可信 row_count 等字段，并写“本次返回行数”，不当全表总数；不支持摘要的事实回 full，不让模型提交新的已核实数值。
- [ ] brief 的来源、采集时间、固定说明和丢失提示默认可见；完整获准原表/JSON可折叠，仍占现有预算。放不下的部分明确标出，不许一边省掉原表一边称“完整可展开”。需要更多内容时走已批准再提问/展示途径，不自动查询。
- [ ] 正式双入口覆盖 full/brief、聚合行数与结果行数、分页、历史/新证据混合、撤权、临时不可复核、字节不足；至少一个成功短答与一个拒绝交付。引用校验、SQL、原值和四种投影隔离不变。

### R12：统一业务卡片与受限格式（第 1、2 项，同一展示根因）

**依赖：** C1/C2 批准；R3 已确定 full/brief 接口时复用。只改飞书格式，Web 的文本安全与 JSON 契约保持，除第 4 项明确的系统提醒字段。

## 6. 第 4 项会话详细设计（原 v1 方案合入）

复用 SDK SQLAlchemySession 与已有 PolicySession，不用 SessionSettings.limit 取尾部裁剪。公开 Session 是唯一历史接口；提醒为可信渠道字段，不进入 AgentAnswer、模型请求或 SDK 历史。固定期限以真实 PolicySession 元数据为准，而非渠道映射创建时间。

### 6.1 状态与失败契约

采用一个有界的**可信会话状态快照**：观察时间、观察阶段、已提交轮数及限额、完整回放字节及限额、PolicySession 失效时间，以及可空的固定原因码。无法安全取得的计数留空，不能填零冒充测量值。快照不含问题、SQL、工具结果、Evidence 正文、签名、地址或凭据。

- 固定会话原因仅区分 `history_turn_limit`、`history_bytes_limit`、`expired`、`binding_changed`、`unavailable`；归属异常、损坏、失效证据等不能确定更细原因时用 unavailable。不要解析异常文字。
- `phase` 区分开始前、提交前、提交后；只从可信执行阶段产生，不从模型/远端取得。
- 外层仍保留 `session_unavailable` / 已存储的 `session_failed` 类别；日志追加 `session_reject=<闭集>`，保留原有 answer_reject/tool_error 等，不修改其他失败含义。
- 请求终态与快照同次应用表事务保存；completed 的快照只能来自成功提交，失败快照不能把未提交轮次计入。Session/应用表仍不假设跨组件原子，保留 result_not_saved 关闭规则。
- 用现有请求表增加一个可空、校验并限长的状态字段；总编码上限拟为 1024 字节：只容纳固定状态字段，防止附加字段成为正文旁路；现有 max_answer_bytes 只保护回答列，不能覆盖新增字段。不挤进 AgentAnswer/失败正文，不新增状态服务或通知表。旧请求为空，保留旧回执，不追溯猜原因。
- 显示用提示从快照的固定字段生成，加入渠道 Delivery 的可空系统提醒；只在已通过当前身份读取后展示。事实、推断和系统提示分开。
- 历史/重发显示“本轮结束时”的快照，不把旧剩余额度当成当前余额；不重新回放历史来更新一个旧提示。
- 在原本计算完整回放字节/读取会话元数据的位置取快照；不为提醒再做一次 Evidence 复核或全量回放，不多占 max_scope_checks。
- 快照非法时拒绝该记录的交付，不静默丢掉必要提醒；关键保存失败沿现有受控失败路径，不吞异常。

这需要一次显式应用表迁移；基线为 v6，实施时协调监控分支后分配下一个版本。保持失败码 CHECK 闭集及 SDK 自有表不动。接口字段的具体命名/内部函数留给开发；上述数据来源、事务和外部行为先锁定。

### 6.2 用户看到的结果

| 场景 | 默认可见的说明 |
| --- | --- |
| 达到已提交轮数上限 | “会话已达交互轮数上限。请新建会话继续；之前的上下文不会自动带过去。” |
| 历史字节达到上限 | “会话历史已达容量上限。请新建会话，并补充目标和关键线索。” |
| 本轮执行后提交超限 | “本轮执行后历史超出容量，回答未保存/交付，会话已封存；已执行的工具不会自动重试。” |
| 已过期 | “会话已超过保留期限。请新建会话；原历史不能继续回放。” |
| 模型/数据策略绑定变化 | “模型或数据策略已变化。请新建会话。” |
| 其他不可继续 | “会话历史不能安全继续，请新建会话；已执行操作不会自动重试。” |
| 未达到限额 | 正常结果；没有长篇实现说明 |

按渠道补最短操作指引：Web 点“新建会话”，飞书发 `/新建`；新建不等于立即删除保存记录。这里只修固定提示，不增加自然语言命令帮助功能。

接近上限：在**成功提交并保存**的同一条回复中，轮数达到限额的 80%、历史字节达到 80%，或 PolicySession 距过期不超过 1 小时，显示一条短提醒。合并命中条件，达到阈值后每个成功轮次最多一条；不加后台计时器、额外消息或告警状态表。

示例：“本轮结束时会话已用 80/100 次；历史容量接近上限。后续可能需新建会话，关键线索请自行保存。”不能说“还能保证聊 20 次”，字节、期限或证据失效可能先到；会话期限也不保证每条历史证据仍可复核。最后一次合法提交明确“下轮需要新建”。

### 6.3 会话契约取舍（提案，未生效）

1. **轮数建议 20 → 100。** 仍是有界上限；本片不取消期限、字节、权限或数据复核。只是允许更多完整历史回放，会增加耗时、模型输入用量和复核成本。
2. **字节与模型请求暂不拍脑袋调大。** 先比较当前 400000 / 1000000 与代表性排障样例；容量报告决定是否足够。若需增加，先给出最小成对数值、请求开销与预算证据，再获用户批准；不能以 100 轮为名顺带放宽四种投影、结果/响应/工具预算或 7 天期限。
3. **新增可信提示字段与应用表迁移。** 目的是首次投递、轮询、历史和重启后说明一致，不改变 AgentAnswer / Evidence 格式。旧客户端可忽略新增显示字段；旧镜像不能直接运行升级后的应用表，回退需明确迁移/恢复路径。
4. **提醒占渠道容量。** 默认可见，计入现有文本/卡片两项容量预算；沿既有事实优先与固定容量说明契约，不多发一条、不挤掉限制后冒充完整结果。

没有新增 Agent 硬步骤或更低资源上限。80%/1 小时是展示阈值，不阻断任务。更大的上下文能否保证真实模型更好排障仍是待验收问题。
