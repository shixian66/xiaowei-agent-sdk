## 1. 最小范围与复用

已确认环境是 Linux、已有 Docker、可从获准镜像仓库下载。公司服务器只运行发行包，不要求 Git、Python、uv、测试工具或构建工具。首个交付只支持实际选定并验证的一种 Linux CPU 架构；架构和 Compose 可用性在 A 的环境核对中记录，不先建设多架构发布或离线镜像分发。

| 已有能力 | 复用位置 | P3 工作 |
| --- | --- | --- |
| 正式启动与装配 | `src/xiaowei/cli.py`、`runtime.py` | 镜像运行同一 `xiaowei --config … serve`，适配容器监听与关闭期限 |
| Web 与飞书单聊/单群 | `web.py`、`static/`、`feishu.py`、`channel.py` | 验证正式入口、SSH、真实 mention/群成员/回复及排队；不另建入口 |
| Agent、工具与数据 | `app.py`、`governance.py`、`sqlguard.py`、`starrocks*.py`、`evidence.py`、`session.py` | 原链路进入已配置目标；复用 P2.5 与单群固定样例，核实真实模型和目标差异 |
| 存储与维护 | `storage.py`、`channel_store.py`、`migrations/` | 复用 `storage init/upgrade/cleanup` 与 `requests resend`；当前应用表版本为 5 |
| 安装与验证 | `pyproject.toml`、`uv.lock`、CI 的 `product-entry`、现有相关测试 | 复用 wheel 与锁定运行依赖，增加发行物和真实容器边界检查 |

关键链路：`Compose → cli → runtime → Web/飞书 → ChannelService → Application → SDK Runner → function tool → GovernedTools/SQLGuard → StarRocksAdapter → Evidence/PolicySession → 当前权限验证 → 渠道回复`。维护路径直接进入现有 CLI；重发只读取并复核已保存结果，不运行模型或业务查询。

基线的根 `Dockerfile`、`docker-compose*.yml` 属于旧 M5，含旧 API/Worker/迁移入口，不能作为新产品部署入口。新部署资产单独命名；旧 CI 和旧源码的物理清理不混入 P3。

## 2. 交付接口与必要契约

### 2.1 操作者只维护配置，不维护源码

正式发行包展开到固定目录，以下为接口约定：

| 文件或资源 | 归属与更新规则 |
| --- | --- |
| `compose.yaml` | 发行物；只有 `xiaowei`、`postgres` 两项服务，使用已验证的镜像 digest，无现场 `build`；普通应用版本不改变 PG digest、项目标识或卷绑定 |
| `OPERATIONS.md`、`release.json` | 发行物；唯一运维步骤与机器可核对的版本信息 |
| `xiaowei.example.json`、`.env.example` | 无凭据模板；只用于首次配置，升级不得复制覆盖实际文件 |
| `xiaowei.json`、`.env` | 服务器上操作者创建并保留；不在发行包中，升级前后逐文件比较内容不变；JSON 只读挂载，凭据沿用 `env:NAME` |
| `certs/`（有自定义 CA 时） | 操作者管理，只读挂载；证书路径在容器内有效，升级保留；不为不存在的需求生成证书 |
| PostgreSQL 命名卷 | 与镜像和发行目录的版本独立，初次部署确定绑定后沿用 |

`release.json` 只含代码 SHA、应用/PG 镜像引用、CPU 平台、应用 schema 版本和配置迁移说明；无真实配置或凭据。部署包以文件白名单构造并核对归档成员，不能先复制全仓再删除。镜像白名单基于 wheel、运行依赖和必需资源；不靠 `.dockerignore` 单项声明证明镜像干净。

镜像入口固定使用 `xiaowei --config /etc/xiaowei/xiaowei.json`，默认命令为 `serve`，所以维护仍可用 `docker compose run --rm --no-deps xiaowei config check` 或 `storage upgrade`。宿主机 `xiaowei.json` 挂到上述路径，可选 `certs/` 挂到 `/etc/xiaowei/certs/`；首次初始化/升级前先确认 PG 已就绪。Compose 项目标识与卷名在首次部署确定，换发行目录不得偷偷连到新空卷。

`.env` 只存实际运行所需环境值，由 Compose 读取；应用获得其配置所引用的值，PostgreSQL 只获得自己的初始化变量。文件受宿主机权限保护，JSON 挂载应可被镜像中的非 root 用户读取。模板说明 PostgreSQL 密码与 `XW_DATABASE_URL` 的一致性及 URI 编码，不能把特殊字符直接拼接成 URL；升级不轮换 `XW_DIGEST_KEY`。核验不得输出 `.env`、完整 `docker inspect` 或展开凭据后的 Compose 配置。检查 `$`、`#`、空格和引号等合成凭据的传递，遵守 [Compose 变量规则](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)。

### 2.2 容器网络与正式入口

基线 `ServeConfig.listen_host` 只接受 `127.0.0.1`/`::1`，且要求监听地址出现在 `web.allowed_origins`；直接发布容器端口无法使只绑定容器 loopback 的 Web 可达。A 只增加容器所需的 `listen_host="0.0.0.0"`，保留原本机默认值与校验；不开放任意外部监听地址。

容器绑定时，监听接口与浏览器来源分开：`web.allowed_origins` 仍只接受明确的 loopback 地址，至少包含实际访问的 HTTP 来源，`secure_cookie=false` 配合同一 SSH HTTP 入口；`0.0.0.0` 不是允许的浏览器来源。Compose 首个默认发布 `127.0.0.1:8501:8501`，浏览器经本地转发访问 `http://127.0.0.1:8501`。需要不同端口时同步配置发布端口、本地转发端口、允许来源和健康探针 Host，不关闭 Host/Origin 校验。应用不能自行证明宿主机的端口发布正确，必须检查实际容器网络。

PostgreSQL 只连接专用 Compose 网络，无宿主机发布端口；不用 host network。应用镜像为非 root，配置只读，日志有大小/份数上限。运行一个应用进程；复用实例锁，不用多个 Uvicorn worker。Compose 停机宽限应覆盖现有 Web/飞书的有界停止链路，不能只取群 SDK 的 7 秒最低值。

`/healthz` 只证明进程存活，`/readyz` 反映存储/实例状态及安全的渠道状态；不发付费模型请求。飞书不可用不等于 Web 不就绪；某个 StarRocks 目标不可用不得误写为所有业务路径健康，也不因此反复重启整个应用。检查与文档复用现有语义。

### 2.3 升级、配置兼容与恢复

- 普通升级：取得已验证发行物，保留 `xiaowei.json`、`.env`、可选 CA 和卷绑定；拉取应用镜像，再只重建小维容器。模板不能覆盖配置；失败时保留旧发行物及数据，不自动退回后再重放请求。
- 含应用 schema 变更：先备份配置与完整应用数据库，再停止小维，使用新镜像显式执行 `storage upgrade`，成功后启动。沿用实例锁和迁移事务；普通 `serve` 不建表、不升级。旧程序拒绝新 schema 时，通过匹配的旧镜像、旧配置及升级前备份回退，不实现降级迁移。
- 配置兼容：保持现有配置含义和权限范围，增加可选字段须有不扩大权限的兼容默认值。确需不兼容变更时，发行说明明确列出；配置预检查失败应在替换运行实例前发现，不能仅在停掉旧服务后才告知需重新配置。在既有 CLI 增加唯一必要的只读操作 `xiaowei --config <路径> config check`，复用 `load_config` 核对配置、引用环境值是否存在且非空及所需本地 CA 是否可读；不连接数据库、模型或飞书，不建表/写文件。成功返回 0，配置问题返回 2，仅报告字段路径与固定原因。操作者通过一次性应用容器预检，无需编写 Python；预检通过不证明外部服务连通或凭据已被服务端接受。
- 备份恢复：配置为优先保留对象，运行记录保持现有持久卷并提供手工备份。数据库备份覆盖 SDK 与应用表；使用 PG 镜像内同版本 `pg_dump -Fc`，成功才把临时文件标为有效备份。恢复先进入新建隔离库，用 `pg_restore --exit-on-error`；不直接覆盖现有业务库，验证通过后再由操作者决定切换。参见 [pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html)、[pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html)。
- 恢复验证沿用架构 §8–§9：未完成请求不补跑，写入不明的会话关闭，过期或撤权内容不能读出；群中仅排队未开始的请求按现有语义中断。备份文件同样限制访问和保留，配置与凭据备份不进入 Git、CI 产物或对话。首版不提供自动备份、时间点恢复或高可用承诺。
