# 会话限额与提醒修复实施计划

> 文档版本：v1，2026-10-10。状态：待独立审查、未实施。当前仅授权设计、计划、文档和有边界的离线验证；没有产品代码、真实服务、推送、PR、合并或部署授权。
> 后续实施按 `superpowers:executing-plans` 串行完成各片；每片先观察目标测试失败，再最小修复、验证和提交。

**目标：** 长排障对话能在明确容量内继续；接近上限有提醒，不能继续时知道原因和下一步。

**架构：** 复用 SDK Runner、SQLAlchemySession、PolicySession 和现有请求/投递链。由可信代码记录会话状态并生成渠道提示，不增加模型循环、记忆服务或会话管理工具。

**技术栈：** 锁定 OpenAI Agents SDK 0.22.3、Python 3.11、Pydantic、SQLAlchemy/asyncpg、PostgreSQL、现有 Web 与 lark-channel-sdk 1.4.0。

**需求与权威：** 本轮用户要求“先写修复实施计划”，并限定为设计/文档；延续此前会话轮数太少和监控能否并行的讨论。已批准边界引用 [AGENTS](../../../AGENTS.md)、[ARCHITECTURE §8–§9](../../../ARCHITECTURE.md#8-最少的状态与可靠性)；本计划中的新增契约是提案，批准后才据实更新 ARCHITECTURE，不复制另一套规范。

## 1. 基线、范围与事实

- 基线：最新 `origin/main` 的 `2b541a30bb39d88d160e7f6f69de1c81fdea74d8`，包含 PR #73 / A4；已 fetch 并核对。工作树 `session-limits-plan/agent-SDK`，分支 `codex/session-limits-plan`。不改 `codex/monitoring-g0` 或其他工作树。
- 本片只处理会话限额、接近上限提醒和会话失败说明。Markdown、附件、报告导出、同名表目标确认等七项复盘中的其他事项另行实施。
- 自动摘要、自动裁剪、跨会话接续、长期记忆不在本片。用户认为低优先级的“让模型介绍 /新建”也不做；现有新建入口和提醒中的操作指引仍须正确。

| 已核实事实 | 源码/证据 | 根因与影响 |
| --- | --- | --- |
| 模板是 20 个已提交轮次、400000 历史字节、604800 秒期限；模型请求限额为 1000000 字节 | `examples/xiaowei.example.json` | 三道上限独立；只改轮数不保证长对话可继续 |
| 轮数是一次成功提交的用户交互，不是工具调用数 | `PolicySession.commit_validated` | 一轮多次工具仍计一次；提交后飞书发送失败也已计数 |
| 字节检查用完整回放，包括获准工具投影、调用参数、最终消息和签名；不是数据库中 Evidence 引用的大小 | `PolicySession.get_items` / `commit_validated` / `_size` | 查表、DDL、监控结果可比纯聊天更快填满历史 |
| 会话期限从创建起固定计算，不随聊天续期；渠道映射与 PolicySession 元数据各有自己的期限 | `ChannelStore._insert_current`、`PolicySession._new_row` | 活跃也会过期；不能仅用渠道映射期限估计 Runner 历史寿命 |
| 开始前轮数/字节限额会拒绝；本轮提交前新增历史超字节则封存，工具可能已经执行 | `PolicySession.get_items` / `commit_validated` | 两条失败路径不能都声称“未执行” |
| 轮数、字节、过期等合并成 session_unavailable，渠道又合并成 session_failed | `app._turn_error`、`channel._FAILURE_CODES` / `_receipt` | 用户看不到具体原因，日志也不能区分 |
| 页面轮询与飞书投递都从请求记录重新构造结果；该记录没有安全的细分会话原因/提醒快照字段 | `ChannelStore`、`ResultDelivery.view/send`、`web._view` | 只改异常文字或本次内存对象，刷新/重启后就丢失说明 |

2026-10-08 三次线上失败在 storage_ready 后约 30–46 ms，日志只有 `session_unavailable`。这证明未进入正常回答阶段，**不能证明就是 20 轮或字节超限**；此前猜测仍未证实。

## 2. Agent 任务、信息与停止规则

沿用已确认的样例，在合成数据上扩展成连续排障，不规定工具顺序：

| 用户任务 | 交给 Agent 的选择 | 必要信息与成功标准 |
| --- | --- | --- |
| “查看 fat 的 data_center.quota_virtual_account_quasi_rt 结构”，随后“只查这张表的 5 条数据”“为什么这么多” | 选获准工具、写 SQL、判断何时补布局或引用已获准历史 | 目标来自本轮或清楚的可信上下文；表字段来自工具；只查 5 条，解释有实际 SQL/Evidence，不能凭记忆冒充事实 |
| “不要执行，只解释刚才 SQL”“要原始结果，不要预先截短” | 根据本轮意图选择解释、生成 SQL 或受治理查询，标明实际限制 | 不继承上轮查询许可；原文与完整性仍受既有投影/结果上限，不因为会话放宽而改变 |
| 监控调查中反复追问 CPU、告警与时段，并回到早先证据 | 在本轮已授权源中选择工具、补取证、比较、结束调查 | 源/时段/指标口径从当前用户、可信业务说明和工具获得；关键歧义须问用户，不能默认选一个同名集群/源 |

本片不改这些任务的提示词或工具契约，也不宣称修复了同名目标误选。任务样例用于检查会话改动是否损伤已有行为。

- 正常历史可安全回放时，让 Agent 自行调查，不因“第几步”固定工具顺序。
- 参数、SQL 或预算在 I/O 前被拒绝时，仍按现有治理契约回给模型；能否调整/继续由现有分类决定，本片不扩大可修正范围。
- 已批准的监控 timeout/auth/unavailable/5xx：停用本源本轮，不生成成功 Evidence；可继续其他已授权源，说明未核实范围，遵循[监控计划 §3.1–§3.3](2026-10-09-monitoring-mcp.md)。
- 不能安全回放、会话过期/关闭/超限、未知协议错误、Evidence/最终回答拒收：停止相关轮次，保持原原因及状态，不自动重跑。
- 只是暂不可验证数据权限时，保持 `scope_unverifiable` 与可继续的会话；不能改成永久过期。
- 取消、远端执行/发送未知、部分存储失败保持现有 unknown/封闭/readiness 保护；提示不把“已提交”说成“已送达”。
- 权限、目标、预算、证据复核与未来写审批是必要依赖，模型不能跳过。W5 的 Action 持久化与批准独立于对话续跑，本片不改审批或执行机会。

当前工具说明继续沿已批准版本：明确适用问题、目标/参数、分页/截断及可修正拒绝；本片不新增工具或说明覆盖入口。容量样例必须复用正式工具装配，不能删工具说明来挤出请求空间。

提醒只给用户，不进入 AgentAnswer、模型请求或 SDK 历史；Agent 无须新增“查会话余额”工具。用户实际意图和既有预算仍决定调查。未提供目标、必要口径时如何澄清沿既有契约，本片不增加固定反问。

## 3. 最小方案与调用链

### 3.1 SDK 与现有机制

已读取本地锁定 SDK：公开 Session 提供 get_items/add_items/pop_item/clear_session，SQLAlchemySession 提供持久化；SessionSettings.limit 按条目取尾部历史，**不是已提交轮次**。小维已有 PolicySession 的归属、Evidence 重验、暂存/提交和完整配对保护，继续复用。

官方[内存与压缩示例](https://developers.openai.com/cookbook/examples/agents_sdk/building_reliable_agents_memory_compaction)介绍 Responses 压缩能力；不能据此推断当前 Vertex/Gemini Profile 和本仓库 Evidence 契约已支持。自动摘要既超出本次范围，也不能用条目裁剪替代安全回放。

关键路径：

```text
Web / 飞书验证身份、接受请求、同会话互斥
 → ChannelService（当前授权、prepare_tools）
 → Application → SDK Runner → PolicySession 准入/完整回放
 → 已授权工具 → 治理/Adapter → Evidence
 → 最终回答重验 → Session 提交与可信状态快照
 → ChannelStore 原子保存请求终态及会话说明
 → ResultDelivery 当前接收权限/Evidence 重验
 → Web / 飞书同条结果显示系统提醒 → 单次投递
```

### 3.2 必须确定的数据与失败契约

采用一个有界的**可信会话状态快照**：观察时间、观察阶段、已提交轮数及限额、完整回放字节及限额、PolicySession 失效时间，以及可空的固定原因码。无法安全取得的计数留空，不能填零冒充测量值。快照不含问题、SQL、工具结果、Evidence 正文、签名、地址或凭据。

- 固定会话原因仅区分 `history_turn_limit`、`history_bytes_limit`、`expired`、`binding_changed`、`unavailable`；归属异常、损坏、失效证据等不能确定更细原因时用 unavailable。不要解析异常文字。
- `phase` 区分开始前、提交前、提交后；只从可信执行阶段产生，不从模型/远端取得。
- 外层仍保留 `session_unavailable` / 已存储的 `session_failed` 类别；日志追加 `session_reject=<闭集>`，保留原有 answer_reject/tool_error 等，不修改其他失败含义。
- 请求终态与快照同次应用表事务保存；completed 的快照只能来自成功提交，失败快照不能把未提交轮次计入。Session/应用表仍不假设跨组件原子，保留 result_not_saved 关闭规则。
- 用现有请求表增加一个可空、校验并限长的状态字段；总编码上限拟为 1024 字节：只容纳固定状态字段，防止附加字段成为正文旁路；现有 max_answer_bytes 只保护回答列，不能覆盖新增字段。不挤进 AgentAnswer/失败正文，不新增状态服务或通知表。旧请求为空，保留旧回执，不追溯猜原因。
- 显示用提示从快照的固定字段生成，加入渠道 Delivery 的可空系统提醒；只在已通过当前身份读取后展示。事实、推断和系统提示分开。
- 历史/重发显示“本轮结束时”的快照，不把旧剩余额度当成当前余额；不重新回放历史来更新一个旧提示。
- 在原本计算完整回放字节/读取会话元数据的位置取快照；不为提醒再做一次 Evidence 复核或全量回放，不多占 max_scope_checks。
- 快照非法时拒绝该记录的交付，不静默丢掉必要提醒；关键保存失败沿现有受控失败路径，不吞异常。

这需要一次显式应用表迁移；基线为 v6，实施时协调监控分支后分配下一个版本。保持失败码 CHECK 闭集及 SDK 自有表不动。接口字段的具体命名/内部函数留给开发；上述数据来源、事务和外部行为先锁定。

### 3.3 用户看到的结果

| 场景 | 默认可见的说明 |
| --- | --- |
| 达到已提交轮数上限 | “会话已达交互轮数上限。请新建会话继续；之前的上下文不会自动带过去。” |
| 历史字节达到上限 | “会话历史已达容量上限。请新建会话，并补充目标和关键线索。” |
| 本轮执行后提交超限 | “本轮执行后历史超出容量，回答未保存/交付，会话已封存；已执行的工具不会自动重试。” |
| 已过期 | “会话已超过保留期限。请新建会话；原历史不能继续回放。” |
| 模型/数据策略绑定变化 | “模型或数据策略已变化。请新建会话。” |
| 其他不可继续 | “会话历史不能安全继续，请新建会话；已执行操作不会自动重试。” |
| 未达到限额 | 正常结果；没有长篇实现说明 |

按渠道补最短操作指引：Web 点“新建会话”，飞书发 `/新建`；新建不等于立即删除保存记录。这里只修固定提示，不增加自然语言命令帮助功能。

接近上限：在**成功提交并保存**的同一条回复中，轮数达到限额的 80%、历史字节达到 80%，或 PolicySession 距过期不超过 1 小时，显示一条短提醒。合并命中条件，达到阈值后每个成功轮次最多一条；不加后台计时器、额外消息或告警状态表。

示例：“本轮结束时会话已用 80/100 次；历史容量接近上限。后续可能需新建会话，关键线索请自行保存。”不能说“还能保证聊 20 次”，字节、期限或证据失效可能先到；会话期限也不保证每条历史证据仍可复核。最后一次合法提交明确“下轮需要新建”。

## 4. 产品契约取舍（提案，未生效）

1. **轮数建议 20 → 100。** 仍是有界上限；本片不取消期限、字节、权限或数据复核。只是允许更多完整历史回放，会增加耗时、模型输入用量和复核成本。
2. **字节与模型请求暂不拍脑袋调大。** 先比较当前 400000 / 1000000 与代表性排障样例；容量报告决定是否足够。若需增加，先给出最小成对数值、请求开销与预算证据，再获用户批准；不能以 100 轮为名顺带放宽四种投影、结果/响应/工具预算或 7 天期限。
3. **新增可信提示字段与应用表迁移。** 目的是首次投递、轮询、历史和重启后说明一致，不改变 AgentAnswer / Evidence 格式。旧客户端可忽略新增显示字段；旧镜像不能直接运行升级后的应用表，回退需明确迁移/恢复路径。
4. **提醒占渠道容量。** 默认可见，计入现有文本/卡片两项容量预算；沿既有事实优先与固定容量说明契约，不多发一条、不挤掉限制后冒充完整结果。

没有新增 Agent 硬步骤或更低资源上限。80%/1 小时是展示阈值，不阻断任务。更大的上下文能否保证真实模型更好排障仍是待验收问题。

### S2：会话拒绝原因贯穿存储与双入口

**交付：** 同一次失败在日志、Web 轮询和飞书固定回执中含一致且准确的安全原因；重启不丢失。

涉及：`session.py`、`app.py`、`channel.py`、`channel_store.py`、`models.py` 的可信应用/交付接口；应用迁移、`storage.py`、`scripts/package_release.py` 和相应存储/发行测试。SDK 历史表、AgentAnswer 和 Evidence 验证不改。

- [ ] 先补真实 Session/请求存储的参数化 RED：轮数、历史字节、期限、绑定变化、不可回放；以及一条工具已执行而提交超字节的正式入口失败。断言原类别、具体原因、持久状态和真实 I/O，不只匹配异常文本。
- [ ] 在旧代码确认至少一个正式 Web/飞书失败场景缺少原因，再做最小数据贯通和迁移；取得投递权、幂等和保存失败保护复用现有链。
- [ ] Web 轮询/页面刷新、飞书事件替身都显示对应固定说明；重启后重新读取同一记录仍相同，重复消息不重跑。历史原因不根据现在的计数重新猜测。
- [ ] 对开始前轮数/期限拒绝断言没有模型调用和业务工具 I/O；字节回放可能先做证据权限探测，MCP prepare_tools 也可能先重连/发现，不把这说成“所有外部 I/O 为零”。提交超限断言已发生的工具不重跑、SDK 历史未提交且状态 sealed。
