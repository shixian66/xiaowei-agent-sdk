### 第 4 类误读的根因与处理

1. **超长数被当作无法判定数：** 代码已将 `window_oversize_rows` 与 `unclassified_candidate_rows` 分开，已有 Skill 也解释二者，但直接交付的英文嵌套字段难读；工具 description 没有逐项解释。优先在工具说明中补清两个字段口径，代码展示为“全窗超长记录”和“无法判定候选”，保留原字段名，避免无收益的迁移。
2. **ERR 被归因为集中的语法错误/探测：** 固定采集列只有状态等元数据，没有返回错误原因，也没有全体失败行的时间分布。6 条 ERR 只能支持“执行失败 6 条，原因未取得”，不能据此确认错误类型或集中发生。
3. **多语句被归因为 ETL/风控：** 程序只识别一条审计记录中的多语句结构，既不返回 SQL 正文，也没有业务用途字段。单凭此信号无法区分客户端元数据探测与批任务。首版采用“多语句线索，业务用途待 DBA 按 Query ID 核对”，不新增用途分类器或提取更多 SQL 内容。
4. **结论缺失：** 当前 Skill 只泛指“写范围、覆盖、发现、依据和下一步”，未要求结论先行；v4 渲染遵从模型块顺序，代码不会自动补风险结论。

以上数据和调用链为源码事实；“字段缺少就近说明促成了本次模型误读”是推测，没有原始对话证据可归因到某一句提示词。不能宣称只改说明就能保证模型判断正确，仍须公司侧真实回答验收。

## 3. 推荐方案与备选

**推荐：一个共用的轻量业务展示视图，加一个巡检专属的标签/计数映射。** 在现有 `feishu_render.py` 的业务 helper 附近补纯函数，供飞书卡片、纯文本、Web 和 MD/HTML 共用。已有跨渠道调用已经落在这里，本轮不为文件命名另做模块搬迁。

### 3.1 通用修复：从获准原值恢复类型，再渲染

- 提取 `feishu_report._fact_section()` 已有的类型恢复做法：只从当前 `DeliveryFact.result_json` 取原值，沿 `business_fact()` 的业务/技术选择生成展示视图；不从其他渠道、模型文本或数据库补值。
- 普通对象/数组按真实类型用缩进、换行或现有字段/表格组件展示；不再把已经编码的 JSON 文本二次编码。真实字符串即使长得像 JSON 也保持字符串，不逐字段猜测解析；缺少 `result_json` 的旧/合成事实沿现有展示值处理。
- 大整数先在服务端转为精确显示文本；嵌套值与业务字符串保留原类型，NULL/空串/缺失及各渠道标量显示见 [ARCHITECTURE §7](../../../ARCHITECTURE.md#user-delivery-and-history)。Web 技术字段复用已有获准 metadata 和 technicalKeys，无需另加一份 technical payload。复用现有控制字符显示、飞书纯文本组件、Web `textContent` 和报告转义。
- 保留轻量共用视图，只提供当前需要的可见说明、字段、检查表和样本表，不承载权限决策、可变取证状态或模型意图。Web `_view()` 为 v4 附加即时生成的 `presentation` 展示数据，JS 通用遍历即可；保留现有 API 字段，旧响应没有它时走现有渲染路径。它不写入 Evidence、Session、`TurnAnswer` 或数据库，也不扩展为展示 DSL、注册器或可配置模板。
- 不扩大全局隐藏字段集合来屏蔽所有工具的 `coverage`、`query_id` 等名字；巡检的业务/技术划分只作用于该 tool_id。其他工具只获得嵌套值可读性修复。
- 复用 `_raw_redundant()` 的无损替代判据，不因嵌套值显示得更好看就认定原始 JSON 冗余；隐藏、丢失或无法保真替代原值时，卡片和 Web 的技术区仍保留获准原文。纯文本继续不附技术详情。

### 3.2 巡检展示：结论、覆盖、检查表、代表样本

1. **模型首个正文文字块用一行给结论。** 使用 🟢 未发现线索 / 🟡 有需核查线索 / 🔴 有高风险操作或注入、延迟信号，结合证据说明核查优先级。颜色不等于攻击成功或维护未授权，不由代码按命中数打分。未完成取证时直接说明“覆盖不完整/尚不能判断”，不硬凑健康结论。这里的首行指业务正文，保留必要系统提醒和“AI 说明”身份标签的既有优先级，不重排审批或必要状态。
2. **紧接事实块，由代码先给覆盖行。** 包含目标、半开窗口及明确时区、全窗聚合条数（读取时）、候选是否截断、分类计数是否完整；另区分“仅省略样本”。例如“fat · 15:00–16:00（UTC+08:00）｜全窗聚合（读取时）29,232 条｜候选未截断｜分类计数完整”。聚合不承诺晚到日志已收齐，或聚合与候选读取来自同一快照；窗口时区取获准证据，不由模型补写。**安全巡检 v4 的 full 和 brief 均默认显示覆盖说明、检查计数及必要完整性提示；brief 只影响样本明细和补充原值的收起，不能把检查表作为样本表一并折叠。** 此约定不改变其他工具、旧回答版本或已绑定内容的恢复语义。
3. **代码生成固定五行的检查项计数表。** 同一获准 Evidence 中直接取值，千分位显示；缺字段显示“未提供”，不补零。不相加分类数或操作分项计算独立请求数。

| 中文检查项 | Evidence 来源 | 不完整时的显示 |
| --- | --- | --- |
| 注入探测（OR 同值常量线索） | `signal_counts.boolean_probe` | 已确认至少 N 条 |
| 时间延迟调用线索 | `signal_counts.delay_call` | 已确认至少 N 条 |
| 多语句 | `signal_counts.stacked_statements` | 已确认至少 N 条 |
| 高风险操作（审计行） | `signal_counts.high_risk_operation`；同一行补充非零 `operation_counts` 分项 | 总数及非零分项均显示已确认至少 N 条 |
| 执行失败（ERR） | `failed_rows`，全窗聚合（读取时） | 不受候选截断影响，不跟随分类计数降为下界；仍受晚到与采集缺口影响 |

授权、撤权、账号/角色、口令修改、删表/库、清空表、导出、覆盖写入、无 WHERE DELETE 九项只展示非零分项，不为其另开一张表。九项字段齐全且均为零、分类计数完整时，高风险行可写“0（授权、删表、清表等九项均未命中）”；同为零但分类不完整时写“已确认至少 0 条（分类计数不完整）”，不能把已读部分的零命中说成全窗均未命中。

4. **“需要核查”的代表样本。** 复用现有样本及代表优先顺序，不再选样、不补 SQL。代码给样本序号、时间、账号、中文信号/操作、执行状态；延迟样本保留实际耗时、排队时间与请求延迟参数，供解释使用。Query ID 等内部定位信息在技术区与样本序号对应。模型在相邻文字块按样本序号给短解读与建议，不把模型解读拼进“系统事实”单元格。
5. **限制压缩成一两句。** 代码从既有 note/limitations 生成短说明并去掉同一事实的重复提醒，保留当次截断、无法判定、样本省略及既有晚到/规则缺口。巡检仅省略样本时，明确写“样本未全部列出，分类计数完整”，替换这一事实的笼统截断提醒；原始 `truncated` 不改，其他工具的提醒不变。完整限制、原始 coverage、规则版本、列定义、Query ID 与原始获准投影进入现有唯一技术区；重要完整性结果仍在覆盖行可见。

普通卡片/Web 按上述方式呈现；显式 MD/HTML 和自动容量附件复用检查表和样本映射，但按现有契约不附技术元数据 JSON，不新增“技术详情附件”。纯文本输出使用同一标签、覆盖与逐行计数/样本，不承诺卡片表格或折叠。公司本次究竟走卡片还是纯文本尚未知，验收时记录实际载体。

**为什么保留一点工具专属映射：** 通用格式器能解决对象可读性，却无法知道哪些数是全窗统计、哪些是分类下界，也不能把操作代码自动翻成正确中文。这一处映射只转换现有事实，不形成新规则引擎或独立报告链。

### 3.3 `scanned_through`：推荐置空

新结果将 `coverage.scanned_through` 置为 `null`，包括截断和未截断场景；工具说明明确“未提供扫描水位”，不能把 null 理解成未扫描。全窗范围由 `window` 表达，完整性由 `scan_limited`、`unclassified_candidate_rows`、`match_counts_complete` 表达。全仓未发现运行时读取该子字段的消费者；保留可空键是沿用已确认的置空方案，避免本次再改变嵌套字段集合，不以假设的读取方作为依据，也不新增空值校验或兼容层。

不取窗口结束时间：那只是请求边界，不能证明晚到日志收齐或所有候选可判定；不改名：当前没有消费者需要最后候选时间。删除键在技术上也可行，本次维持置空选择。旧证据中的非空值只随原始获准 JSON 保留在技术区，不为它单独添加注释或展示分支；新覆盖行不读取它，新回答也不以它判断进度。已保存模型文字的处理见 §5。

### 9.3 Agent 的信息、选择与记忆边界

| 需要的信息 | 获取与复用方式 | 缺失时的行为 |
| --- | --- | --- |
| 本次目标、时间、用途和接收范围 | 用户请求/已确认任务规格、可信上下文、工具绝对窗口 | 环境或必要时间无法确定才澄清；已有信息不重复问。后台确需答案才能完成时用既有 awaiting_user/incomplete 交付 |
| 本窗操作、ERR、覆盖限制 | 本次 `inspect_audit_security` 的原始 Evidence；补证按需 | 历史结果不能代替新窗口。单目标已分类取数失败沿既有局部失败语义；缺口不补零 |
| 业务用途、原调查依据 | 当前明确背景；获准 history 搜索/直读；必要时已有只读源 | 用户说明、历史已观察事实和旧模型猜测分别表述；无源的旧“正常”文字不升级为事实 |
| 对应哪个外部调度作业、当时版本、是否变化 | 只有当前已配置并获准的源真实提供时才使用；可核对运行回执、Query ID 等关联 | 目前固定审计列不提供关联键；相同账号/时间/SQL 注释不足以确认来源。没有版本/变更信息时重查相关依据或写“未复核”，不能声称未变化 |
| 当前用户可读、模型可见、接收方可收 | 既有治理与 Evidence 校验 | 不由提示词、历史批准或背景说明授予权限，不新增另一套权限检查 |

Agent 自主决定是否读历史、按哪个目标/窗口搜索、是否直接读取已知原记录、如何写获准 SQL、是否缩窗/补证、何时结束；不要求每次先搜索再读取再查询，也不要求每个信号都补查调度。历史工具未开启时照常完成当前可做的巡检；只有任务确实需要历史时说明该缺口，不因工具缺席无谓澄清或增加固定提醒。

建议工作方法：先根据任务和已有可信材料判断当前缺什么；需要过去事实才取历史；同样背景足够且没有影响当前判断的变化时，不重复查询它；本次状态需要当前证据。对新出现的范围变化、错误或其他重要信号自主补证，给出具体关注理由；材料不足时只报告可确认事实及缺口。这个方法不构成工具强制顺序或固定调用数门槛。

**查过一次的实际含义：** 原业务 Evidence/请求/定时结果仍保存且可读时，可以检索；期限未到只说明允许读取，不证明内容至今没变，Evidence 对象版本也不等于调度任务版本。没有源版本或内容更新信号，无法自动知道背景是否变化。新一次只保存历史转述的回答不是新的原始依据。连续运行应按需检索原始记录，原记录过期后重新取证或保留未知；不延长保留期、不生成常驻记忆。H1/H2 不检索用户所有聊天，不能承诺用户随口一句“正常”以后永远生效。明确且稳定的业务用途可以由用户写在现有任务正文或可信业务口径中，始终标明是用户提供的背景，不由 Agent 自动把推断写成长期事实或操作授权。

### 9.5 错误、停止及用户看到的结果

| 可达情况 | 沿用的处理与用户结果 |
| --- | --- |
| 参数/绝对时间错误；已批准 SQL 解析修正 | 由现有工具反馈允许的原因，Runner 在原预算内修正或结束；不加重试循环 |
| 历史未找到、过期、单条来源不可读；只含转述的旧总结 | 工具内按原 gaps 返回；可继续其他获准依据或说明未知。不会因一个背景缺失把其他已取得事实丢掉 |
| 安全巡检已分类源失败或监控 source_stopped | 停止对应操作/源，允许调查用户已要求的其他目标；保留既有可信未完成提示 |
| not_allowed、authorization_unavailable 等不可修正工具拒绝 | 停止相关操作；不改身份/换源绕过。若发生在已接纳 Evidence 的提交/交付复核，沿原整轮失败，而不是从正文删一句继续发送 |
| Evidence/Session/存储、未分类执行错误、结果契约失败；原业务查询非可修正错误 | 沿现有 TurnError 终止相应轮次，保留失败状态；不把旧报告当作本轮成功 |
| 工具/SDK预算或期限用尽 | 沿现有路径，仍能安全验证时用已知事实收尾；整轮超时或复核额度不足导致无法验证时受控失败，不交付未验证正文。不加额度、运行时预留或“必须查完”的门槛 |
| 任务执行/通知结果 unknown | 保留 unknown，不自动重跑/重发，不声称远端已停止或成功 |

报告中的未知分两类：影响本轮关键目标、需要用户决定的，明确提出必要问题；只影响背景完整性的，说明缺口并交付当前结果，不强制 awaiting_user。保持每次巡检原有发送机制；C1 只改变何时提出核查建议，不新增静默、去重或阈值。
