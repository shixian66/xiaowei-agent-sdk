## 1. 保留的最小方案

同一进程内用小型 asyncio 到期检查和现有 PostgreSQL 记录任务。固定提醒到点直接发送；业务任务每次建立新 Session，走 `Application.run_turn → SDK Runner → GovernedTools → Adapter/MCP → Evidence`，由可信交付路径发送校验后的最终结果。后台 Agent 只见获准自动执行的只读工具，不开放 notify、任务管理或生产写工具；通知仍经过治理，不另建 Loop。

A 即时多机器人通知 → B 一次性固定提醒 → C 通用独立 Agent 定时任务 → D Node 核心巡检。每片只建设自己的直接需要，不提前搭后片平台；C 不按 `task_type=node` 分派业务函数。后续 StarRocks、Grafana 等能力逐项核验授权及样例后复用 C。

管理员静态登记机器人别名、目的地说明、安全引用和可接收源/工具范围；第一批操作入口仍是当前指定飞书群，多个目的群不等于多群操作入口。仅支持纯文本、一次时刻及固定间隔；不做任意 URL、Shell/curl、MCP Server、独立 Worker、通用 DSL 或自动修复。asyncio 复用现有异步 PG 与生命周期已够用；APScheduler 仍不能代替业务授权和发送记录，只有复杂日历、多进程或实际负载证明需要时才重评。

## 3. 固定用户样例与 Agent 行为

U1–U4 沿用原验收，U5–U7 沿用后续确认的任务，不以安全检查替代任务成功。

| 样例 | 应有结果 |
| --- | --- |
| U1：给 ops_alert_bot 发“今晚 22:00 检查 StarRocks” | 正确目标、准确内容、一次发送。HTTP 与飞书业务响应都成功才说“已向运维告警机器人提交消息，Webhook 接口返回成功” |
| U2：发到未经登记的 Webhook URL/机器人 | 在 HTTP 前拒绝：“该机器人尚未配置或授权，未发送消息。” |
| U3：把刚才 fat 慢查询分析/巡检结论发到 ops_alert_bot | 允许获准摘要外发；复核当前读权、Evidence 和目的地数据许可，展示实际内容/状态。不满足则说明未发送及原因，不能因有查询权限就发完整原始结果 |
| U4：测试发送失败或超时 | HTTP 200 但业务码非零不报成功；确定拒绝报 failed，可能已发送但无可靠响应报 unknown，均不自动重复 POST |
| U5：明天上午10点把汇报提醒发到大数据群 | 展示绝对日期、时区、文字、目标及迟到策略，确认后到点一次发送；迟到按该任务策略，原 Session 过期不影响任务 |
| U6：每3小时巡检所有 Node 主机并发到大数据运维告警群 | 每次独立取证并发送覆盖、异常和未检查项。若起草带旧 Evidence，确认时明确任务截止及无旧依赖的创建办法，不能承诺持续数周。完整目标仍含 IO/网络；D 首次只验收采集、覆盖、CPU/内存/磁盘，明确 IO/网络未纳入，不能宣布完整 U6 已验收 |
| U7：把已有获准只读能力设置为一次或周期任务 | Agent 可整理规范化任务，用户确认后成为批准版本；未来逐项接入自动只读集合。自动改配置/重启不能获准，须另走原生产 Action |

**交给 Agent：** 在批准源、工具、目标和预算内选择工具、写只读 SQL/PromQL、根据证据修正查询、补证及结束调查。可把“照刚才的方法”整理成自包含任务说明；已有可信信息足够就不让用户完整重述。示意顺序不是固定工作流，Node 覆盖要求也不写进调度器。

**需要的信息：** 身份、当前时间/时区、允许范围和机器人来自可信配置/上下文；结构、指标与事实来自工具。Agent 草拟内容、源/范围、时间、接收方、预算与输出要求，代码校验权限和参数，再向有权限用户展示最终版本。别名/时区/业务口径歧义且现有上下文不能确定时才问。无需原文片段证明、自然语言 DLP 或来源签名。

**错误与停止：** 按现有契约修正可纠正的表达式、选择器或容量拒绝，预算不重置；停止失败源，可在批准范围调查其他源并报不完整。权限或 Evidence 不通过则不使用相关数据、不发送相关结果；存储/Session 一致性失败不重跑补保存。无人值守需要澄清、SDK interruption 或发现写操作时结束该轮，说明需处理，不自动批准。暂时无法核验权限的处置与确定撤权分开，见 §5。

## 4. 必需接口、批准与最少数据

| 能力 | 输入与准入 | 输出/限制 |
| --- | --- | --- |
| send_webhook_message | 机器人别名、明确文字或获准 Evidence 摘要；独立发送许可，不接受 URL/headers/签名/重试参数。一次用户发送意图由服务端登记，不由模型 call_id 决定 | 安全 receipt_id、accepted/failed/unknown/not_sent 和有限原因；模型不同 call_id、并发调用只能获得同一意图的原回执 |
| 提出/创建/恢复/扩大任务 | fixed_message 或 agent_task、规范化正文、at/interval、源和自动只读工具范围、机器人、预算/迟到策略；模型可整理说明。代码校验后展示最终计划，由有权用户明确确认 | 保存不可变批准版本、批准人/时间和必要权限范围；确认后改目标/内容/范围须新版本，不能执行未批准候选 |
| 查询/暂停/取消 | 当前有管理权限的用户可直接调用；后台 Agent 不开放此能力。暂停、取消仅降低后续授权，不走完整 Action 审批 | 原子停用并返回当前状态；重复操作不增加权限，不删除发送回执。已准入 I/O 可能完成，不能承诺撤回 |
| Node 数据读取 | 优先复用实际能保留完整类型/标签/值/时间的获准 MCP 契约；确有缺口才补同源受治理读取 | 保留必要指标、覆盖和限制，不接受任意 URL，不访问结果里的 scrape URL |

**A 的意图键：** 即时通知用 `(原请求 turn_id, 稳定机器人 ID, SHA-256(最终纯文本的规范化 UTF-8 字节))`，唯一约束和原子占用共用现有 attempt 记录。turn_id 来自可信的普通群请求；只统一换行等非语义格式，签名/时间戳不进摘要。相同内容换 call_id 或并发只返回原回执；同轮明确要求的两条不同提醒可各占一次，相同文本在同轮合并为一次，不承诺自然语言语义去重。不同文本仍须属于用户授权的发送范围，哈希变化本身不授予新权限。同轮同机器人准入串行：已有发送中可在预算内等待，不先占第二次机会；accepted 后可发送用户原先要求的另一条，failed/unknown 后则停止本轮该机器人后续发送，改字也不能自动重发，剩余消息明确记未发送。后者复用已有 attempt 状态，不另建重试机制。定时通知用固定 occurrence 的唯一发送机会，内容变化不生成第二次机会；不新增发送清单/槽位平台。

**A 的审批恢复限制：** 恢复轮不提供通知工具，准备/等待批准材料由代码明确提示“批准后不会自动通知，完成后请另发通知要求”；恢复轮如实说明未发送，用户随后在群里另提通知要求。原请求的 sent 可能只是审批材料已送达，不能证明恢复后新产生的风险提示已送达，因此不直接放开 paused 准入。未来若需批准后自动通知，另做实际审批交付与回执绑定，不改变本片生产审批链。

**用户主动重发：** unknown 的用户回执应说明“上一条结果未知，可能已经发过，重发可能重复”。之后用户在新一轮明确要求向同一目标“再发一次”，属于新的用户发送意图，可在当前授权和 Evidence 校验通过后占用新机会，原回执仍保留 unknown；不能把后台补发或模型自行换轮当作用户请求。风险提示必须在再次 POST 之前通过原入口展示，不能只在发送后的最终回答补一句；此前已展示同一回执的该提示则不强制再问一次。若此前未展示或无法核验，先提示，提示尚未展示时不发送；内容或目标指代不清才澄清。不新增生产审批或自动重试。A 须验证原入口提示与发送的时序，不能以可能失败且不控制执行的进度卡代替这一保证。

**A/C 的内容与投影：** 沿原飞书 owner/channel 的 `EvidenceStore.validate_answer` 取得 feishu 投影的 Delivery，由结构化 blocks/facts 渲染通知纯文本，不使用 Web 转义 content 或内部 Evidence 编号/JSON 信封。仅发送明确文字时保留原文及实际换行，不因无关历史查询加前缀或改变正文；所见历史仍全部复核。选择事实时，必要数值、SQL 和事实行由代码从 Delivery.facts 生成，模型文字单列“模型说明（未经系统核实）”；不自动转发未选择的查询结果。发送前的上下文为 `session.replayed_evidence ∪ 本轮已产生且模型可见 Evidence`，由代码收集，连同未引用项复核；在源端可读之外，再要求目的机器人获准接收这些源/工具。feishu 只是既有渠道投影，不等于机器人接收授权。管理员要在共享会话连续使用通知与提醒，须按 README 显式登记 scheduled 记录的接收范围；程序不自动授予该许可，任务记录也不消除原业务源依赖。缺配时给出管理员应核对的配置项，不能把日常连续操作变成 /新建 的固定流程；不伪造目的群 owner、不新增 webhook Audience 或第五列投影。A 最终 JSON 超过20000字节时整条 not_sent，用户可缩小所选摘要后重提；不新增自动省略/拆分算法。B 的带依赖正文及 C 的通知沿同一事实/接收边界，后续确有容量需求再评估完整行/块省略。

风险提示的门槛仅拦即时通知（包括用户明确重发），按原群＋稳定机器人共享，避免换人绕过；分别批准的固定提醒不因其他回执 unknown 被作废，仍各自最多一次 POST，自己的 unknown 继续计入即时门槛。代价是另一成员的无关消息也可能先被暂缓一次，用户已接受。原入口的容量提示/报告预览也必须保留 accepted/failed/unknown 与重复风险，放不下则明确交付失败；整个父交付失败时，即使尽力发送过预览，也不把它当作门槛已解除。接收范围不符时解释是当前可见历史超出目的地授权；可由用户显式 `/新建` 后完整重述纯文字，须说明这会轮换全群共享上下文，不能自动新建绕过。

**确认复用：** 创建及恢复/扩大任务优先复用已有 ActionBinding/SDK 暂停、材料展示、指定群确认及单次激活，把获准版本保存为独立 job 授权，不延长原 Action 有效期。任务配置是本地持久化，不等于生产写；监控 Action 的守卫保持原样。B 用最小贯通验证这一复用，不先建第二套审批引擎。

**免审批控制的真实改动：** 当前 GovernedTools 对 write 一律要求 ApprovedAction，不能仅关闭 SDK needs_approval。建议 B 在同一治理层增加窄义 task_control effect，仅用于本地暂停/取消，仍核验当前身份、管理权和 job 状态后原子更新；不授权恢复、创建或任何远端生产写，不另增管理抽象层。A 的 notify effect 只管外部通知；这两项是各片的必要语义扩展，不能登记成 read。恢复重新确认，只安排合法未执行时点，不重置既有发送机会。

**B/C 的定义依赖和 TTL：** 用户可确认 Agent 整理的自包含说明，不恢复原文证明。服务端在生成该草案的工具调用入口，冻结此前已回放及本轮已产生、模型可见的全部 Evidence ID 为 `definition_evidence_ids`，不是模型自行选择引用。普通轮次必须在工具调用时读取现有 `replayed` 回调所提供的 `session.replayed_evidence`，再合并治理账本中的本轮可见证据；不能用通常为空的 `ctx.evidence_ids` 或回放前的空快照替代。沿 app.py:677/843 的既有区分，仅审批恢复时由已恢复的 `ctx.evidence_ids` 提供历史。当前草案工具自身及之后的审批回执不反向加入该版本。连同原 owner/channel/source_session 的必要归属引用保存，创建/确认时复核，并在材料里列出依赖源及最早失效时间。依赖为空的纯文字按任务保留期；有依赖的正文及派生副本的 content_expires_at 只取最早数据期限，不因 task TTL 续期。发送截止另由 run_at＋lateness_seconds 计算，仅用于 tick/claim 的 missed 判定；不得用短发送窗口缩短有效群历史的保留期。B无依赖正文期限保持发送截止，普通 Evidence/Session 副本沿正常保留期；C无旧依赖定义按用户指定期限或长期授权保存，运行结果仍按正常保留期清理。后台入模/发送按当前创建者，定义展示按当前查询者的数据权限，配合服务器保存的源归属，经现有 EvidenceStore 批量读取/校验路径复核 TTL、策略、对象依赖、当前模型数据策略及机器人接收范围；管理员能停用不等于能借创建者读正文。开始前统一核验当前静态授权、目标、数据期限和三态成员；保存前只复核任务状态/期限，发送前再核验主体，数据权限仍由Evidence复核。不能仅调单条 _checked 而漏 _verify，也不能在新 Session 里冒充旧 Evidence。只做获批定义依赖的数据核验，不续跑原 SDK Session、不向后台 Agent 加依赖源的查询权限。失效/撤权则停止使用正文，发送为 not_sent；沿现有维护清理删除过期派生正文/缓存，只留安全任务状态与回执，不延长或复制原 Evidence。已知一次执行时刻晚于依赖期限应在创建时拒绝或请用户改为到点重新调查，不能答应后再静默丢弃。

**U6 的实际期限代价：** 群 Session 为全群共享；只要旧查询 Evidence 仍向起草模型回放，即使用户这条 U6 已自包含、正文未引用旧数据，也会冻结这些依赖。示例配置 `examples/xiaowei.example.json:5` 的保留期为 604800 秒（7天），因此这类定义受最早旧证据期限限制，剩余时间可能仅几小时，至多7天，不能按“长期每3小时”承诺持续数周。公司实际保留配置和出现频率尚未验证。确认材料必须写“本任务将于 X 时失效”（绝对时间及业务时区，取数据截止与配置有效期的较早者），说明因旧证据依赖受限，并给出无旧依赖的创建办法；无数据截止者：B展示发送截止，C展示用户期限或“长期，直到取消或权限失效”，不另加固定寿命。带依赖任务到期须重新生成确认，不能只续期旧引用。

最小可用办法是由用户显式发送现有 `/新建`，再完整提出自包含任务，起草前不查询旧业务数据；新上下文实际没有回放/新产出的业务 Evidence 时，定义才没有旧数据期限。`ChannelService.new_session` 明确轮换整个群的共享会话且不复制历史；必须告知会影响全群后续上下文，不能由 Agent 为省事自动执行，也不能把旧草案复制过来消除依赖。此办法须在 B/C 测试，而非把已有命令当作新链路已验证。任务仍受各自实际有效期、当前权限和预算约束。任务本身独立于原 Session；每次业务结论重新取证，历史说明不充当当前健康事实，本期不新增完整历史快照导出/存档功能。

**非阻断优化备选：隔离起草。** 若 C 的 U6 评估表明上述期限或共享会话切换频繁妨碍正常使用，优先评估仅为已明确的定时请求增加一次无历史、无工具的公开 SDK Runner 规范化调用，输入只含当前用户原消息及必要非秘密可信配置；不传原会话、历史生成的草案/总结或含历史数据的动态指令。自包含请求成功整理后仍经同样校验和用户确认；“照刚才的方法”等依赖历史的请求继续保留定义依赖，不能靠隔离洗掉依赖。SDK 公开的 Agent.clone/Runner.run 可复用，但 app.py:681 的 finish_on_limit 实际传入 history，不能原样当成无历史调用。代价是一笔额外模型调用，计入预算且须验证输入确无历史；不是前置意图分类器、第二业务 Agent 或另一套 Loop。本修订只记录重评路径，不要求 A/B 增加这次调用，不建来源分类器。

批准绑定可使用不可变草案/任务 ID＋版本，正文由任务服务按上述依赖校验后展示，避免把旧业务内容另复制成无依赖的通用 Action 参数/状态。现有 Action.status 直接返回已存材料，Evidence.record 默认从本次记录重新计算 TTL，不能假称它们已自动继承定义依赖；B/C 须沿审批材料、派生 Evidence、Session 与运行结果证明同一数据截止和当前权限生效。只作本地任务所需的窄适配，不重构通用 Evidence/审批平台；未贯通前不能开放带历史依赖的任务。

分片增加应用表，沿现有迁移、归属/版本和保留机制，不改 SDK 私表：

- A 仅 notification_attempt：上述意图键、归属、逻辑接收方/目标版本、最终内容的必要绑定、占用/结果时间、安全状态码；记录关联原请求，不能依赖最终模型回答保存成功。准入并占用必须早于 HTTP；落库失败不补发。
- B 增 scheduled_job：不可变获批定义/版本、创建者及操作群、批准记录、definition_evidence_ids 及最小源归属/数据期限、状态、计划时间/迟到策略、机器人/读范围及预算、next_run。只保存必要依赖引用和有期限正文，不复制原聊天历史，不建原文签名链。
- B 只保存固定提醒的 occurrence/发送占用；C 再增加 Agent run 所需的新 Session/turn、开始/结束、状态/安全原因及Session/turn关联；调用/token/耗时只记安全日志，不保存回答或用量副本。可用同一运行表，B 不提前实现 C 的 Agent 状态。每个计划时点唯一占用，运行与发送状态分开。

链路：群消息→现有身份/治理→Agent 草拟→冻结定义依赖并校验/展示→有权用户确认→保存 job。到期→当前主体/定义依赖和 job 准入→固定文字或独立 Application.run_turn→保存合规结果→当前接收范围/Evidence 复核→原子占用发送机会→GovernedTools(notify)→httpx2 POST→落定回执。后台 Agent 不直接持有 notify，可信交付闭包也不能绕过治理。RunContext 只加必要安全标识，不携带客户端/依赖/凭据。

**发送与整轮结果分开：** A 已 accepted 后若最终回答校验、模型或 Session 提交失败，已有 attempt 不能回退为未发。既有失败回执/状态读取叠加当前有权查看的独立发送状态：“消息已提交，后续回答未完成”；unknown 仍写未知，不笼统只报 model_failed 并诱导重发。记录暂不可核验时说无法核验，不虚构已发或未发；不另建查询 API/CLI。

## 5. 时间、权限变化及恢复

**用户已确定的主体：** 每次后台 Identity.subject_id 为创建者，owner 为原指定群，channel=feishu，session_id/turn_id 每次新建；不借批准者或共用 Web 身份。读取沿当前群共享授权，另核对创建者当前成员资格、独立通知权限、批准范围及配置的自动只读集合。批准者只在当次激活/恢复时需要相应确认权限；之后仅撤销其批准 grant 不自动撤销已建任务，管理员仍可明确停用。若批准者同时是创建者，其当前读取/通知权限被撤销仍按创建者失权处理。暂停/取消要求操作者既是当前可确认的原指定群成员，又是任务创建者或个人 grants 明确配置的任务管理员；管理员同样须通过当前成员核验，个人 grant 不能替代群成员资格。成员不可核实时不执行管理变更，按现有授权失败方式提示。不能把 StaticAccess 对群工具的共享授权当成所有成员都能管理别人的任务；沿同一配置授权来源加 job 归属检查，不建第二套角色平台。

保留单进程和同任务不重叠，后台占用现有全局并发；at 存 UTC aware 时间并展示业务时区，interval 按批准锚点计算，不随上次结束漂移。首跑时间、时区、迟到窗口及次数/有效期/预算初值来自管理员配置，创建材料必须显示有效值，Agent 不为已有默认值另起澄清；U5 解析为下一个“明天上午10点”的绝对日期/一次任务，不变成每天10点。每轮预算必须有界，不硬编码 30 天/240 次/60 秒，也不预建计费平台或承诺硬美元限额。

| 情况 | 最小行为 |
| --- | --- |
| 批准达到或晚于提醒时间 | 同一激活准入事务以当前时钟复核 now >= run_at，拒绝激活，保持不可发送；Action 结果和群回执明确“提醒时间已过，未激活，请重新创建”。确认材料要求在提醒时间之前批准，不以迟到窗口延长批准时限 |
| 已激活的一次性提醒尚未开始 | 在配置的允许迟到窗口内可补执行一次，标实际发送时间；超过窗口记 missed。短暂成员核验失败可保持未开始，下一次有界到期检查重核，直到窗口结束。B 采用管理员配置的一小时窗口；不因固定“迟到两分钟”直接丢弃 |
| 周期巡检错过时点/重叠 | 不积压重放历史巡检，按下一合法时点重新取证；只更新job.reason和next_run，未开始的历史时点不另建运行行。已进入队列的真实机会仍保留skipped状态；周期允许迟到窗口与一次性提醒分开配置 |
| 执行槽忙或 Application.run_turn 明确返回 busy | 只有模型/业务工具确未开始才按未开始处理：B在迟到窗口内再准入；C准时进入的同一occurrence可在配置排队期限内等名额，超窗skipped；不复制机会。业务执行后的超时/失败不能归为 busy 重跑 |
| 成员接口超时、异常、False 或其他无法确认 | 当前不读业务源、不发消息；周期本轮记未核实、下个独立时点重查，job 保持启用。不沿用上次成员资格，也不把一次网络故障升级成人工恢复。False 不能证明撤权 |
| 确定撤权/目标改变/批准范围不再有效 | 复用现有授权源可确定的拒绝，停用并要求有权用户恢复；任务不绑定批准时模型；换模型或调整数据策略本身不自动停用，每次按当前配置复核。更改任务定义须取消后重新创建并确认。静态改权沿既有停用/排空旧进程后启用新配置的规则，不承诺跨进程即时撤权 |
| 单轮模型/只读源暂时失败 | 该轮未完成，后续时点独立重查；需要用户澄清/审批或定义失效才转需处理。不能假装健康；有批准通知范围时可发该轮一次“不完整/未完成”摘要 |
| 运行/结果保存中断 | 标 interrupted/失败，不续跑原模型或补保存重查；新 Session 按现有一致性处理。后续时点只有 job 仍有效才能开始 |
| POST 之前未准入/存储不可用 | not_sent，零 HTTP；不能先发再补记意图 |
| API 明确拒绝或可证明请求未发出 | failed；本期仍不自动重试 POST |
| POST 可能已到达、超时/响应损坏、占用后崩溃或接受后落库不明 | unknown，不自动再次 POST、不重跑 Agent。补执行仅适用于从未开始/未占用发送机会的提醒，不适用于该状态 |
| 接口合法成功并落库 | accepted，只表示 API 接受，不表示群成员收到/阅读 |

**不能永久静默：** 经授权的任务状态查询显示最近核验/成功时间、末次原因、连续未核实次数（可由运行记录取得）和下一计划时间；连续未核实在现有安全日志中可见。partial 名单始终找不到创建者时保持不执行，由管理员据状态处理成员目录覆盖或任务归属，不能改用批准者身份继续。不能为了告知故障而绕过当前权限给 Webhook 额外发消息，不新增通知渠道或固定失败次数自动解禁。

**接收目标与凭据分开：** 任务绑定稳定逻辑机器人别名及非秘密接收目标版本，不绑定原始 URL/Token 的变化。管理员确认同机器人同接收群、权限范围不变的凭据轮换，只更新安全引用/秘密值并按现有方式重载，不让全部任务重批；轮换不能重置已有 attempt。实际换群/换机器人或扩大接收范围必须变更目标版本并重新授权。Webhook URL 的不透明 Token 不能证明是轮换还是换目标，无法确认同目标时按目标变更处理；这个声明来自可信管理员，不来自模型。不开发自动目的地识别或密钥管理平台。有意接受的残余风险是管理员误换群但未更新版本可能发错群；首批靠管理员核对实际机器人/群并用测试消息确认，同类配置误配出现时再评估额外校验。

**启动/停用的具体入口：** B 必须增加服务端配置 `scheduled_tasks.enabled`（默认 false，B 已实现），false 同时阻止后台 run 准入和后台发送机会占用；状态查询/直接停用仍可用，不影响 A 的显式即时请求。循环只在持实例锁的启动恢复成功、装配完成及 readiness 正常后启动；新 job/run/attempt 的准入事务复用 InstanceLock.admits 的数据库屏障，并在发送前复核 readiness。丢锁后不再新开运行或占用机会，已准入请求可能落定或未知，不承诺外部撤回。暂停/取消与发送机会占用先锁同一 job，在事务内的新语句快照核对当前状态及是否已有 attempt；已准入则不改状态并明确告知，防止等待 claim 提交后仍按旧快照暂停的竞争；不引入新 lease/fencing 体系。

普通重启：未开始的一次性按迟到窗口处理，周期按跳过策略；已开始/未知通知不重放。备份隔离恢复先不接真实入站，并设 `scheduled_tasks.enabled=false`，核对恢复点后再显式启用合法未来任务；B 须实测 false 模式零后台模型/业务/发送 I/O。暂停/取消、恢复及凭据轮换均不清空发送记录。旧镜像不兼容新 schema 时按备份恢复，不直接修改 SDK 表。

## 6. Webhook 与 Node 的首批边界

Webhook 复用 httpx2.AsyncClient、TLS 校验、有界超时/响应和生命周期；可信静态官方 HTTPS 目标，不接受用户 URL、不跟随重定向、不隐式继承环境代理，不自动重试。只发 text，最终 JSON（含签名）不超过官方大小限制；后台超限用同一发送机会发固定容量说明，run 记 content_too_large，不新增截断或拆分；发送主体暂不可核验返回带类型结果，零POST、run记 authorization_unverified，连续计数递增，不能归为 execution_failed；密钥、URL、原始异常/响应不进模型、Session、Evidence 或日志。严格检查 HTTP 和合法业务 code=0，关键词/IP/签名按真实配置验证；不新增多厂商、卡片、@all、自动拆分文件或通用 HTTP 功能。既有飞书应用机器人 uuid/message_id 不用作自定义 Webhook 保证。[飞书官方参考](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot)、[HTTPX2](https://pypi.org/project/httpx2/)。

D 先复核实际 MCP 版本/结果与现有协议反例：若能完整保留 resultType、标签、样本值/时间、warnings 和目标覆盖，复用该契约；若仍是锁版有歧义的文本，沿已证实缺口补最少结构化读取。需要新增 HTTP 时仍经治理、同一个获准 Prometheus，端点/认证另取服务端安全配置，不把 MCP 地址当 Prometheus API；A–C 不依赖此接入。不能为了避免 Adapter 就让模型猜解析歧义文本，也不把支持 structured_content 等同于保真样本。

D 首次只保证：目标覆盖/采集状态、CPU、可用内存、文件系统磁盘空间及有界摘要。先确认 Node job/labels、实例口径、CPU rate 窗口和必要磁盘过滤；分母不能仅取有 CPU 数据的主机，down/缺项/重复 series、NaN/Inf、warnings/截断均不能算健康。CPU 用 Prometheus 正确 counter 语义，不手建复杂采样算法；源/工具/预算是硬权限，Node selector 是覆盖口径，不建指标 ACL。

不强制首批实现 inode、IO 瓶颈、网卡利用率、完整三小时历史或“持续15分钟”判断；IO/网络在公司指标和业务价值核实后再扩展，每次结果明确哪些未检查。核心指标的窗口、单位、阈值和覆盖口径仍须验收；未确认阈值时只报观察值/限制，不把 Grafana 默认颜色当告警规则。没有告警规则不妨碍核心巡检，也不能声称替代常驻告警。[Prometheus API](https://prometheus.io/docs/prometheus/latest/querying/api/)、[Node Exporter](https://prometheus.io/docs/guides/node-exporter/)供实际版本核对。
