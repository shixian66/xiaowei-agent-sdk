## 2. 用户已确认的展示规则

- 模型继续组织结论、解释、建议及文字与事实的顺序，只选择 fact 和 full/brief；未引用结果不补交。“任务所需字段”指代码为每个工具确定的固定业务字段集合，模型不选择字段。
- 正文、纯文字通知、MD/HTML 报告正文及预览，不直接展示由代码将工具对象序列化形成的 JSON 数据块；统一展示规则，不统一回答模板。
- 非附件飞书卡片“查看依据”和 Web 技术折叠区保留获准原文 JSON，不因业务表格被判为冗余而省略。用户主动展开即可查看，满足“明确索要时允许”；沿用现有入口，不另做意图判定、来源证明或 schema。非附件卡片容量不足时，普通事实沿用 §3.3 的整技术区省略及标注。附件预览模式是已确认例外：普通事实的卡片折叠区不附原文，避免挤占正文预览行；第二步完成后报告正文也不附原文。
- 业务 JSON 字符串、Prometheus 结果文本原样作为文字展示，不猜测解析、不额外加 JSON 引号或反斜杠；渠道所需的 HTML/Markdown 安全处理保留，以解码后的可见文字不变为准。
- 改动前已冻结的 DeliveryPart 正文及文件沿原语义补发，使用原字节、原 uuid 和已有文件键，按已确认的 30 天保留期失效并由现有清理流程删除，不增加旧字节检查器或持久字段。
- unknown、审批送达及 Action 语义不变；已发送消息和已下载文件不追溯改写。冻结补发仍可能呈现旧格式，这是已接受的过渡行为。

## 3. 最小修改

### 3.1 已复现列表转为业务行

在现有 `business_presentation` 中，将 Alertmanager 的 data、Grafana get_annotations 的 annotations 映射为 rows，复用现有表格路径；固定字段由各工具的现有获准契约确定，告警、事件的来源、时间及必要限制继续显示。

其他结构有具体失败样例后再扩展；不建设通用嵌套布局、字段组、编号项或整份 Evidence 的递归展示。直接使用 v4 已有获准数据，不增加“result_json 缺失时回读 Evidence”的恢复路径。

定位：`feishu_render.py:396` 的共享业务视图、`:704` 的字段/值回退、`:829` 的表格消费；数据契约见 `runtime.py:1102` 与 `mcp.py:1202`。

### 3.2 共用一个可读值格式函数

把普通业务事实在飞书 `_cell`、`business_text` 中的 `value_text`、Web `_web_cell` 及报告字段/单元格中重复的可见值格式化合为一个共享函数，卡片、预览、Web、纯文字通知及报告的现有消费者复用。

- 字符串直接显示原文，不加 JSON 引号和反斜杠。
- NULL、空字符串、缺失、false、0 明确区分，沿用“NULL（空值）”“（未提供）”等现有写法，并给布尔值、数值必要的文字标注。
- 嵌套值只在现有字段或单元格内格式化：映射显示为“键=值”，用“；”或换行分隔；标量列表用“、”连接，含对象的列表每项一行；更深层按同一规则缩进。空列表、空映射都显示为“（无）”，不显示为空串；字符串原样，None 显示为“NULL（空值）”。例如告警 labels 为 `{"alertname":"HighCPU","instance":"host-a","severity":"warning"}` 时，单元格显示 `alertname=HighCPU；instance=host-a；severity=warning`；status 为 `{"state":"active","silencedBy":[],"inhibitedBy":[],"mutedBy":null}` 时，显示 `state=active；silencedBy=（无）；inhibitedBy=（无）；mutedBy=NULL（空值）`。两者均不显示 JSON 对象或 JSON 围栏。
- silence matchers、告警组 alerts、Grafana panels/tags 及按契约解码后的看板定义都复用上述单元格规则，不另做结构映射或展示数据模型；这不新增 §3.1 所排除的通用嵌套布局。大整数保持原值；大看板展开可能很长，走现有容量路径与报告，不另做摘要。

审批材料与动作类分支本期不改：`business_text` 的 `_control_fact` 分支（`feishu_render.py:593–601`）和 `requires_complete` 完整材料后备分支（`:646–688`）保持现状，审批材料继续运行现有审批测试；这些测试不能替代控制事实任务列表的格式验收。卡片控制事实的 `add_table`（`:871`）与普通事实共用 `_cell`，Web 任务列表也经 `business_presentation → for_web → _web_cell → _cell`；格式函数由调用方传入或显式区分普通／控制事实，仅普通业务事实接入新的共享函数，控制事实两条路径保持原格式。任务列表的“任务、状态、计划时间、有效期、说明”增加卡片与 Web 输出不变的断言；完整审批材料、技术区及状态文案沿用现有路径。

实现定位须区分“内部包装”和“可见格式”：`feishu_report._fact_json` 不是 v4 报告入口；v4 经 `_fact_section(business=True)` 编码内部段落。保留其中的 `json.dumps(values)`（`:139`），它供 `:765–769` 的 `json.loads(section.value)` 解码后按整行分片。报告只改普通业务事实的 `_html_fact`、`_md_fact`、`_md_cell` 可见格式及 `:421/449` 的嵌套值 JSON 围栏输出，接入共享函数；不能把内部包装换成可读字符串。

定位：`feishu_render.py:208/605`；`feishu_report.py:111/133/229/333/352/383/421/449`，分片对内部结构的依赖在 `:769`。

### 3.3 契约编码与各出口

Grafana 契约解码仅限投影正好为 `Projection(("result_json",))` 的工具，工具 ID 集合由 `grafana.py` 与 `grafana_c8.py` 中的对应契约提供（`grafana.py:314`，`grafana_c8.py:360/412/421/430`）。`DeliveryFact.result_json` 保存整份获准投影；投影内的元数据键 `result_json` 才是这些工具用 `_json(value)` 编码、需要按契约解码的内容，两者不能混用。普通业务事实解码后进入可读视图，不按工具名前缀、同名字段或字符串外观泛化解析。上述审批／动作分支例外不变：`update_dashboard` 的审批参数 `dashboard_json` 及前后定义保持原样、完整展示（`grafana.py:437–443`）。

v4 普通事实采用方案 A：只将 `feishu_render.py:1032` 的原文附加条件改为 `fact.result_json is not None and not attachment`（`attachment` 来自 `attachment_preview`）。非附件卡片不再按 `_raw_redundant` 省略原文，避免去掉字符串引号后正文中的字符串“1”和数字 1 同形又无原文可查；附件预览卡片不附普通事实原文。`:1473–1480` 先放技术区、再用 `fitting_prefix` 求预览行数的顺序保持不变，不新增裁剪或容量机制。非附件卡片容量不足时沿用 `:1395` 起的整技术区省略及 `TECHNICAL_OMITTED` 标注，代价是大表可能更早丢掉整个技术区（含实际 SQL）；附件预览不受新增原文占用影响，SQL 按现有规则保留。控制事实的技术区仍走原分支。

Web、飞书卡片、纯文字通知、MD/HTML、预览中的普通业务事实统一消费共享视图及可读格式函数，移除这些出口默认把工具对象 dump 成正文的路径；技术折叠区按上述规则保留原文。显式报告及容量附件使用同一业务内容，继续复用现有分片。`channel.py:466/692` 的无版本失败回执没有事实，直接走 `feishu_render.py:1253` 的纯代码文本分支，不经 `_cell`；保留原文案，不强行附加事实结构。
